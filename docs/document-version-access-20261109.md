# Доступ к истории проектных документов — 09.11.2026

Основа runtime `b30168d`, локальная основа с тестами предыдущего аудита `f7633a9`.
Подтверждены два нарушения в `/document-versions`: директор видел версии другой
компании; заказчик получал внутренние суммы и комментарии снимка АОСР. До изменения
оба реальных HTTP/PostgreSQL-теста завершились FAIL. Рабочие данные для проверки
чужого доступа не использовались.

## Исправление

История использует существующий RecordScope: текущую роль и членство в выбранной
компании, доступ к объекту и разделу работ. Поддерживается только фактический тип
`hidden_works_act`, который записывает текущий сервер. Проверяются исходный акт,
однозначный объект внутри его компании, а также сохранённые в JSON снимка ID акта,
company_id, объект, раздел и связь с ЖПР. Владельцем не назначается компания,
выведенная из названия. Несовпадение или отсутствие записанного владельца скрывает
версию. Удалённый родитель, неизвестный тип и повреждённый JSON не дают доступ.

Для заказчика доступны только версии акта подтверждённой работы. Для мастера,
бригадира и субподрядчика дополнительно требуется `work_journal.master_id`,
совпадающий с текущим пользователем. Этим ролям возвращается ограниченный набор
полей без внутренних сумм, комментариев, ссылок на файлы и служебных метаданных.
Директор сохраняет полный снимок своего разрешённого акта.

Миграция не нужна: текущий writer сохраняет `row_to_json(hidden_works_acts)`,
включая company_id. Его реальный PUT и последующее чтение проверены в тесте.
Два новых nullable owner-поля из #395 не переносились вместе с чужой веткой
миграций. Исторические строки не переписываются; снимки без достоверного владельца
не доступны. Имена объектов используются только для сверки внутри уже установленной
компании с запретом неоднозначных совпадений.

- 8 frontend-тестов реестра PASS. Frontend не менялся, повторная сборка не требуется.

Команда новых регрессий:
`python scripts/run_supplier_catalog_postgres_tests.py --require-no-skips backend.features.document_versions.test_access_postgres.DocumentVersionAccessTests`.
Python 3.12, PostgreSQL 15 в PATH. Логи: `tmp/document-version-access-20261109/`.

В ходе проверки исправлены тестовые предпосылки: customer fixture недоставало
существующей миграции 0077; mock старого OpenAI-вызова заменён на текущую границу

и ожидание 409 для несовпадающей компании файла. Это отдельные ошибки теста,
не дополнительные доказанные ошибки продукта. Логи неудачных прогонов сохранены.
У тестового логгера при искусственном сбое остаётся предупреждение о недостающем
`api_errors.owner_scope`; проверка rollback независима от этого логгера.

## Совместимость и ограничения

- API неизвестной/чужой/неподтверждённой версии возвращает 404 вместо прежнего
  200 с `error`; список не показывает недоступные версии.
- Без owner в сохранённом снимке доступ запрещён. Перенос акта, изменение связи
  ЖПР/раздела или переименование объекта может скрыть старый снимок до отдельной
  проверенной процедуры восстановления происхождения. Автоматического переназначения нет.
- За один запрос рассматриваются последние 200 версий доступных родителей;
  непригодные снимки исключаются. Пагинация глубокой истории не добавлена.
- Запись версий остаётся прежней; отдельная атомарность writer и уникальность
  version_label не входят в эту задачу. Массовый экспорт иных типов документов,
  все отраслевые журналы и внешние хранилища этим проходом не проверены.
- Мутации и скачивания под чужими ролями проверены на синтетических данных.
  Production-браузер используется только для чтения разрешённого реестра/истории.

## Установка

Backend-only выпуск без миграций и изменения флагов. Перед переключением —
стандартный резерв и восстановление в отдельную проверочную БД; сверить также
`document_versions`, `hidden_works_acts`, `project_documents` и `file_ownership`.
После запуска проверить health/схему 0108, контрольные таблицы, текущие frontend
файлы и браузер директора: реестр, история и просмотр версии. Только после всех
проверок оформить verified/deployed и удалить резерв/staging этого выпуска.
Возврат старого кода возвращает выявленный пробел доступа; при сбое предпочтительно
сначала закрыть оба `/document-versions` маршрута и восстанавливать доступ после
проверки. БД при откате кода не восстанавливать поверх пользовательских изменений.
Фактический результат выпуска фиксируется отдельно, установка этим документом
заранее не объявляется завершённой.
