## Что изменилось

Один личный черновик пакетной выдачи на пользователя и компанию хранится в PostgreSQL.
Сохраняются точные ID партий/объектов, строки количества, включая незавершённый ввод,
и основание. Черновик сам не проводит выдачу, не резервирует остаток и не создаёт оплат.
На другом устройстве нужно войти тем же пользователем и выбрать ту же компанию.
Автосохранение начинается через 350 мс после изменения; доступна отдельная кнопка.
Надпись «Черновик сохранён на сервере» означает подтверждённый снимок.

`GET/PUT /warehouse-distributions/draft` проверяют действующего пользователя,
компанию и текущие права на сервере. Идентификатор владельца не принимается от клиента.
PUT передаёт `expectedRevision` и UUID сохранения; блокировка строки и проверка
ревизии выполняются в одной транзакции. Устаревшая запись получает 409.
Повтор после потери ответа использует прежние UUID, ревизию и содержимое.
Серверный конфликт сохраняет ввод в форме, запрещает выдачу и не вызывает
автоматическую перезапись. Можно скачать JSON-копию и явно загрузить серверную версию.
Автоматического слияния и импорта такой копии нет.

Выдача передаёт `X-Warehouse-Draft-Revision`. Существующий JSON команды и его
идемпотентный хеш сохранены. Сервер сверяет ревизию и нормализованный снимок,
проводит существующую складскую операцию и очищает черновик в той же транзакции.
При ошибке остатков откатываются оба действия. Повтор проведённой команды
возвращает её результат, не очищая следующий черновик. Успешная операция записана
в черновике: новое устройство узнаёт о ней даже после потери ответа в старой вкладке.

При быстром переходе в другой раздел неподтверждённый ввод остаётся в памяти вкладки.
При возвращении проверяется серверная ревизия; изменившаяся версия даёт конфликт.
Закрытие/обновление вкладки с неподтверждённым вводом вызывает предупреждение браузера,
в том числе после ухода из формы. Это вспомогательный буфер, не замена серверному
сохранению: он не переживает принудительное закрытие процесса браузера.

## Что проверено фактически

| Действие | Куда поступает результат | Проверка | Результат |
|---|---|---|---|
| Незавершённый ввод, включая `2.` | Личный серверный черновик | PostgreSQL, компонент и новый браузерный контекст без общего хранилища | Работает |
| Два устройства меняют один черновик | Только одна текущая ревизия в БД | Два конкурирующих PUT; два браузера | Второе изменение получает 409, локальный ввод сохранён |
| Быстро уйти из раздела до автосохранения | Временный буфер вкладки, затем сервер | Регрессия сначала падает, после исправления проходит | Исправлено |
| Серверная версия изменилась во время ухода из раздела | Локальный ввод остаётся отдельным | Компонентный тест | Нет автоматической перезаписи |
| Выдать 3 кг на Alpha и 1 кг на Beta | Общий склад, материалы объектов, партия, движения, история распределений | Настоящий API и SQL, браузер | Одна операция, две выдачи; общий остаток 6 из 10, Alpha 3, Beta 1 |
| Потерять ответ успешно проведённой выдачи | Серверная история и очищенный черновик | Прокси разрывает ответ после commit; третий новый браузер | Пустой черновик и сообщение о завершённой выдаче |
| Повторить неподтверждённую выдачу | Та же операция | Равенство тела/UUID/заголовка; SQL после повтора | Остатки и число операций не изменились |
| Открыть историю связанным ролям | Существующий API истории выдачи | Бухгалтер, заместитель, кладовщик | Видят обе выдачи; бухгалтеру POST запрещён (403) |
| Выбрать другую компанию / другого пользователя | Отдельный черновик и история | PostgreSQL, включая одного пользователя в двух компаниях | Нет смешения данных; чужие ID — 404 |
| Отозвать права / получить поздний ответ старой формы | Закрытый доступ; новая форма не меняется | API и компонентные регрессии | Работает |
| Выдать больше остатка / другой снимок | Нет операции; прежний черновик | PostgreSQL | 409, частичных движений нет |

Браузер использовал реальный компонент, реальный складской API и отдельный PostgreSQL.
Аутентификация в этом стенде синтетическая; разрешения проверял существующий серверный
resolver. Сметная аннотация стенда подменена. Это не проверка входа и всех кабинетов
на рабочем сервере. История Alpha/Beta фактически показана в браузере; остальные роли
проверены через API, а остатки связанных таблиц — через SQL. Отдельные страницы
материалов каждого объекта и браузерные кабинеты каждой роли в этом блоке не обходились.

## Совместимость и необходимые шаги установки

1. Нужна отдельная команда пользователя на миграцию рабочей базы: переданные правила
   AGENTS запрещают применять production-миграции автоматически. Этот отчёт не разрешает
   установку. Релиз сейчас только локальный; `verified.json` и `deployed.json` не созданы.
2. Назначить окно. Пользователям сохранить отдельные копии незавершённых старых форм;
   старый frontend не умеет перенести их на сервер. Неподтверждённые операции сначала
   сверить с историей/остатками, не создавать заново с другим UUID. После проверки копий
   закрыть старые вкладки, не перезагружать их с несохранённым вводом.
3. Сверить фактические HEAD/изменения сервера, версию БД 0110 и frontend-флаги.
   Если база/код отличаются от ожидаемого, сначала пересмотреть пакет. Резервировать
   текущую БД и uploads; frontend — только текущий manifest, его ресурсы и public-файлы.
   Проверить восстановление резерва в отдельную БД и повторить миграцию на этой копии.
   Полный Git bundle и копии исторических static-чанков не нужны.
4. Под maintenance/deployment lock остановить запись. Установить согласованный backend
   и frontend. В окружении сервера выполнить `.venv/bin/python -m alembic upgrade
   0111_warehouse_batch_drafts`; не использовать stamp вместо миграции.
   Схема добавочная, таблицы остатков и документы не переписываются.
5. До миграции новый API черновика выдаёт понятный 503. Старые выдачи без заголовка
   остаются совместимы с прежним контрактом и **не потребляют серверный черновик**.
   Поэтому смешивать работающие старые и новые вкладки нельзя: старый клиент не имеет
   новой защиты общего черновика. Новая форма всегда передаёт ревизию.
6. Старый sessionStorage pending без userId намеренно блокирует новую операцию.
   Нельзя автоматически приписывать его текущему пользователю или удалять как мусор.
   Сначала сверить исходную операцию; после разрешения неопределённости использовать
   новую вкладку. Сам серверный черновик от sessionStorage не зависит.
7. После запуска отдельно проверить backend/health и ошибки, БД/версию/сохранность
   исходных данных, хеши текущего frontend, затем браузерный сценарий разрешённой роли.
   Проведение тестовой выдачи на рабочей базе без отдельной необходимости не выполнять;
   полный сценарий предварительно подтверждать на восстановленной тестовой копии.
8. Только после всех четырёх фактических PASS записать соответствующий установленному
   HEAD `verified.json`, затем `deployed.json`; выполнить очистку по
   `docs/deployment-retention.md`. При провале любой проверки оставить резерв.

## Откат и оставшиеся ограничения

- Downgrade 0111 намеренно запрещён: автоматический DROP потерял бы черновики.
  При проблеме остановить складскую запись (`WAREHOUSE_DISTRIBUTION_ENABLED=0`),
  сохранить резерв и диагностику. Предпочтителен исправленный совместимый релиз.
- Если нужен откат к предыдущему коду/frontend, таблицу и данные 0111 сохранить,
  файл миграции оставить доступным инструментам Alembic. Не понижать версию stamp-ом.
  Складскую запись не открывать до сверки оставшихся черновиков с проведённой историей:
  прежний код не потребляет их. Восстановление всей БД допустимо только отдельным
  решением с учётом всех записей после резерва, не как автоматический откат интерфейса.
- На другом устройстве доступен только подтверждённый сервером ввод. Принудительное
  завершение браузера/ОС до подтверждения может потерять последние символы; пользователь
  должен дождаться статуса сохранения. Работа без сети не делает локальный ввод серверным.
- Один личный черновик на компанию, без списка нескольких черновиков и совместного
  редактирования разными пользователями. Автоматического объединения конфликтов нет.
- Изменения другой вкладки обнаруживаются при сохранении/выдаче или явном обновлении,
  постоянной push-синхронизации нет. Сохранённые ID недоступных партий/объектов остаются
  видимыми, но новая выдача требует актуальных разрешённых данных и остатков.
- Не проверены на рабочем сервере: установка 0111, репетиция на свежем production backup,
  реальная cookie-сессия после обновления, мобильные Safari/Android и аварийное завершение
  ОС. Нет отдельного независимого агентского ревью этого блока; выполнена собственная
  проверка изменений. Технических падений итоговых локальных проверок не осталось.
