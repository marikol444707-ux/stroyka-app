Ветка: `fix/warehouse-transfer-persistence-20261109`. Новая миграция: `0113_warehouse_transfer_drafts`.
Предыдущие исправления смет, кабинета мастера, выдачи и возврата сохранены.

## Подтверждённые проблемы

До исправления формы отправки и приёмки держали ввод только в памяти страницы.
GET `/warehouse-distributions/transfer-draft` возвращал 404; два frontend-теста
не находили восстановленные формы. Результаты RED сохранены.
При проверке интеграции обнаружен второй дефект: восстановленные с разных устройств
возврат и перемещение взаимно блокировали даже отмену формы. Отдельный тест сначала
упал. Теперь отмена перемещения доступна при блокировке другой формой, но недоступна
во время отправки команды, её неопределённого результата, загрузки или потери прав.

## Результат

Один личный черновик отправки **или** приёмки принадлежит точной паре
`company_id + user_id`. Сохраняются только тип формы, ID распределения/перемещения,
объект назначения, введённые количества и основание. Неполный ввод вроде `2.`
разрешён в черновике, но не в складской команде. Имена и остатки берутся из
авторизованных серверных записей, не используются для определения принадлежности.
Подтверждение физической приёмки остаётся только в текущем открытии формы.

PUT требует `expectedRevision` и `requestId`. Сервер блокирует строку и проверяет
ревизию атомарно; 409 сохраняет проигравшие правки в форме без автоматической
перезаписи. Есть скачивание локальной копии и явная загрузка серверного варианта.
Сохранение через 350 мс и кнопка сохранения используют общий проверенный механизм
выдачи/возврата. До подтверждения сохранения закрывать страницу нельзя: предупреждение
beforeunload и буфер восстановления при навигации защищают несохранённый ввод,
но не гарантируют его переживание аварийного завершения ОС.

Перед новым POST интерфейс подтверждает сохранение и передаёт
`X-Warehouse-Transfer-Draft-Revision`. Backend проверяет точный снимок, проводит
существующую складскую команду и очищает черновик в одной транзакции. При ошибке
склада откатываются и движение, и очистка. Повтор исходного `requestId` проверяет
старую операцию и не очищает следующий черновик. Локальная неподтверждённая команда
теперь также изолирована по пользователю; старый ключ без пользователя блокирует
новую запись до сверки с историей, автоматически не присваивается другому человеку.

## Установка и совместимость

1. Отдельно разрешить production-миграцию 0113. Перед переключением пользователи
   завершают работу и проверяют копии несохранённых форм. Старые формы не умеют
   сохранять серверный черновик; их ввод нельзя спасти одним обновлением frontend.
   До копирования вкладки не закрывать, затем закрыть старые рабочие вкладки.
2. Проверить точную базовую версию 56cf131, чистоту отслеживаемых серверных файлов,
   SHA-256 пакета и неизменность 29 флагов. Не применять поверх другой версии вслепую.
3. Под deployment/maintenance lock при остановленной записи создать свежий резерв
   БД/uploads и текущего frontend manifest/public с его ресурсами, без старых chunks
   и полного Git bundle. Восстановить резерв в отдельную БД, проверить миграцию0113,
   полный запуск, неизменность прежних таблиц и отсутствие внешних интеграций.
4. Применить `.venv/bin/python -m alembic upgrade 0113_warehouse_transfer_drafts`;
   согласованно переключить backend и готовую frontend-сборку из пакета. Запустить
   службы, проверить версию, health/БД, журнал, OpenAPI, схему и хеши публичных ресурсов.
5. В авторизованном браузере проверить «Склад → Перемещение», загрузку трёх личных
   черновиков, партий и истории, повторное открытие/обновление. Реальные тестовые
   отправки/приёмки на рабочей базе не создавать. Запись уже проверена отдельно.
6. Только после backend/database/frontend/browser PASS создать verified.json и
   deployed.json с точным HEAD. Штатно очистить резерв и staging только завершённого
   выпуска по docs/deployment-retention.md. Если любой этап не завершён — сохранить резерв.

Новые PUT без expectedRevision получают 422; отсутствующая миграция даёт понятный503.
Новый frontend со старым backend несовместим: нет нового GET/PUT. Старые POST без
заголовка оставлены совместимыми для прежних клиентов/API: они сохраняют прежнюю
идемпотентность и проверки склада, но не участвуют в атомарном потреблении нового
черновика. Поэтому старые вкладки нужно закрыть до совместного переключения;
нельзя объявлять защиту черновика общей защитой от двух независимых физических команд.
Новый frontend не отправляет новую складскую команду до подтверждённого сохранения.

## Откат и ограничения

- При неудаче установки оставить maintenance и резерв, восстановить предыдущие
  backend/frontend согласованно. Таблицу0113 и её данные сохранить; автоматический
  downgrade намеренно запрещён. Сохранить также файл ревизии0113, чтобы Alembic
  распознавал актуальную схему при откате кода. Старый код не читает эту таблицу.
- Возврат полного дампа допустим только до возобновления записи. После появления
  новых операций восстановление старого дампа потеряет данные — требуется отдельный
  разбор, а не автоматический restore. При обычном откате приложения схему/данные
  новой таблицы не удалять; сохранённые черновики временно недоступны старому UI.
- Не проверены установка0113 на рабочем сервере, свежий рабочий backup и реальная
  cookie-сессия после такого обновления. Это этап установки, сейчас не выполненный.
- Не проверены мобильные Safari/Android, аварийное завершение ОС, долгая работа при
  потере сети и производительность на больших историях. Несохранённые правки
  не доступны с другого устройства до подтверждения PUT.
- При фильтре/странице истории, скрывающей выбранную запись, ввод остаётся видимым,
  проведение блокируется до актуальной загрузки источника. Это сохранённое поведение.
- Восстановление серверного варианта при конфликте явно заменяет текущую форму:
  сначала скачать нужные локальные правки. Автоматического объединения нет.
- Автоматического назначения мастеру, новых связей с оплатами или новой приёмки
  другой юридической компанией здесь нет. Проверяется существующее перемещение
  между объектами одной компании. Личные черновики не передаются другим ролям;
  подтверждённая история доступна существующим разрешённым ролям.
- Отдельный агент написал backend-регрессии; независимое ревью всего выпуска
  не проводилось и не заявляется. GitHub, деплой и рабочая база в этом блоке не использовались.
