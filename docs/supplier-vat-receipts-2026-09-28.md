# НДС в новых счетах и частичных поступлениях

Локальная реализация, на сервер не установлена. Миграция 0056 следует за 0055.
Серверный флаг `SUPPLIER_VAT_RECEIPTS_ENABLED=1` и флаг сборки
`REACT_APP_SUPPLIER_VAT_RECEIPTS_ENABLED=true` по умолчанию выключены.
Нужны существующие флаги спецификации строк, проверенного договора, частичной
приёмки, принадлежности поставок и качества. Для поставки без первого платежа
дополнительно нужен `SUPPLIER_UNPAID_RECEIPTS_ENABLED=1`.

## Поведение

Сумма счёта и цены строк включают НДС. Для одной строки используется явно введённый
общий НДС счёта. Для нескольких строк поставщик вводит НДС каждой позиции;
соответствие сохраняется по исходной позиции КП, а не по названию материала.
Общий налог не распределяется между разными товарами автоматически. Суммы строк
и НДС должны точно совпасть с итогом счёта. Ставки из сумм не выводятся.
Пустое поле НДС не подменяется нулём: нулевую сумму также нужно указать явно.

НДС по каждой строке неизменяем. Повтор создания счёта с другим распределением
налога отклоняется. Приёмка записывает базу, налог и общий итог накладной.
Налог очередной партии — разность округлённых накопленных сумм по строке.
Например, 1,00 с НДС 0,17 при поступлениях 0,33/0,33/0,34 даёт налог
0,06/0,05/0,06. Итог сходится до копейки.

Поступление брака сохраняет НДС своего документа, но не расходует количество
и НДС принятого товара. Нулевой явно объявленный НДС не переименовывается
автоматически в освобождение от налога. Накладные не создают второго долга:
расчёты продолжаются по исходному счёту.

## Защита базы

- Колонки НДС в строках счёта и доказательствах приёмки с проверкой точности,
  диапазона и неизменяемости.
- Сумма НДС строк проверяется при завершении транзакции создания счёта.
- Налог и база поступления проверяются относительно сохранённой строки;
  ошибочные значения откатывают накладную и склад вместе.
- Для счёта с НДС нельзя завершить регистрацию поступления без доказательств
  строк. Плательщик и принадлежность сохраняют существующие проверки.
- Пустой downgrade/upgrade проверен. При ненулевом НДС в сохранённых данных
  downgrade запрещён. Старые строки получают нулевой НДС без пересчёта истории.

## Проверки

- 8 PostgreSQL/HTTP-сценариев НДС: частичные поступления, смешанные строки,
  брак, повтор/изменение налога, откат при неверном НДС, отключённый флаг,
  неизменяемость, запрет потери истории при downgrade, нулевой объявленный налог.
- 16 прежних сценариев распределения после миграции и 8 сценариев поставки
  без предоплаты: `/tmp/receipt-vat-verified.log`, все 32 прошли.
- 40 тестов расчёта и подготовки спецификаций: `/tmp/receipt-vat-unit.log`.
- 4 теста полей НДС и точной отправки сумм в API: `/tmp/receipt-vat-ui.log`.
- Playwright: настоящий компонент на тестовой странице; ввод 12,34 и 0 сохраняет
  исходные позиции КП 7 и 2. При ширине экрана 390 поля занимают 350 пикселей,
  без внутреннего переполнения. Это проверка формы, не браузерная запись в API.
  Локальный сервер и окно браузера после проверки закрыты.
- Сборки с выключенной и включённой функцией успешны:
  `/tmp/receipt-vat-build.log`, `/tmp/receipt-vat-build-enabled.log`.
- Предупреждения AI-контроля тестовой fixture не являются проверкой AI-контроля.

## Что остаётся

Старые счета без сохранённых строк требуют отдельной подтверждённой сверки;
автоматический перенос не реализован. Отдельно остаются распределение возвратов
по партиям и налоговые корректирующие документы: финансовое уменьшение долга
само по себе не меняет первоначальные суммы НДС. Ввод сумм налога не заменяет
структурированное хранение ставок/оснований для налоговой отчётности.
Перед выпуском нужна полная браузерная проверка с тестовым API и проверяемый
деплой. Рабочие данные, письма и реальные платежи этим этапом не затрагивались.
