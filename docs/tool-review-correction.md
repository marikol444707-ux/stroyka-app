# Исправление первоначальной сверки инструмента

10.11.2026. Блок продолжает ручное распределение стоимости инструмента. Раньше
ошибочно подтверждённые получатель и стоимость не имели отдельного пути исправления.
В «Бухгалтерия → Закрытие → Инструмент в счёт оплаты» появилась команда
«Исправить первоначальную сверку» с причиной и явным подтверждением по документам.

## Правила

- Меняются только точный сотрудник своей компании и стоимость выдачи. Объект,
  исходная складская запись, первоначальный снимок и основание сохраняются.
- Если в исходной выдаче известен ID пользователя, сотрудник должен соответствовать
  его точной активной связи в компании. Совпадение ФИО не даёт права смены получателя.
- Исправление разрешено при нулевом историческом удержании и отсутствии ненулевых
  распределений/возвратов. Неоплаченное распределение сначала явно отменяется суммой 0.
  При фактическом удержании, в том числе уже возвращённом, переписывание запрещено.
- PUT `/tool-deductions/{source_id}/correction` требует `expectedRevision`,
  `staffId`, `amount`, `basis`, `confirmed: true`. Изменение источника и запись события
  выполняются одной транзакцией под общей блокировкой финансового реестра.
- При конфликте 409 ввод остаётся на экране, автоматического повтора нет.
  Применение новой ревизии и новое подтверждение выполняются пользователем.
  Поздний ответ закрытой формы не изменяет повторно открытую форму.
- История хранит прежние/новые ID, имена и суммы, автора, причину и ревизию.
  Денежные выплаты, складские записи и старые нулевые распределения не переписываются.

## Проверки

До исправления 8 backend-тестов дали 15 отказов в сценариях и subtest: endpoint 404.
Четыре новых frontend-теста упали из-за отсутствия формы, три прежних прошли.
После реализации и расширения проверки:

| Проверка | Результат |
|---|---|
| Новые HTTP/PostgreSQL регрессии на отдельной базе | 11 PASS |
| Существующие удержания, возвраты, зарплата/акты, изоляция | 14 PASS |
| Frontend: исправление, закрытие, зарплата, расчёты | 34 PASS, 5 наборов |
| Production build с 29 текущими feature flags | PASS |
| Полный `uvicorn backend.main:app` на тестовой схеме 0116 | PASS |
| Две реальные вкладки → API → PostgreSQL → связанный акт → reload | PASS |

Backend охватывает конкурирующие исправления и исправление/распределение, устаревшую
ревизию, компанию/роль/неподтверждённого сотрудника, точный user–staff, уже выплаченные
акты/зарплату, исторические удержания, запрет после возврата и откат при сбое аудита.
Frontend проверяет сохранение ввода при 409, отсутствие повторного запроса, поздний
ответ после закрытия/открытия, обновление истории и снятие подтверждения при правке.

В браузере получатель №100/стоимость 1000 исправлены на №102/800,25. Вторая вкладка
получила 409, сохранив 900. После обновления страницы акт №4 нового сотрудника
получил удержание 800,25 и остаток 9199,75; акты прежнего сотрудника не изменились.
В PostgreSQL проверены три события, одно распределение, отсутствие денежных выплат.
Тестовый браузер использует реальные компоненты, API и БД; это не проверка
финансовых записей через полный авторизованный production-кабинет.

Первая проверка полного запуска получила timeout при генерации OpenAPI (5 секунд),
хотя startup и health уже прошли. С лимитом 45 секунд проверка прошла; приложение
не изменялось. Сохраняется прежнее предупреждение OpenAPI о duplicate operation ID
в CRM и предупреждения сборщика о размере bundle/возрасте Browserslist — вне блока.

## Установка и откат

Миграция не нужна: схема остаётся `0116_tool_deductions`. Новых зависимостей нет.
Endpoint добавляется под уже установленным nginx-префиксом `/tool-deductions/`.
Старые формы распределения совместимы: сервер проверяет прежний expectedRevision
и отклоняет запрос после исправления. Принудительная перезагрузка вкладок не нужна.

1. Сверить текущий сервер с base пакета, чистоту tracked-файлов, отсутствие коллизий
   с untracked-файлами и 29 build flags. Подготовить протестированный backend/frontend.
2. Во время короткого обслуживания остановить писателей, сохранить текущие
   manifest/public-файлы, БД и uploads. Восстановить дамп в отдельную базу;
   сверить полные отпечатки 83 наборов бизнес-таблиц, включая три таблицы удержаний.
3. Запустить новый полный backend на восстановленной базе с запретом внешних
   соединений, подтвердить схему 0116 и неизменность данных. Миграции не запускать.
4. Согласованно переключить backend/frontend; проверить startup, схему, данные,
   хеши файлов через публичный HTTPS и маршруты; открыть бухгалтерию директором.
   Не создавать фиктивных финансовых операций в рабочей базе.
5. Только после отдельных backend/БД/frontend/browser проверок записать markers
   выпуска и очистить staging/резерв по `docs/deployment-retention.md`.

При неуспешном переключении оставить обслуживание и резерв. Вернуть исходный
commit и текущие файлы frontend из резерва, восстановить nginx/таймеры, проверить
startup и экран. Схема не меняется, поэтому откат кода не требует отката БД.
Дамп не накатывать поверх новых пользовательских записей. После очистки выпусков
предыдущий код берётся из Git и пересобирается с сохранёнными flags. История
исправлений остаётся в БД даже при откате UI; старая версия покажет исходное имя
операции, но сохранит актуальные суммы и проверку ревизии.

## Остаток и ограничения

Не входят: исправление объекта/складского оригинала, исторических уже удержанных
сумм, перенос фактически удержанных денег другому сотруднику, автоматическая
сверка старых выдач, v2-акты и частичная зарплата. После выплат требуется отдельная
финансовая процедура; эта форма намеренно отказывает. Заполненный сценарий на
production без подходящих реальных записей не подтверждается пустым GET.
Фактическая установка и проверка production фиксируются отдельным install-report.
