# Подтверждение начального остатка старого отдельного счёта

Локальный этап с интерфейсом в окне «Оплата и история», без выпуска. Не является переносом старых
строк материалов, поставок или НДС. Подходит только для утверждённых отдельных
старых счетов без накладной, исходной спецификации и регистрации в журнале.

## Поведение

Сначала финансовый пользователь запрашивает актуальные суммы и `reviewedHash`:

`GET /companies/{company_id}/supplier-opening-confirmations/preview/{invoice_id}`

Затем подтверждает увиденное с основанием:

`POST /companies/{company_id}/supplier-opening-confirmations`

```json
{
  "requestId": "UUID подтверждения",
  "invoiceId": 123,
  "reviewedHash": "64 символа из актуального ответа preview",
  "reason": "Начальная оплата сверена с историческими документами"
}
```

Оба запроса используют обычную авторизацию и заголовки выбранной компании.
Чтение проверяет финансовый read-доступ; запись — write-доступ к владельцу,
плательщику, объекту и пакету. Суммы/сотрудник/компания из тела не принимаются.

Подтверждение записывает неизменяемый начальный остаток и доказательство:
полный снимок исходного счёта, хеш сверки, сотрудника, основание и время.
Платёж, расход, складское движение и строки счёта не создаются.
Исходный `paid_amount` не изменяется и не сбрасывается.

Пример: счёт 200 ₽, прежняя оплата 50 ₽ → начальный остаток 50 ₽, долг 150 ₽.
После настоящей новой оплаты 20 ₽ оплачено 70 ₽, долг 130 ₽.
Регистрация не доказывает факт исторической банковской оплаты сама по себе:
основанием служит выполненная пользователем сверка первичных документов.

Любое изменение исходного счёта между просмотром и подтверждением требует
нового preview. Повтор того же UUID с тем же телом возвращает прежний результат,
в том числе после последующих платежей; текущие права проверяются каждый раз.
Другой UUID не регистрирует уже учтённый счёт повторно. UUID подтверждения имеет
собственное пространство имён и не является UUID денежной операции.

## Подготовка

- Миграция `0057_supplier_opening_confirmations` после 0056.
- `SUPPLIER_PAYMENTS_ENABLED=1` и новый флаг
  `SUPPLIER_OPENING_CONFIRMATIONS_ENABLED=1`; по умолчанию новый путь выключен.
- Рабочие ограничения журнала и доказательств обязательны. При недоступной
  схеме/отключённой защите запрос завершается без регистрации остатка.

Миграция ничего не переносит автоматически. Пустой downgrade поддержан,
при наличии подтверждений запрещён, чтобы не потерять историю.

## Ограничения и остаток

Связанные старые счёт–накладная остаются отдельным сценарием; отчёт сверки
уже умеет сравнивать их суммы, но этот writer их не принимает. Новые счета
с сохранёнными строками используют ранее реализованный путь.
Отсутствующая историческая оплата не трактуется как ноль.

Интерфейс просмотра/подтверждения и локальная браузерная проверка с API выполнены.
Реальные данные не переносились, производственный сервер не обновлялся.

## Проверки

- 11 PostgreSQL/HTTP-тестов нового пути: начальный остаток без денег, доплата,
  идемпотентность после доплаты, одновременные повторы, устаревший снимок,
  неверные права, выключенный флаг, отсутствующая оплата, старые связи,
  неизменяемость и отказ при отключённом ограничении.
- 25 существующих PostgreSQL/HTTP-тестов платёжных маршрутов.
- 12 тестов нормализации команд и HTTP-границы.
- Пустой upgrade/downgrade/upgrade выполнен в изолированной БД; downgrade
  после записи подтверждения отклоняется.

В старой изолированной фикстуре обработчик ошибок дополнительно пишет предупреждение
об отсутствующем `api_errors.owner_scope`. Проверки платёжных ответов проходят;
этот запуск не подтверждает работоспособность отдельной подсистемы журналирования ошибок.


## Интерфейс и восстановление после обрыва связи

Для отображения включаются сборочные флаги
`REACT_APP_SUPPLIER_PAYMENTS_ENABLED=true` и
`REACT_APP_SUPPLIER_OPENING_CONFIRMATIONS_ENABLED=true`.
В окне «Оплата и история» у незарегистрированного счёта доступна команда
«Сверить прежнюю оплату». Сервер проверяет допустимость конкретного счёта.
После просмотра сумм пользователь вводит основание и отмечает подтверждение
сверки. Начальная оплата также отображается в общей сводке зарегистрированного
документа и не исчезает после повторного открытия окна.

Запрос сохраняется до отправки отдельно по API, сотруднику, компании и счёту.
При обрыве связи/503 повтор использует тот же UUID и тело даже после перезагрузки.
До завершения попытки обычный платёж в этом окне блокируется. Web Locks
исключают одновременную отправку из вкладок, серверные ограничения остаются
окончательной защитой. При проблемах localStorage отправки нет.

Полученный 409 завершает локальную попытку и требует новой сверки. Это не
отмена ранее проведённой регистрации: поздний параллельный запрос может уже
зарегистрировать счёт, и свежая сверка покажет, что он учтён. Повторного
начального остатка не будет благодаря уникальности регистрации счёта.
Неопределённые ответы и неверный ответ другого счёта не очищают запрос.

Проверено 104 frontend-теста платёжного блока. Сборка с включёнными флагами.
В реальном Chromium использованы действующие React-компоненты и локальный API
с одноразовой PostgreSQL-базой: счёт 200/оплачено 50 → подтверждение с намеренной
потерей ответа после серверного commit → перезагрузка → повтор → доплата 20.
База подтвердила одну запись начального остатка 50, одну денежную операцию 20
и итог paid_amount=70; экран показал долг 130. При ширине 390 px ширина окна
и его содержимого составила 356 px, горизонтального переполнения нет.
Тестовые серверы, браузер и база после проверки закрыты.
