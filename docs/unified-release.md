# Единый пакет для рабочего сервера

Пакет содержит все коммиты после baseline `c30b5c7a6b641bc59860ea5eed6e743f67f1318d`
одной цепочкой, точный Git bundle, манифест SHA256, установщик и проверку БД.
Точный целевой SHA и список коммитов находятся в `release.json` внутри пакета.
Файлы `.env`, uploads, дампы и токены в пакет не входят. Ничего не публикуется в
GitHub и не устанавливается на сервер при сборке пакета.
Результаты проверок и ограничения среды находятся в `VERIFICATION.ru.md`.

Включены накопленные исправления объединения истории поставщика, отзыва доступа
менеджеров, выбора точного user/staff/contract, ручных бригад и восстановления
отправки после обрыва связи. Полный новый кабинет/команда подрядчика сюда не входят.

## Проверки и установка

Команды выполняет администратор на рабочем сервере из распакованного каталога.
Используйте Python окружения с зависимостями приложения. Нужны Git, npm, rsync,
клиенты pg_dump/pg_restore совместимой с сервером PostgreSQL версии и systemd.
Установщик не устанавливает Python зависимости и не меняет конфигурацию сервисов.

Сначала проверить SHA256 загруженного архива, затем распаковать его:

```sh
sha256sum -c stroyka-unified-release.tar.gz.sha256
tar -xzf stroyka-unified-release.tar.gz
```

Перейти в созданный каталог `stroyka-unified-<SHA>` и выполнить:

```sh
python3 install.py db-check --app-root /var/www/stroyka-app
python3 install.py check --app-root /var/www/stroyka-app --public-url https://stroyka26.pro
```

Первая команда проверяет только БД. Она открывает REPEATABLE READ READ ONLY
транзакцию, задаёт таймауты и в конце делает rollback. Проверяет фактическую
ревизию Alembic, необходимые колонки, включённый ALWAYS guard упаковок,
реестр/ограничения/guards ручных бригад, если 0101 уже установлена, и отсутствие
нарушений компании/объекта у новых manual origins. Вывод содержит агрегаты,
не реквизиты, документы или DSN. Старые unlinked договоры только считаются;
автопривязки, backfill или выдачи доступа нет.

Вторая команда также сверяет пакет, установленный SHA, чистоту tracked файлов,
ветку main, nginx, локальный и публичный health с точным SHA и manifest frontend.
Она не переключает Git, не применяет миграции и не меняет флаги.
Также читает синтетический DOCX настоящим изолированным обработчиком во временном
каталоге: ошибка sandbox останавливает выпуск до изменения кода или схемы.

Если обе команды успешны, использовать **полный current SHA из check**:

```sh
python3 install.py apply --app-root /var/www/stroyka-app \
  --public-url https://stroyka26.pro --expect-current ПОЛНЫЙ_CURRENT_SHA_ИЗ_CHECK
```

Это действие меняет рабочую установку. Установщик:

1. Берёт общий deployment lock и повторяет проверки. Не делает reset/clean/pull;
   неизвестный SHA, изменённые tracked файлы или другая ветка останавливают выпуск.
   Untracked файлы не удаляет; конфликт с ними останавливает обычный Git merge.
2. Сохраняет custom pg_dump и проверяет читаемость его TOC через pg_restore --list.
   Это проверка формата дампа, не доказательство успешного восстановления.
   Резерв frontend включает только текущие manifest assets и публичные файлы,
   без исторических static chunks. Копия всей Git-истории не создаётся.
3. Импортирует все коммиты из bundle, готовит сборку в отдельном staging и
   проверяет режимы через существующий resolver. Существующие флаги сохраняются;
   объединение истории, служебный доступ и пилоты не включаются автоматически.
4. Только после успешной сборки останавливает backend и активный agent worker,
   делает fast-forward на точный SHA и выполняет upgrade **до 0101**, не `stamp`.
   Есть короткое окно недоступности API. DB baseline должен быть ровно 0100
   либо 0101; более старый/неизвестный head требует отдельной проверки цепочки.
5. Заново проверяет схему, импорт backend, перезапускает сервисы, публикует
   frontend штатным скриптом, сверяет health/SHA, хеши локальных assets и
   опубликованный manifest. Схема устанавливается перед новым frontend.

Произвольные systemd EnvironmentFiles автоматически не разбираются: если они
настроены, check остановится, чтобы администратор сверил фактическое окружение.
DB_NAME/DB_USER/DB_HOST должны быть явно заданы в runtime или backend/.env;
подключение к development defaults запрещено. Секреты в отчёт не выводятся.

## Завершение и ошибки

После установки создаётся `installed.json` со статусом `installed_awaiting_browser`:
backend/database/frontend проверены, browser=false. Установщик **не создаёт**
`verified.json`/`deployed.json` и не объявляет выпуск завершённым по одному health.

Нужна фактическая приёмка установленного приложения: вход с обычными cookie/2FA,
выбранная организация, списки/просмотр поставщиков и подрядчиков, переключение
организаций и проверка отсутствия чужих документов. Мутационные отказные сценарии
синтетических договоров/оплат выполняются на отдельной тестовой БД, а не на
настоящих финансовых документах рабочего сервера.

Только после успешной backend/DB/frontend/browser приёмки записать markers с
точным head согласно [deployment-retention.md](deployment-retention.md) и выполнить
штатный finalize_release. Он оставит небольшую квитанцию, удалив подтверждённый
резерв и staging. До этого либо при любой ошибке резерв сохраняется. Отдельно
удалить загруженный установочный пакет после успешной приёмки; не накапливать копии.

При сбое установщик сохраняет `failed.json` и путь резерва. Если код ещё не менялся,
остановленные исходные процессы запускаются обратно. После смены кода или начала
миграции нет автоматического downgrade/reset/восстановления дампа. Сначала выяснить
состояние транзакции и прав; предпочтителен совместимый исправляющий релиз.
Безусловный откат старого backend может снова открыть доступ по имени или закрытые
ранее документы. Downgrade 0101 запрещён при существующих manual origins;
восстановление дампа может потерять записи после backup и требует отдельного окна.

## Повторная сборка пакета

Из чистой ветки с уже закоммиченными изменениями:

```sh
python3 scripts/unified_release.py pack \
  --base c30b5c7a6b641bc59860ea5eed6e743f67f1318d \
  --output /tmp/stroyka-unified-release.tar.gz
```

Пакет намеренно не заменяет существующий deploy.sh: тот выполняет reset/pull и
не фиксирует единый reviewed SHA. Для данного накопленного выпуска используется
только приложенный install.py. Если установленный сервер ушёл на другой SHA,
сначала объединить и проверить его изменения; принудительной перезаписи нет.
