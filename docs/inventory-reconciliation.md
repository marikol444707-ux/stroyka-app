# Инвентаризация и расхождения

## Задача и порядок

Следующий раздел склада после инструмента — инвентаризация. Пользователь поручил продолжить блоки по порядку. Сверка должна сохранять состояние учёта на момент начала, фактический пересчёт и решение по расхождениям. Старый экран отправляет новую строку при каждом blur, доверяет клиентскому остатку/разнице и не загружает сохранённый факт при открытии.

Рабочее предположение до ответа пользователя: кладовщик/прораб проводит пересчёт, директор утверждает корректировку с причиной. Недостача сама по себе не создаёт денежного штрафа. Инструмент по-прежнему меняет состояние через уже выпущенные операции ответственности.

## Приёмочные сценарии

1. Одна выбранная компания; основной склад или точный ID объекта. Сервер фиксирует полный снимок материалов и инструмента. Для неоднозначных названий объектов сверка блокируется; чужие компании и не назначенные прорабу объекты недоступны.
2. «Черновик» → «На проверке» → «Утверждена»; возврат на пересчёт и отмена с причиной. Каждый переход сохраняет неизменяемое событие, автора и дату. Утверждённая ведомость не редактируется и не удаляется.
3. Факт изначально пустой, ноль вводится явно. Повторное сохранение обновляет конкретную строку по ID без дублей; учёт, единица, название, получатель и разница вычисляются сервером. Для расхождения обязательна причина. Сохраняются все позиции снимка, в том числе нулевые остатки.
4. При утверждении сервер повторно проверяет остатки и версии инструмента. Изменившаяся база требует новой сверки; старая остаётся в истории. Корректировка материалов и её история атомарны, остаток не отрицателен. Повтор исходного UUID не проводит разницу дважды.
5. Недостача основного склада требует явного распределения по доступным партиям и/или части без привязки к партии. Излишек учитывается отдельной корректировкой без выдуманной накладной. Исходные приходы, цены, оплаты и договоры не переписываются. На объекте корректируется точная строка складского остатка; материал на руках и в пути не включается в складское наличие.
6. По инструменту сверяется наличие/состояние; утрата или повреждение отражаются в ведомости и направляют к «Операциям и ответственности». Сверка не подменяет выдачу, возврат, назначение ответственного и решение о денежном возмещении.
7. Сохранённая ведомость открывается с теми же учётными и фактическими данными. Печатный акт отражает снимок, расхождения, решение, автора, дату и статус; все тексты экранируются. Интерфейс помещается на телефоне, сетевой повтор сохраняет UUID и содержимое, смена компании/пользователя очищает частные данные.

## Реализация

React/FastAPI/PostgreSQL без новых зависимостей. Модуль backend/features/inventory_reconciliation и src/features/inventory-reconciliation, существующая вкладка «Инвентаризация». Additive migration 0030 после инструмента; старые inventory/inventory_items остаются историей без автоматического переноса остатков. Новые команды за INVENTORY_RECONCILIATION_ENABLED / REACT_APP_INVENTORY_RECONCILIATION_ENABLED; защита уже проведённых сверок сохраняется при отключении.

Сначала failing tests старого поведения и новых команд, затем схема/сервер, интерфейс, PostgreSQL и браузер. Использовать существующие lock_actor, общий stock lock и work_material_operations для повторов. Денежные поля и количество — Decimal, ID строго числовые, клиентские имена/роли не являются доказательством доступа.

## Границы

Счета и оплаты поставщикам остаются другому чату. Данные production сначала проверяются чтением; хозяйственные операции при тестировании выполняются только в изолированной БД. Перед выпуском — репетиция миграции, резервная копия и проверка неизменности прежних данных. Не приписывать старые расхождения людям, не удалять старые ведомости и не включать недостачу в штраф автоматически.
