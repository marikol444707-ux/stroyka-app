Новый API оплаты, полный адаптер документов и интерфейс пока не подключены.
Последующее уточнение: guard сторно бригад и bound-contract/receipt evidence helpers

Позднейшее продолжение: четыре прямых document PUT/DELETE защищены в

## Что изменено

1. `supplier_payments/access.py`: доверенный вызов проверяет свежую запись
   пользователя, действующие финансовые роли компании-владельца и отдельного
   плательщика. Повторно используются существующие правила company context,
   объекта и пакета работ. Роли не расширены. User/company/membership rows
   заблокированы до завершения транзакции; autocommit запрещён. Пароли и секреты
   не выбираются. Legacy company fallback не заменяет действующее членство.
2. Старый `DELETE /project-payments/{id}` после проверки прав отклоняет сторно
   проводки, принадлежащей новому реестру. Иначе отрицательный расход оставлял бы
   долг документов неизменным. Принадлежность определяется только явной связью.
3. `GET /project-payments` сохраняет два самостоятельных ledger-платежа даже при
   одинаковых сумме, дате, основании и авторе. Legacy-дедупликация обычных расходов
   сохранена. До миграции 0017 отсутствующая таблица не используется в запросах.

Проверка прав — **часть**, а не замена полного адаптера: caller обязан получить
проект, компанию и плательщика из проверенных документов, проверить их отношения,
сессию/2FA/CSRF и условия новой оплаты. HTTP-тело не является таким источником.
Helper пока не импортируется в рабочие маршруты и не подключён к engine.

## Проверки

31 проверка текущего этапа: 12 unit-тестов project payment routes/service,
15 проверок реальных членств и блокировок на PostgreSQL, 3 authenticated HTTP/PG
проверки с ledger, 1 authenticated HTTP/PG проверка без миграции 0017.
Для PG-наборов использовались отдельные новые синтетические базы, Unix-сокет,
без доступа к рабочей базе и внешней сети.

Воспроизведены RED → GREEN: обход сторно, схлопывание равных платежей;
авторизационный helper разработан с предварительными падающими тестами.
Проверены также обычное legacy-сторно, повтор, GET-дедупликация реально
существующих legacy-дубликатов, чужая компания, отключённый пользователь/компания,
отозванное членство, отдельный плательщик и конкурентный отзыв полномочий.
Независимое ревью не выявило блокеров в этом ограниченном наборе изменений.
Frontend не менялся; браузерная готовность нового реестра не заявляется.

## Конкретные оставшиеся обработчики

До runtime-включения нужны общая сериализация с engine **до row locks**,
повторное чтение регистрации и запрет обхода для обеих сторон связи, включая
документы с нулевым балансом после полного сторно.

| Обработчик | Что ещё защитить |
|---|---|
| `main.update_supplier_invoice` | paid amount/status, сумму, пакет и warehouse link |
| `main.update_warehouse_invoice_accounting` | второй writer оплаты и зеркальные балансы |
| `main.delete_supplier_invoice` | аннулирование и снятие связи |
| `main.delete_warehouse_invoice` | guard до закрытия партий, складских и журнальных изменений |
| `main.dedupe_supplier_accounting_documents` | canonical/duplicate документы и перенос ссылок |
| `main._sync_supplier_invoice_from_warehouse` | duplicate/reuse UPDATE существующего счёта |
| `main._ensure_supply_delivery_invoice` | добавление/замена накладной при приёмке |
| `main.create_supplier_invoice`, `supplier_offers.routes.create_invoice_from_offer` | UPDATE в повторных create-ветках |
| `accounting_exception_checks.link_repair_runtime._apply_plan` | ремонт обеих сторон связей |
| `brigade_access.payment_routes.delete_brigade_payment` | ошибочная перекрёстная связь с ledger-проводкой |

Дополнительные входы: `backfill_supplier_documents`, messenger/own-expenses через
`_create_warehouse_invoice_record`, ownership/project writers и `init_db`.
Особенно важно: `_create_warehouse_invoice_record` может закоммитить приёмку
**до** отдельной бухгалтерской синхронизации, превратив её ошибку в warning.
Guard только внутри последней синхронизации не откатит уже сохранённую приёмку.

Оплату бригады или промежуточного акта нельзя глобально запретить и нельзя
объявить оплатой поставщика по тексту примечания. Обычный POST project payment
пока не превращён в новый supplier writer.

Следующий интеграционный блок: канонический document/payer resolver и условия
договора/приёмки, согласованная защита перечисленных writers, затем новый HTTP
маршрут и интерфейс. Сценарий «аванс по счёту → появление накладной» требует
явного безопасного присоединения документа; текущий запрет молчаливой смены группы
нельзя просто отключить ради прохождения приёмки.
