# ADR 0008: диагностика участников отдельно от выдачи доступа

Дата: 2026-10-12. Статус: первый локальный этап, выпуск не разрешён.
Baseline: origin/main d788bce9ef2d0845e9c6acfeff93c4dbf56afeed.

## Модель и границы

Сохраняем users (человек), platform_accounts (независимый клиент), companies
(организация), user_company_roles (внутреннее членство), suppliers (внешняя
юридическая идентичность), company_supplier_links (отношение с покупателем),
supplier_team_members/customer assignments (команда и область менеджера),
brigade_contracts/items (договор/назначения). Не вводим универсальную таблицу
участников или универсальную роль полного доступа.

Общий контур первого этапа — служебное обращение. participant_type имеет
закрытый набор supplier/contractor/employee/brigade; сейчас только supplier
может получить доказанный сервером контекст. Остальные подключения будут
реализованы через собственные политики, без фиктивных строк в реестре.

Диагностика сохраняет выбранную проверенную организацию/аккаунт, пользователя,
эффективную роль, точный supplier ID, код причины, версию связи/приложения,
фиксированные экран/действие и известный тип источника создания. Состояние связи
снимается после rollback при сохранении диагностики, а не выдаётся за снимок
внутри откатившейся операции. Свободный source_detail не копируется. UUID диагностики
является correlation ID служебного процесса, а не токеном доступа. Контекст
запроса/ответа, cookies, пароли, пригласительный код и секретные ссылки не хранятся.
Неизвестные исторические автор/дата создания не выдумываются.

Отказ приглашения сначала откатывается. Затем в другом соединении сохраняется
диагностика с повторной авторизацией. Недоступность служебного хранилища не
заменяет первоначальную причину отказа. Обращение создаётся только отдельным
нажатием, не повторяет invite и не меняет бизнес-данные. Диагностика действует
час; повтор одной причины в течение пяти минут использует тот же UUID; максимум
20 диагностик пользователя в час. Открытое обращение с тем же владельцем,
участником и причиной переиспользуется; одновременно отправленные команды
сериализуются блокировкой выбранной компании. Лимит одного пользователя между
разными компаниями защищён advisory-блокировкой. Повторная авторизация обязательна
даже для возврата ранее сохранённого результата.

## Права первого этапа

| Кто | Действие | Серверная граница |
|---|---|---|
| Директор/заместитель | Создать приглашение и обращение по отказу | Активное членство/эффективная роль, одна выбранная company и её platform account |
| Автор обращения с сохранённым доступом к каталогу | Прочитать свои обращения и результат | reporter_id + проверенная company/account |
| system_owner/platform_admin | Реестр поставщиков, обращения, история, статусы | Явная company из существующего реестра; только метаданные выбранных отношений |
| platform_support/billing_admin | Новые административные API | Запрет; запись support session сама полномочий не даёт |
| Поставщик/менеджер/подрядчик | Новые API обращений покупателя | Нет членства в покупателе — нет доступа; собственный вход поддержки ещё не реализован |

История статусов неизменяема; FK фиксирует точный диагностический родитель,
компанию, аккаунт, автора, тип/ID участника и причину. База запрещает менять
происхождение обращения/диагностики и удалять историю. Закрытие допускается
после статуса resolved, текста результата и явной отметки проверки исходного
сценария; повторное открытие сохраняет события. Изменение требует expectedVersion.
Ответственный — администратор, выполнивший последнее действие. Отдельные
внутренние заметки/переписка/вложения/уведомления в первом этапе не добавляются;
поле результата явно публично автору обращения.

## Интерфейс и включение

Используем существующий экран Аккаунты/компании: у каждой организации кнопка
«Участники и доступ», внутри — «Поставщики» и «Проблемы и обращения».
Поиск/пагинация выполняются сервером. Панель key=company.id, отмена загрузок и
проверка поколения команды исключают запоздавшие результаты старой компании.
Ошибка, пустой каталог и отсутствие результатов поиска различаются.
В приглашении точная причина показана рядом с кнопкой «Сообщить о проблеме».
В Снабжение → Поставщики есть «Мои обращения» для чтения сохранённого результата.
Договорные редакторы остаются в Бухгалтерии, новые копии оригиналов не создаются.

Миграция 0094 создаёт пустые служебные таблицы/индексы/ограничения, без backfill.
PARTICIPANT_SUPPORT_ENABLED=0 по умолчанию; UI включается только сборкой с
REACT_APP_PARTICIPANT_SUPPORT_ENABLED=1. Без миграции/флага сервер возвращает 503.
Откат кода/выключение флага сохраняет историю. Downgrade разрешён только для
пустых служебных таблиц; универсального отката с данными нет.

## Выявленные риски и альтернативы

Старый /suppliers/{id}/link-user очищает suppliers.user_id у всех других карточек
человека. Нельзя использовать его для многоклиентского подключения: это может
отозвать доступ к объединённой истории. Новый экран не вызывает его.
link-duplicate сохраняет aliases; aliases не дают права. Обычный company merge
из PR #360 сохраняется; два действующих кабинета требуют отдельной проверки
принадлежности, не обычного merge.

platform_support_sessions есть как реестр/аудит; поиск runtime-потребителей
обнаружил административный и клиентский просмотр, но не enforcement в обычной
company_context. Обход этого пробела через имперсонацию отклонён. Новые маршруты
не принимают support-session ID, platform_support запрещён даже с такой записью.
Перед выдачей поддержки бизнес-доступа нужен отдельный проверяемый механизм
scope/company/expiry/revocation на каждом маршруте, включая файлы/экспорт/jobs.

brigade_access.resolve_brigade_contractor_user различает совпадения users/staff
частично, но содержит восстановление по имени/email и неоднозначный числовой ID.
Новая модель подрядчика должна использовать типизированные ссылки и явное
членство команды подрядчика; существующий fallback не расширяем.

Автоматический перенос по названию/email, создание нового кабинета при конфликте,
прямые бизнес-правки поддержки и передача всех архивов покупателя отклонены.
Реальный «Сатурн» не читался и не изменялся. Неизвестны точные IDs, ИНН, владелец
кабинета, отношения и происхождение карточки. Тесты воспроизводят обе причины
на полностью синтетических данных, не утверждают диагноз конкретной карточки.
