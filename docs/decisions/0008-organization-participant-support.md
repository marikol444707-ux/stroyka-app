# ADR 0008: диагностика участников отдельно от выдачи доступа

Дата: 2026-10-12. Статус: первый локальный этап, выпуск не разрешён.
Baseline: origin/main d788bce9ef2d0845e9c6acfeff93c4dbf56afeed.

## Модель и границы

Сохраняем users (человек), platform_accounts (независимый клиент), companies
(организация), user_company_roles (внутреннее членство), suppliers (внешняя
юридическая идентичность), company_supplier_links (отношение с покупателем),
supplier_team_members/customer assignments (команда и область менеджера),
brigade_contracts/items (договор/назначения). Не вводим универсальную таблицу
участников или универсальную роль полного доступа.

Общий контур первого этапа — служебное обращение. participant_type имеет
закрытый набор supplier/contractor/employee/brigade; сейчас только supplier
может получить доказанный сервером контекст. Остальные подключения будут
реализованы через собственные политики, без фиктивных строк в реестре.

Диагностика сохраняет выбранную проверенную организацию/аккаунт, пользователя,
эффективную роль, точный supplier ID, код причины, версию связи/приложения,
фиксированные экран/действие и известный тип источника создания. Состояние связи
снимается после rollback при сохранении диагностики, а не выдаётся за снимок
внутри откатившейся операции. Свободный source_detail не копируется. UUID диагностики
является correlation ID служебного процесса, а не токеном доступа. Контекст
запроса/ответа, cookies, пароли, пригласительный код и секретные ссылки не хранятся.
Неизвестные исторические автор/дата создания не выдумываются.

Отказ приглашения сначала откатывается. Затем в другом соединении сохраняется
диагностика с повторной авторизацией. Недоступность служебного хранилища не
заменяет первоначальную причину отказа. Обращение создаётся только отдельным
нажатием, не повторяет invite и не меняет бизнес-данные. Диагностика действует
час; повтор одной причины в течение пяти минут использует тот же UUID; максимум
20 диагностик пользователя в час. Открытое обращение с тем же владельцем,
участником и причиной переиспользуется; одновременно отправленные команды
сериализуются блокировкой выбранной компании. Лимит одного пользователя между
разными компаниями защищён advisory-блокировкой. Повторная авторизация обязательна
даже для возврата ранее сохранённого результата.

## Права первого этапа

| Кто | Действие | Серверная граница |
|---|---|---|
| Директор/заместитель | Создать приглашение и обращение по отказу | Активное членство/эффективная роль, одна выбранная company и её platform account |
| Автор обращения с сохранённым доступом к каталогу | Прочитать свои обращения и результат | reporter_id + проверенная company/account |
| system_owner/platform_admin | Реестр поставщиков, обращения, история, статусы | Явная company из существующего реестра; только метаданные выбранных отношений |
| platform_support/billing_admin | Новые административные API | Запрет; запись support session сама полномочий не даёт |
| Поставщик/менеджер/подрядчик | Новые API обращений покупателя | Нет членства в покупателе — нет доступа; собственный вход поддержки ещё не реализован |

История статусов неизменяема; FK фиксирует точный диагностический родитель,
компанию, аккаунт, автора, тип/ID участника и причину. База запрещает менять
происхождение обращения/диагностики и удалять историю. Закрытие допускается
после статуса resolved, текста результата и явной отметки проверки исходного
сценария; повторное открытие сохраняет события. Изменение требует expectedVersion.
Ответственный — администратор, выполнивший последнее действие. Отдельные
внутренние заметки/переписка/вложения/уведомления в первом этапе не добавляются;
поле результата явно публично автору обращения.

## Интерфейс и включение

Используем существующий экран Аккаунты/компании: у каждой организации кнопка
«Участники и доступ», внутри — «Поставщики» и «Проблемы и обращения».
Поиск/пагинация выполняются сервером. Панель key=company.id, отмена загрузок и
проверка поколения команды исключают запоздавшие результаты старой компании.
Ошибка, пустой каталог и отсутствие результатов поиска различаются.
В приглашении точная причина показана рядом с кнопкой «Сообщить о проблеме».
В Снабжение → Поставщики есть «Мои обращения» для чтения сохранённого результата.
Договорные редакторы остаются в Бухгалтерии, новые копии оригиналов не создаются.

Миграция 0094 создаёт пустые служебные таблицы/индексы/ограничения, без backfill.
PARTICIPANT_SUPPORT_ENABLED=0 по умолчанию; UI включается только сборкой с
REACT_APP_PARTICIPANT_SUPPORT_ENABLED=1. Без миграции/флага сервер возвращает 503.
Откат кода/выключение флага сохраняет историю. Downgrade разрешён только для
пустых служебных таблиц; универсального отката с данными нет.

## Выявленные риски и альтернативы

Старый /suppliers/{id}/link-user очищает suppliers.user_id у всех других карточек
человека. Нельзя использовать его для многоклиентского подключения: это может
отозвать доступ к объединённой истории. Новый экран не вызывает его.
link-duplicate сохраняет aliases; aliases не дают права. Обычный company merge
из PR #360 сохраняется; два действующих кабинета требуют отдельной проверки
принадлежности, не обычного merge.

platform_support_sessions есть как реестр/аудит; поиск runtime-потребителей
обнаружил административный и клиентский просмотр, но не enforcement в обычной
company_context. Обход этого пробела через имперсонацию отклонён. Новые маршруты
не принимают support-session ID, platform_support запрещён даже с такой записью.
Перед выдачей поддержки бизнес-доступа нужен отдельный проверяемый механизм
scope/company/expiry/revocation на каждом маршруте, включая файлы/экспорт/jobs.

brigade_access.resolve_brigade_contractor_user различает совпадения users/staff
частично, но содержит восстановление по имени/email и неоднозначный числовой ID.
Новая модель подрядчика должна использовать типизированные ссылки и явное
членство команды подрядчика; существующий fallback не расширяем.

Автоматический перенос по названию/email, создание нового кабинета при конфликте,
прямые бизнес-правки поддержки и передача всех архивов покупателя отклонены.
Реальный «Сатурн» не читался и не изменялся. Неизвестны точные IDs, ИНН, владелец
кабинета, отношения и происхождение карточки. Тесты воспроизводят обе причины
на полностью синтетических данных, не утверждают диагноз конкретной карточки.

Полный последующий план и критерии: tasks/participant-access-plan.md.

## 13.10.2026: списки членств и приглашений (этап 2а)

Внутри выбранной организации добавлены два чтения: `participant-memberships`
и `participant-invitations`. Авторизация, проверка компании и feature flag
переиспользуют `admin_transaction`; platform_support по-прежнему запрещён.
Это представления существующих связей, не команды выдачи/отзыва прав.

Членство определяется строкой user_company_roles с точным company_id.
NULL platform_account_id допустим для существующего company_users writer:
аккаунт определяется подтверждённой компанией. Противоречащий ненулевой аккаунт
исключён. users.company_id/глобальная роль не создают членство в этом списке.
membershipId и userId — разные поля; staff.id не подставляется вместо users.id.
Показывается сохранённая роль, а не расчёт всех effective permissions.
Несколько включённых ролей одной компании отмечаются для проверки; максимальная
привилегия не выбирается. Отключённые членства остаются видимыми.

Приглашение сотрудника требует точной компании и разрешённой COMPANY_ROLES;
приглашение поставщика — supplier_invite_companies с согласованной компанией/
аккаунтом и назначением. supplier_team_invites исключены даже при повреждённом
role/company в invite_codes. В ответе только inviteId, purpose, role, status,
createdAt, expiresAt: без code/URL, контактов, имён объектов и чужой команды.
Статус pending означает только неистёкший срок, не гарантию возможности принятия:
проверка инициатора/назначений/лимитов принадлежит регистрации. Удаление старого
invite физическое; список не выдумывает отсутствующую историю отзыва.

Поиск и фильтры выполняются на сервере, страницы 25 (API максимум 100).
Смена вкладки сбрасывает условия и отменяет предыдущий запрос; компания меняется
через существующий keyed panel. На телефоне четыре вкладки размещены в две колонки.
Новый срез не меняет схему БД, бизнес-права или issued document snapshots.

## Дополнение 13.10.2026: проверка кабинета перед восстановлением связи

Read-only connection-preview начинается с подтверждённого company/account
catalog link и читает один REPEATABLE READ snapshot. Уже подключённая карточка
не получает дополнительного обязательного подтверждения. Точные валидные ИНН/
ОГРН могут найти минимальный юридический профиль потенциального кабинета, но не
доказывают его владельца. Несколько кабинетов или противоречивые ключи — спор;
имя, контакты и aliases не служат доказательством или fallback.

Buyer-owned history counts отделены от текущей invoice/offer disclosure policy.
NULL currentVisibility потенциальной связи означает отсутствие оценки будущих
прав; не ноль документов и не готовность выдачи архива. Файлы и договоры имеют
отдельные политики. canApply всегда false, write endpoint не добавляется.
Следующая операция требует самостоятельного proof/версий/повторной авторизации/
точных получателей и аудита. Глобальная очистка user_id старого link-user не
используется; бизнес-снимки, платежи и компании документов не изменяются.

## Срез 2в: отдельное согласие на связь с покупателем, 13.10.2026

Новая команда создаёт owner-addressed request, а не регистрационную ссылку и не
команду смены владельца. Источник — карточка каталога точной company/account;
target — один кабинет с совпадающими непротиворечивыми юридическими ключами.
Инициатор system_owner/platform_admin; согласие может дать только текущий активный
прямой владелец target.user_id. Team leader/manager не получает это полномочие
из самого факта делегирования. Существующим связям повторное согласие не нужно.

Consent добавляет только company_supplier_link на target, без изменения source,
user_id, членств покупателя, финансов/stock и snapshots. Source из накладной не
передаётся поставщику. Проверка/объединение её адресованной истории — следующий
отдельный срез с consequences preview; consent на нового покупателя не является
consent на исторический доступ. Shared/unknown-owner source остаётся неизменным.

Запрос живёт два дня; хранит точных source/target/owner/issuer, source version,
legal evidence, epochs обоих пользователей и epoch смены владельца target.
Ключи/контакты не позволяют принять запрос другим пользователем. Возврат прежних
прав или владельца после смены не оживляет старое согласие. Отказ/отзыв финальны;
expiry проверяется по wall clock после ожидания блокировок и перед самой вставкой
связи. UUID creation replay сверяет payload и текущего инициатора; решение
повторяется только после fresh authorization. Аудит и связь атомарны.

Новая таблица имеет immutable company/account/source-link ownership и evidence;
downgrade не удаляет заполненную историю. Служебный ownership epoch не назначает
владельцев существующим карточкам. Новый backend/frontend флаг default-off.
Универсальной имперсонации, support session полномочий и новых каналов уведомления
этот срез не добавляет. Полная приёмка: tasks/participant-access-stage2c-review.md.

## Срез 2г1: точная история и закрытие глобальных обходов, 13.10.2026

История source-card читается только для точной пары source/target с подтверждённой
связью кабинета в выбранной company/account. Транзакции snapshot переведены в
READ ONLY; блокировка company FOR SHARE остаётся только для обычных команд.
Существующие invoice/offer policies определяют текущий доступ, но не будущие права.
Накладные/версии договоров/файлы требуют отдельной parent/file проверки. Основные
файлы включают лишь зарегистрированные первичные ссылки; это не доказательство
целостности всех вложений или доступности физического файла.

Глобальные link-user/link-duplicate возвращают 409 после штатной авторизации,
без чтения/записи БД; их формы удалены. Company merge сохраняется без изменения.
Новый просмотр default-off, canApply=false. Следующий срез должен связать merge
с точным подтверждением исторического раскрытия, версиями/epochs и аудитом.
Результаты и границы: tasks/participant-access-stage2d1-review.md.

## Срез 2г2: подтверждаемое раскрытие истории, 13.10.2026

Объединение исходной карточки без кабинета с уже подключённым основным кабинетом
добавлено как отдельная административная команда выбранной организации. Источник
должен принадлежать только этой company/account; чужие документы, неизвестная
принадлежность, чужая selected_suppliers/recipient-group адресация и команда
источника останавливают операцию. Поиск основных кабинетов исключает merged source,
чтобы после объединения не диагностировать новый ложный дубль у другого покупателя.

Перед изменением прав сохраняется неизменяемый план с issuer/owner epochs,
target ownership epoch, точными ID и digest проверенных данных. Предполагаемое
владение подставляется только в SELECT-only CTE: runtime invoice/offer/delivery/
claim/team/file/contract policies остаются единственным источником решения.
Старые претензии без company_id проверяются через каноническую полную цепочку
claim/delivery/offer/request. Namespace хранилища проверяет общий file guard;
физическое наличие оригинала и доставка content не проверяются.

Администратор явно подтверждает принадлежность сторон и документов и записывает
основание. Это ручное подтверждение с точными юридическими ключами, не автоматическая
проверка реестра или разрешение ownership dispute. Company merge переиспользует
существующие записи: snapshots, документные supplier_id, банк, суммы, платежи и
назначения менеджеров не переписываются. Менеджеры не наследуют права прямого
владельца на исходную карточку.

TTL — 15 минут; перед apply проверяются полномочия, epochs, company/account,
пара и полный план заново, затем wall clock. Данные должны совпадать полностью.
Изменение и аудит атомарны. Повтор проверяет актуальные полномочия и возвращает
тот же result; смена source owner и возврат прежнего owner не оживляет replay.
Заполненный реестр планов нельзя удалить downgrade. Список UI обновляется после
подтверждения и ведёт от сохранённой объединённой карточки к основной.

Реализация ограничена: 2000 строк на реестр, 100 зарегистрированных файлов всей
компании и bounded N+1 file-policy проверки. Apply использует глобальные SHARE
table locks для защиты от новых предикатных ссылок; lock timeout 3s и statement
timeout 15s. Нагрузочная приёмка и общие company-scoped writer locks обязательны
до production enablement. Новый backend/frontend флаг default-off. Старая merge
команда для target с кабинетом возвращает 409 независимо от нового флага;
merge без кабинета сохранён. Полная локальная приёмка:
[participant-access-stage2d2-review.md](../../tasks/participant-access-stage2d2-review.md).


## Срез 2д1: ограниченная диагностика поддержки (13.10.2026)

Legacy `platform_support_sessions` не конвертируются в полномочия. Новый UUID
привязан составным FK к точному company/account/ticket, к `platform_support`
assignee, к действующему issuer-admin и epochs обоих. Единственное действие —
`diagnostic.read`; обычные бизнес-API не принимают это разрешение. Включённый
новый режим роли поддержки ограничивает общую dependency аутентификации до
точных GET рабочего места/диагностики и выводит отдельный frontend кабинет.

Проверка происходит в PostgreSQL под company/user/ticket/grant row locks.
Expiry проверяется по clock_timestamp после блокировок; отзыв сериализуется
с чтением, успешные использования входят в append-only audit. Повторная выдача
отзывает старый UUID. Изменение ticket version или role/active epoch требует
новой выдачи. Никаких постоянных членств, имперсонации и бизнес-writes.

Миграция 0097, новые backend/frontend флаги default-off. Это законченная
диагностическая команда, а не завершение всего support-контура: остаются
security-denial audit, обходные auth/file/export/WS/job поверхности и полный App
E2E перед включением. Подробности и проверки:
[participant-access-stage2e1-review.md](../../tasks/participant-access-stage2e1-review.md).


## Срез 2д2: отдельный отказной аудит

0098 сохраняет отказы после rollback бизнес-чтения. Scope покупателя выводится
только из grant этого assignee; неизвестные/чужие UUID и прямые бизнес-пробы
остаются в области платформы. URL/query/body/credentials не сохраняются.
Append-only guards включают TRUNCATE; сбой аудита не открывает данные.
Новый режим нельзя запустить с публичным upload mount или public S3 ACL.
Это проверка конфигурации, а не доказательство закрытия bucket policy/CDN.

Локально проверены 556 прямых бизнес-операций; отдельные auth/public/integration
маршруты зафиксированы явным CI-инвентарём. Полный App login и общий bootstrap
поддержки остаются следующим блоком. Никакого production enable/apply.
[Приёмка](../../tasks/participant-access-stage2e2-review.md).

## Срез 2д3: отдельный bootstrap и жизненный цикл входа

При включённом новом UI режиме platform_support исключён из общей загрузки
компании, бизнес-разделов, presence/push и bootstrap-кэша. Predicate выбирает
экран; server capability остаётся единственным источником полномочий.
Company responses отменяются и проверяются по scope/generation; смена
сотрудника перемонтирует рабочее место. Login/2FA/logout сбрасывают CSRF кэш,
старая ожидающая его mutation не отправляется под следующим входом.
Настоящие cookie/TOTP/reload/logout проверяются в отдельном PostgreSQL и
полном App в Chromium. Production не выполнен; следующий шаг — корректирующая
связь с точным preview, не универсальный undo.
[Приёмка и точные границы](../../tasks/participant-access-stage2e3-review.md).

## Срез 2е1: проверка последствий ошибочного подключения

Просмотр привязан к точным company/account/source/request; обе карточки берутся
из выполненного запроса, а не из произвольной пары браузера. Свежая роль
администратора проверяется внутри READ ONLY / REPEATABLE READ snapshot.
Показываем документы обеих карточек только этой компании, по 5 записей;
счётчики основных файлов/версий договоров не удваивают общие originals.
Не возвращаем суммы/банки/snapshots/URL или документы других покупателей.

Creation time после подключения — временной признак, не доказательство причины
и не полный журнал изменений документа. Неизвестная дата/реестр/принадлежность
не заменяется нулём; смена владельца/epochs и состоявшийся merge требуют
самостоятельного разбора. Текущий invoice/offer access проверяем обычными
server policies; files/contracts/receipts требуют отдельной проверки.

Каталожная связь не является источником адресного доступа к документам.
Поэтому её отключение нельзя показывать как полный отзыв прав. Новый просмотр
default-off, canApply=false; это не сохранённый confirm plan и не mutation.
Следующий срез должен охватить адресатов, изменения после исходной операции,
повторную авторизацию и атомарный аудит; не стирать прежнюю историю/просмотры.
[Приёмка](../../tasks/participant-access-stage2f1-review.md).

## Срез 2е2: отключение только неиспользованной ошибочной связи

15.10.2026. Неактивная каталожная связь не закрывает доступ к адресным документам.
Поэтому автоматическая команда допускает только точное accepted подключение,
по которому кабинет ещё не получил документы, заявки, групповых адресатов или
назначений выбранной компании. Учитываются typed supplier FK, scalar/array
ссылки, договорные snapshots и файлы; неизвестный владелец/реестр, смена
владельца, drift юридических ключей и состоявшийся merge блокируют операцию.
История других компаний и других явно определённых карточек того же владельца
не становится основанием для изменения их отношений.

Команда меняет только status/version созданной связи. Исходная непривязанная
карточка, документы/платежи/party snapshots, кабинет/команда, прочие связи и
первоначальное accepted согласие неизменны. План живёт 15 минут, сохраняет
только digest/счётчики/контекст без сырых архивных данных, привязан к actor/epoch.
Подтверждение повторно проверяет полномочия, exact company/account, source/target,
owner epochs, доказательство и архив; результат и audit записываются атомарно.
Потеря ответа допускает повтор того же плана/основания при актуальных полномочиях.
Применённый план и первоначальное согласие нельзя переписывать или удалять.

Новая миграция 0099 создаёт только пустую мета-таблицу. Backend/UI флаги отключены.
Глобальные SHARE locks защищают predicate от конкурентных вставок, но задерживают
писателей других компаний. Перед включением необходим согласованный company
writer protocol и нагрузочная приёмка; пределы 2000 строк/реестр и 100 файлов
компании — явный отказ, а не доказательство отсутствия данных.
Legacy timestamp without timezone сравнивается с учётом TimeZone БД; изменение
её исторической настройки требует отдельной проверки, не массового пересчёта.
Исправление уже использованной связи/исторического merge — самостоятельный блок.
[Приёмка](../../tasks/participant-access-stage2f2-review.md).

## Срез 2е3: отдельная команда для отправленных заявок без ответа

15.10.2026. Использование связи не означает, что её можно отключить одним status.
Для ограниченного случая только отправленных RFQ добавлен отдельный
`rfq-correction-plans` путь с собственными default-off backend/UI флагами.
Старый `correction-plans` по-прежнему отказывает при любой адресной работе.
Тип плана проверяется при proposal/replay/confirm; смешивать пути запрещено.
Переиспользованы immutable correction plans/TTL/epochs/версии/аудит, без миграции.

Разрешены только явные target→target адресаты текущего владельца и пустые
ожидающие ответы. Общая группа/другая доступная карточка того же кабинета,
legacy array без recipient, ответ/цены/файл/снимок сторон/история ответа,
договор/поставка/счёт/назначение и неопределённая принадлежность блокируют команду.
Дочерние ссылки на КП проверяются и в других компаниях: ошибочная company_id
не превращает связанный финансовый документ в независимую чужую историю.
Дополнительно обнаруживаются typed FK к supplier_offers с другим именем колонки.

Точный план до подтверждения показывает IDs заявок/получателей/ожидаемых ответов
и число queued уведомлений. Подтверждение скрывает адресатов, сохраняет их строки,
отзывает пустые ожидаемые ответы, отменяет только queued email/MAX, отключает
точную связь и записывает offer history/result/audit в одной транзакции.
Исходные заявки/selected_suppliers, чужие получатели/ответы и оплаченные документы
не переписываются. Обычные recipient policies запрещают следующий read/respond
и legacy fallback. Удалять уже доставленные письма или файлы команда не обещает.

Неопределённая SMTP-попытка и MAX sending блокируют действие: внешний I/O после
durable claim нельзя объявлять отменённым. Завершённая история доставки сохраняется.
Изменяемые реестры получают SHARE ROW EXCLUSIVE до company/identity locks, прочие
предикаты — SHARE; это избегает upgrade-deadlock двух confirm. Глобальная блокировка
по-прежнему требует company writer protocol/нагрузочной приёмки до production.
Предел 50 RFQ и прежние ограничения большого архива — явный отказ.
Исправление уже полученного КП, оформленных документов и merge остаётся отдельным.
[Приёмка](../../tasks/participant-access-stage2f3-review.md).

## Срез 2е4: полученное, ещё не утверждённое КП

15.10.2026. Сохранённое полученное КП не является пустым ожидаемым ответом:
его коммерческие данные и frozen party snapshot нельзя обнулять. Отдельный
`quote-correction-plans` путь явно показывает отклонение Получено→Отклонено;
ожидающие ответы по той же связи отзываются. Оригинальные цены/позиции/сроки/
комментарии/requisites/PDF/responded_at и прежние события остаются, адресаты
скрываются и точная связь отключается. Обычный buyer select после отклонения
не проходит status guard; supplier read/respond/files/create-invoice — recipient
policy. Новый общий deny-флаг в supplier authentication не вводится.

Счёт/поставка/договор/назначение или любой неизвестный потомок КП блокирует
операцию, в том числе при чужом company_id. Awarded позиции запрещены даже при
неправильно оставшемся pending/received status. Для received требуется согласованность
состояний КП/адресата и responded event; выбор/иная business history не стирается.
PDF должен иметь активный registered original покупателя. Удалённый, чужой,
неизвестный original или ссылка из другого документа требуют отдельного разбора.
Один original нескольких закрываемых КП учитывается один раз.

Общая транзакция использует явный mode вместо наращивания bool-параметров.
Unused/RFQ API и ранее сохранённые планы совместимы; тип пути/mode проверяется
при повторе и confirm. Immutable plan/TTL/epochs/версии, свежая роль/владелец,
повторный digest, блокировки, очередь и atomic audit переиспользованы.
Для mixed pending/received плана сохраняются точные before/after статусы каждого
КП/адресата; result содержит rejectedQuoteCount, проверяемый UI.

Новые PARTICIPANT_QUOTE_CORRECTIONS_ENABLED / REACT_APP_PARTICIPANT_QUOTE_CORRECTIONS_ENABLED
default-off, независимы от отдельного RFQ-флага. Схема 0099 используется без
миграции. Глобальные predicate locks, размер архивов и storage/CDN readiness
остаются production-блокерами. Полученные КП с оформленным заказом/счётом и
исторический merge — отдельные сценарии сохранения финансовой основы.
[Приёмка](../../tasks/participant-access-stage2f4-review.md).

## Срез 2е5: оформленные документы требуют отдельного разбора

15.10.2026. Статус каталожной связи не является отзывом адресации счёта. В
correction-preview добавлены financialReview и context строки; это диагностические
метаданные, не apply-план и не разрешение отключить архив. GET остаётся read-only
repeatable-read, с прежними свежими admin/company/request проверками.

Счёт исходной карточки не приписывается кабинету. Выбранные/awarded КП, даже с
ошибочным pending status, счета включая нулевые, поставки независимо от оплаты,
накладные и версии договоров считаются отдельно для двух карточек компании.
Неизвестный реестр — needs_check, а не ноль. clear означает отсутствие этих
документов по проверенным реестрам; он не заменяет доказательство в mutation API.

На странице счетов/КП/накладных parent IDs показываются только после проверки
компании и, для счёта→КП, совпадения поставщика/заявки. При несовпадении IDs не
выдаются. Это проверка показанных родителей, а не всех связей документа.
Суммы, paid_amount, snapshots, URL и файловые права в новый DTO не входят.
Контекст ограничен текущей страницей и загружается пакетно, без N+1.

UI скрывает unused/RFQ/received-quote команды при оформленной/непроверенной
истории. Их серверные guards не ослаблены. Документный отзыв, дальнейшее
разрешённое закрытие обязательств и спорная переадресация требуют отдельного
сценария с сохранением финансовой основы; просмотр их не выполняет.
Новых флагов, миграций и зависимостей нет; существующий preview default-off.
[Приёмка](../../tasks/participant-access-stage2f5-review.md).

## Срез 2е6: отзыв доступа не является отменой финансовых документов

15.10.2026. Отдельный revoke_issued_access mode и issued-access-plans путь
закрывает exact recipients оформленной цепочки КП, связанных счетов/поставок/
накладных. Строки и статусы этих документов не редактируются. Точные статусы
recipient тоже сохраняются; меняются visible_to_supplier, queued notifications
и точная связь компании. Добавляются audit и connection_access_revoked events
с одинаковыми status_from/status_to. Схема immutable plans 0099 переиспользована.

Предварительный SELECT-only CTE меняет адресатов только в проекции. Через те же
runtime policies проверяются потеря доступа к КП/счетам/поставкам/истории/файлам
и отсутствие потери других документов покупателя. У оригиналов проверяются
компания, registry metadata и отсутствие независимого доступа; байты не меняются.
Физическое наличие/storage/CDN остаётся отдельной приёмкой. Документы и записи
служебных пакетов/истории проверены по точным родителям, включая обратные связи
счёт→накладная. Неизвестные descendants/FK/companies не игнорируются.

Назначения менеджеров по покупателю/КП сохраняются, их metadata/version входят
в evidence; назначение не обходит visible_to_supplier. Отдельные счета без КП,
договоры, претензии, общие originals и непроверенная история блокируют действие.
Прежние unused/RFQ/received-quote API не получают новой authority. Новый путь
показывает сохранение статусов вместо отклонения КП; UI проверяет exact retained
document IDs/counts и revokedRequestCount. Новые mutation/UI флаги default-off.

Выявлен самостоятельный supplier_id-only обход в GET /supply-history. Связанные
записи теперь используют политику поставки/КП и coherent company/supplier/
request/project/work-package chain. Для unlinked legacy сохраняется собственное
основание точной карточки/подтверждённой компании; при team mode — только leader.
Неподтверждённая компания или повреждённые родители не дают доступа. Этот read
guard действует независимо от флага новой административной команды. Роли
покупателя и формат API не изменяются. Нет новой выдачи прав/переноса архива.
[Приёмка](../../tasks/participant-access-stage2f6-review.md).

15.10.2026 — 2е7: отдельная команда `invoice-access-plans` использует прежние
неизменяемые планы и exact company/identity/epoch/version guards. Дополнительно
разрешены отдельные счета без заявки и точно связанные с ними накладные.
`company_supplier_links.profile.closedStandaloneInvoiceIds` — серверное поле
запрета точных ID, которое обычный редактор карточки не принимает и сохраняет
при изменении заметок/статуса. Сами счета/склад/платежи не переписываются.
Индекс unique(company_id,supplier_id) ограничивает поиск запрета одной связью.
Нет новой зависимости обычного чтения от таблиц поддержки или миграции:
bootstrap links без private profile сохраняют прежний режим, а команда требует
полного migrated каталога. Общая статическая SQL-проверка используется списком
счетов и чтением оригиналов через КП; отказ сохраняется при поздней привязке
закрытого ID к новому КП. Архив покупателя и новые ID не затрагиваются.
Оба новых флага команды/UI default-off; read denial не зависит от этих флагов.
[Приёмка](../../tasks/participant-access-stage2f7-review.md).

## Срез 2е8: договоры закрываются точными версиями

15.10.2026. `company_supplier_links.profile.closedContractVersionIds` хранит
серверный запрет доступа к проверенным версиям договоров одной связи компании.
Запрет применяется в кабинете поставщика, выдаче оригиналов/приложений,

История версий и файлы сохраняются у покупателя; новый договор/версия имеет

сторон и полного состава registry; общий/неоднозначный оригинал блокирует
операцию. Командный флаг default-off; постоянная проверка чтения остаётся
включённой после выполнения операции. Миграции нет.
