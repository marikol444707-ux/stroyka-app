# Адресное обновление данных интерфейса

## Проблема

После локального действия старые компоненты вызывали callback `loadAll`. Он
повторно читал почти весь доступный пользователю набор данных. Для роли
снабженца один такой вызов создавал 22 GET-запроса, хотя экрану снабжения нужны
8 коллекций. Проектные и финансовые окна также могли запускать общий снимок.
При нескольких действиях подряд запросы накладывались и могли получить 429.

Серверные права, rate limits и tenant-фильтры не меняются. Исправление находится
на клиенте: после записи перечитываются только изменившиеся коллекции, а
зависимые экраны помечаются устаревшими и обновятся при следующем открытии.

## Новое поведение

- Совместимый callback `loadAll` больше не загружает общий снимок. Он обновляет
  только область текущего экрана и объединяет одновременные повторы одного
  запроса.
- Архивация объекта перечитывает только список объектов.
- Реестр документов, переписка и предписания объекта перечитывают по одной своей
  коллекции.
- Финансы объекта перечитывают четыре связанные коллекции: платежи объекта,
  подотчёт, личные траты и ручные расходы.
- Финансовые модальные окна используют отдельные маршруты: один GET для ручных
  расходов или подотчёта, два GET для возмещения.
- Создание личной траты перечитывает только личные траты.
- Создание прайс-листа перечитывает только справочник прайс-листов.
- Уже реализованные области снабжения, склада, персонала, смет и настроек
  продолжают обновляться своими ограниченными пакетами.

После адресного чтения связанные кеши инвалидируются. Например, личная трата
сразу появляется в своём списке, а бухгалтерия, главная и финансы объекта
получат свежие данные при открытии. Это сохраняет согласованность без фоновой
загрузки всех разделов.

## Проверка реализации

- Регрессия доказывает, что совместимый `loadAll` на экране снабжения вызывает
  только 8 требуемых GET вместо прежних 22.
- Отдельные тесты фиксируют один GET реестра документов, четыре GET финансов
  объекта и один GET личных трат с правильной инвалидацией зависимых экранов.
- 12 затронутых наборов: 53/53 успешно.
- Полный frontend: 263 набора, 1614 тестов, успешно.
- Production build собран без ESLint-предупреждений.

Рабочая браузерная и серверная приёмка фиксируется после выпуска.
