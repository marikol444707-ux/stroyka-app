## Исправление

Уточнение пустого ИНН кабинета проверяло другой зарегистрированный кабинет по сырой
строке и пропускало тот же номер с допустимыми пробелами/дефисами. Блокировки
административного потока также отличались от нормализованных ключей профиля и
регистрации. Теперь используются общие canonical_legal/legal_sql/lock_legal_keys:
допустимы только согласованные разделители и длины, буквы/Unicode-цифры не стираются.

Предварительный просмотр возвращает sourceInn в том же каноническом виде, который
будет сохранён и возвращён командой. Это сохраняет контракт уже установленного
frontend (он сверяет ответ с просмотренным значением), не переписывая исходную
карточку. Сырые реквизиты остаются частью отпечатка проверки.

Связанная диагностика кабинета использует те же сравнения, иначе после уточнения
целевого ИНН форматированная исходная карточка не переходила к проверке истории.
Некорректный вторичный ключ блокирует действие даже при совпадении другого ключа.
Диагностика не выдаёт доступ; роли, компания/account и отдельное подтверждение
исторического доступа сохраняются. Заполненный ИНН и существующие документы не
перезаписываются. Совпадение имени не предоставляет прав.

Первый прогон имел ошибку тестовой фикстуры (NULL account запрещён схемой); фикстура
исправлена на отдельную синтетическую компанию/account. Финальный RED: 9 тестов,
6 failures и 3 PASS, без ошибок окружения. После исправления расширенный набор
10/10 PASS. Отдельный агент написал новые регрессии по test-driven-development.

Итого **96 backend, 38 frontend**. Предварительный baseline 12 тестов и последующие
серверные повторы отдельно не увеличивают уникальный счётчик. Все PG-прогоны —
на свежих socket-only кластерах PostgreSQL 15, синтетических данных, с запрещённым
исходящим TCP и без .env. Кластеры остановлены/удалены. AST и diff-check проверены.

Конкуренция с профилем и регистрацией проверена детерминированно через
pg_blocking_pids: одна операция удерживает общий нормализованный ключ; другая ждёт
и отказывается после несовместимого изменения. Нет второй идентичности, частичной
регистрации или лишнего аудита. Mutation-проверка с raw-only locks только в тестовом
процессе ожидаемо падает; runtime-файлы при ней не изменялись.

## Установка, совместимость, откат

Backend-only, без миграций и новых зависимостей. Схема остаётся 0107_estimate_revisions.
Исполняемый frontend не изменяется: сверить исходники, текущий manifest/public,
файлы и production-флаги; сохранить установленную сборку. Уже открытые вкладки
с прежним просмотром могут получить 409 и потребовать повторной проверки, без
перезагрузки/потери ввода/автоматического подтверждения. Числа с разделителями не
переписываются массово — меняется только явно подтверждённое пустое поле цели.

Перед переключением: чистая точная база, серверные проверки, свежий backup при
остановленных writers, восстановление в отдельную БД. После: backend/схема/хеши/
контрольные таблицы/службы и отдельный браузер. Реальные карточки для тестов не
объединять. Без авторизованного production-сценария не создавать verified.json и
deployed.json; резерв сохранять по deployment-retention.md.

## Ограничения

Это не глобальное ограничение уникальности БД для всех возможных writers.
Исторические неоднозначные группы требуют ручной проверки; массового исправления
рабочих данных нет. Контрольные суммы/реестр ИНН не добавлены. Диагностика использует
выражения SQL; большой production-каталог/планы запросов нагрузочно не измерялись.
Синтетическая проверка 50 покупателей/2 accounts в существующих тестах не является
нагрузочной гарантией. Браузерный файл/печать/все темы и все роли не прогонялись;
связанные API-тесты файлов/фото/изоляции перечислены в логах.

Авторизованный production-кабинет требует обычной пользовательской сессии и остаётся
отдельной проверкой. Прикладные части профиля, приглашений, каталога и уточнения ИНН
из PR #374 перенесены последовательными пакетами; старый универсальный installer
из PR не переносился, применяются проверенные сценарии этих выпусков. Слияние всего
PR и публикация GitHub не выполняются. Складской PR #372 — следующий отдельный пакет.
