# Склады компании

## Задача

Следующая вкладка после инвентаризации — «Склады». Завершить каталог складов: принадлежность компании, понятное создание/редактирование, архив вместо удаления, история изменений и безопасный повтор после обрыва связи. Найденная проблема: старые GET/POST/PUT/DELETE работают с глобальной таблицей без компании, а интерфейс скрывает ошибки сохранения.

Существующая модель остатков — один основной склад компании и запасы объектов. Карточки `warehouses` сейчас не участвуют в приходе/перемещении/инвентаризации, колонок `warehouse_id` в БД нет. Вопрос о нескольких самостоятельных складах задан пользователю отдельно. Защита и завершение каталога не зависят от ответа; переход к отдельным остаткам требует явного решения, не выполняется переименованием карточек.

## Приёмка и границы

1. Только выбранная компания и действующее членство; глобальный режим предлагает выбрать компанию. Старые карточки без владельца скрыты до подтверждённой привязки. На сервере найдена одна такая карточка: ID 1 «Лесной склад», Ставрополь, Лесная; вопрос о владельце отправлен отдельно.
2. Просмотр: директор, заместитель, главный инженер, кладовщик, снабженец, бухгалтер. Создание/редактирование — те же роли кроме бухгалтера; архив/возврат из архива — директор и заместитель. Прораб работает с запасами назначенных объектов через уже выпущенную инвентаризацию.
3. Название обязательно, пробелы нормализуются. Поля строго текстовые, ограниченной длины. Два действующих склада одной компании не могут иметь одинаковое название. Совпадение названий разных компаний допустимо.
4. Изменения сохраняются атомарно с автором, временем, исходной и новой карточкой. Владелец неизменяем; физическое удаление закрыто. Архивирование и восстановление требуют основания. Устаревшая версия даёт конфликт, повтор того же UUID возвращает прежний результат без дубля.
5. Интерфейс сообщает об ошибке, сохраняет введённый текст, блокирует повторные клики, очищает данные при смене компании/пользователя. Архив виден отдельно. История открывается из карточки. Мобильная ширина 320 px.
6. Прежний GET `/warehouses` отдаёт только действующие карточки выбранной компании, глобальный режим — пустой список. Прежние мутации закрыты независимо от флага. Остатки, цены, накладные, платежи, инструмент и ведомости сверки не меняются командами каталога.

## Контракт и структура

Новый модуль `backend/features/company_warehouses`, UI `src/features/company-warehouses`, миграция `0031_company_warehouses`. FastAPI/React/PostgreSQL, без новых зависимостей. Отдельная рабочая копия от последнего выпуска; чужие незавершённые изменения не включаются.

- GET `/warehouses/directory`: `{items,canManage,canArchive,truncated}` с архивными карточками.
- GET `/warehouses/{id}/directory`: `{warehouse,history,canManage,canArchive}`.
- POST `/warehouses/directory`: `{action:'create',requestId,name,city?,address?,notes?,expectedCompanyId?,expectedActorId?}`.
- POST `/warehouses/{id}/directory`: `{action:'update'|'archive'|'restore',requestId,expectedVersion,reason?,name?,city?,address?,notes?}`. Update передаёт все четыре текстовых поля. Ответ команды `{ok,warehouseId,eventId}`.
- Карточка `{id,companyId,name,city,address,notes,archived,version,updatedAt}`. Событие содержит автора, основание и снимки до/после.

В `warehouses` добавляются nullable company_id, archived, version, updated_at; новая таблица `warehouse_directory_events`. Legacy-строки не присваиваются компании миграцией. Общий механизм UUID используется для восстановления отправок; автор блокируется до чтения/изменения. Стиль соответствует соседним модулям: `lock_actor(cur, actor)` → проверка версии → запись → событие → commit; ошибка откатывает всю транзакцию.

## Порядок и проверка

Сначала независимые RED-тесты глобального чтения и старых мутаций; затем безопасная схема/сервер и PostgreSQL-сценарии. После этого UI с сетевым повтором, тесты RTL, сборка и реальный браузер на синтетической БД. Ревью, репетиция на закрытой копии, резервная копия, выпуск и проверка доступности/изоляции без тестовых хозяйственных операций в production.

Тесты должны доказывать изоляцию, отзыв членства, отсутствие потерянных правок, атомарность, неизменяемость истории, повторы, архивирование и неизменность складского учёта. Не коммитить секреты/сборки. Владельца прежней карточки изменять только после подтверждения пользователя и точной сверки строки. Счета и оплаты поставщикам остаются другому чату.
