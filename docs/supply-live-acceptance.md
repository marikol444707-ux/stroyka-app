# Сквозная приёмка снабжения через рабочие кабинеты

Пользователь поручил пройти цепочку через интерфейс заказчика и поставщика перед
дальнейшей разработкой команды. Автоматические проверки PostgreSQL не заменяют
эту приёмку. Базовая рабочая версия: d2366ba0, схема 0035_supplier_team_policy.

## Подготовка

- [x] Сессия директора открывается на текущей сборке stroyka26.pro/app.
- [x] Раздел снабжения загружается без ошибок консоли (одно предупреждение preload).
- [x] Найдены два действующих аккаунта поставщиков; отдельного тестового пока нет.
- [ ] Выбран тестовый поставщик/вход и адрес доставки уведомления.
- [ ] Подготовлен явно обозначенный тестовый контур и порядок завершения тестовых
      учётных записей/документов; реальные оплаты и поставки не имитируются как факты.

## Проверяемый сценарий

1. Заказчик создаёт заявку: объект, материал, количество и пакет работ.
2. Согласование прорабом/директором по действующим правилам.
3. Запрос КП выбранному поставщику, автоматический срок ответа с возможностью изменения.
4. Проверяем отдельно: запись КП, видимость в кабинете поставщика, SMTP-результат,
   фактическое получение письма. Сохранённая отметка не доказывает получение.
5. Поставщик отправляет цену, условия и срок. Заказчик видит именно этот ответ.
6. Заказчик выбирает КП. Подтверждённый заказ появляется у поставщика.
7. Счёт связан с тем же КП/компанией; заказчик видит документ и сумму.
8. Проверка условий оплаты и оформления отгрузки. Банковский перевод не выполняется.
9. Приёмка, количество и связь со складским поступлением; двойной приёмки нет.
10. Контроль конечных статусов и отсутствия раскрытия другим поставщикам.

Для каждого шага фиксируем действие интерфейса, ID созданной записи, ожидаемый
и фактический результат. Итог разделяет «пройдено», «ошибка» и «не проверено».
На момент подготовки новая рабочая заявка/счёт/поставка ещё не создавались.

## Уточнение модели команды после P9

Пользователь изменил порядок: руководитель поставщика закрепляет менеджера за
компанией-заказчиком один раз; менеджер получает все её новые запросы этому
поставщику. У каждого сотрудника отдельный вход в один кабинет поставщика.
Ручное назначение каждой заявки не является основным процессом.
Текущая P9-политика проверяет назначение отдельного КП и требует адаптации к
закреплению заказчиков. Это работа после приёмки, а не уже выпущенная возможность.
