# Договор и приёмка для оплаты — локальный этап 18.09.2026

Продолжение после `c675d2a0`. Новый runtime-маршрут оплаты не включён.
Это подготовка достоверных входных данных, **не готовое разрешение платежа**.
Последующее продолжение: внутренний сценарий полной накладной после аванса
описан в `supplier-payment-attachment-check-2026-09-18.md`; runtime всё ещё закрыт.

## Реализовано

- Внутренний `load_invoice_contract` загружает именно сохранённую версию договора
  счёта. Проверяет цепочку компания → заявка → КП → счёт → исторические стороны
  → версия договора, объект и пакет. Новые договоры и текущие профили не заменяют
  уже сохранённые стороны. Контрольная сумма JSON пересчитывается тем же способом,
  что при сохранении; ID сторон проверяются как целые числа, не `bool`/строки.
- Плательщик может отличаться от компании-владельца. Его ID возвращается только
  при совпадении снимка договора с историческими сторонами. Полномочия на это
  юрлицо всё ещё должен проверить ранее созданный `build_payment_access`.
- `load_invoice_receipts` учитывает только приёмки с точным `source_supplier_invoice_id`,
  сверяет всю цепочку и подтверждение приёмки. Отгрузка другого счёта того же КП
  не считается оплатным основанием. Количество сверх отгруженного, NaN и неверные
  связи отклоняются. Товарные остатки не изменяются.
- Закрыт обход через `DELETE /brigade-payments/{id}`: при ошибочной перекрёстной
  связи с ledger-проводкой отказ происходит после проверки прав и блокировки,
  **до** удаления записи бригады и создания отрицательного расхода.
  Обычные платежи бригад работают прежним способом, в том числе без миграции 0017.

## Проверки

58 проверок: 18 реальных PG-тестов контекста договора/приёмок, 3 authenticated
HTTP/PG-теста сторно бригад, 37 unit-тестов brigade access. Отдельные свежие
синтетические базы, Unix-сокет; рабочая база и внешние получатели не использовались.

Проверены сохранение старой версии после появления новой, изменение профиля,
подмена плательщика в исторических сторонах, отдельный плательщик, неоднозначный
объект, неверные пакет/хеш/структура графика, блокировки до конца транзакции,
частичная/проблемная приёмка, неверное количество и чужой исходный счёт.
Сторно ledger-платежа и его сторно через бригаду отклоняется без изменений;
обычная похожая по тексту проводка не считается ledger-платежом.

Независимое ревью выявило различие округления: Decimal half-up для `0.3 × 0.05`
давал 0.02, существующий складской writer — 0.01. Воспроизведено падающим тестом.
Теперь любой результат строки с долями копейки требует сверки (409), а не
получает молча новую оценку. Это временное ограничение узкого внутреннего
resolver; перед общим включением нужна сверка с сохранённой стоимостью накладной.

## Что этот этап ещё не закрывает

- Resolver не является HTTP-авторизацией и не подключён к engine. Нет решения
  «разрешить оплату» по статусу, графику, авансу или результатам приёмки.
- Поддержан только связанный с договором счёт с однозначным объектом и совпадающим
  пакетом заявки. Unbound legacy, item-level/mixed packages требуют отдельного
  источника истины; пустые значения не приравниваются автоматически к «Основная».
- За один счёт допускается до 1000 строк поставки для этой проверки; превышение
  блокируется, а не обрезает финансовую сумму. Это не лимит работы пользователя
  с 20–50 заявками одновременно и не проверка производительности интерфейса.
- Блокировки существующих строк не закрывают конкурентное добавление поставки.
  До запуска требуется общий протокол блокировок всех writers, описанных в
  `supplier-payment-ledger-integration-check-2026-09-18.md`.
- Сценарий «аванс по счёту → новая накладная → остаток после приёмки» ещё не
  переведён на новый реестр. Требуется явное безопасное присоединение накладной
  к истории платежей, а не отключение проверки неизменности группы документов.
- Нет новой миграции, интерфейса, production-deploy или переноса старых данных.
