# Частичные поставки и журнал оплат — проверка через HTTP

Последующий этап: [брак, недостача и нулевая приёмка](supplier-receipt-exceptions-2026-09-28.md).
Ниже сохранён статус исходной интеграции `aa2adb22`.

Локальная доработка после `502879c8`. На сервер не установлена. Флаг
`SUPPLIER_PARTIAL_RECEIPTS_ENABLED` по умолчанию выключен.

## Реализовано

- Отгрузка сохраняет договор и исходный счёт сразу в INSERT. Прежняя связка
  INSERT → UPDATE нарушала неизменяемость договора на схеме 0044.
- Для зарегистрированного в журнале счёта с неизменяемой спецификацией включён
  отдельный путь частичной приёмки. Старые зеркальные поля счёт↔накладная не
  заполняются; каждая накладная связана с общим счётом через receipt relation.
- Строковое доказательство регистрируется в той же транзакции **после** записи
  склада, принадлежности и журнала качества. Ошибка доказательства откатывает
  всю приёмку. Повторная приёмка проверяет прежнюю связь.
- `/warehouse-invoices` возвращает `settlementInvoiceId` только для накладных,
  доступных текущему пользователю. Бухгалтерия показывает их как «Поступления
  по счетам», сохраняет стоимость материала и не начисляет отдельный долг.
  Кнопка оплаты открывает общий счёт. Прямая попытка оплатить такую накладную
  через API отклоняется с 409 после проверки доступа.

## Подтверждено

Изолированный PostgreSQL, настоящие обработчики FastAPI и три роли:
поставщик, прораб и бухгалтер. Без реальных писем, оплат и производственных данных.

Сценарий: проверенный договор с графиком 20/80 → счёт без НДС на 200 →
аванс 40 → две отгрузки по одной единице на 100 → две приёмки → доплата 160.
Проверены два поступления на склад и в журнал качества, один общий счёт,
статус заявки «Поставлено», итог «Оплачен», отсутствие дополнительных денежных
операций при приёмке. Повтор приёмки не меняет количество.

Отдельные проверки: полный откат при поздней ошибке доказательства; запрет
чужому пользователю; запрет отдельного платежа по накладной; выключенный флаг;
брак не регистрируется как принятый материал. Последнее является ограничением,
а не завершённой поддержкой брака.

Журналы: `/tmp/partial-runtime-regression.log` (5 новых HTTP + 25 прежних
платёжных тестов), `/tmp/partial-runtime-ui-final.log`,
`/tmp/partial-receipt-panel-final.log`, `/tmp/partial-runtime-build.log`.
Регрессия обычной отгрузки/приёмки: `/tmp/partial-runtime-legacy.log`.
В локальном browser preview обе накладные открывают invoice #4 с долгом 60;
мобильный снимок `/tmp/partial-receipts-mobile.png`.
Тестовый fixture имеет известные предупреждения вспомогательного AI-контроля
и api_errors.owner_scope; работоспособность этих подсистем данной проверкой
не подтверждается.

## До включения на сервере

1. Доработать приёмку брака, недостачи, нулевого количества и возвратов. Сейчас
   новый путь отказывает с откатом: доказательства рассчитаны на принятый товар.
2. Поддержать поставку до первого платежа: сейчас путь требует уже созданной
   записи счёта в журнале. Старые счета без спецификации и НДС также не покрыты.
3. Проверить общие финансовые отчёты, сроки после полной приёмки и остальные
   экраны склада: локальная проекция добавлена именно во «Входящие».
4. Пройти полный браузерный сценарий с реальным тестовым API, затем выпускать.
   Локальный browser preview проверяет настоящий компонент с вымышленным
   read-only ответом; это не браузерный тест записи в БД.

Не включать флаги глобально и не объявлять финансовый блок завершённым только
на основании успешного сценария принятого товара без НДС.
