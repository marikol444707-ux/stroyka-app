# P3.2a — сохранение запроса КП до отправки email

В текущем обработчике SMTP вызывается до COMMIT запроса КП. Откат базы после
успешной передачи письма приводит к повторной отправке при повторе запроса.

Первый самостоятельный шаг P3.2:
- В транзакции запроса КП сохраняется «В очереди email» в существующем получателе.
- Фоновая задача регистрируется только после COMMIT. Сбой отправки не отменяет КП.
- Перед SMTP отдельная транзакция проверяет компанию, существование заявки,
  обе подписи, видимость получателя, активного пользователя и активное КП;
  атомарно переводит очередь в «Передача email: результат не подтверждён».
- Только успешно зафиксировавшая этот переход задача может вызвать SMTP.
- Подтверждённый успех записывается как «Отправлено» с датой; False/исключение,
  сбой сохранения результата или остановка процесса оставляют неопределённость.
- Повтор запроса КП не повторяет успешную/неопределённую передачу. Старая
  «Ошибка отправки» также неопределённа: старый SMTP-helper скрывал фазу сбоя.
- До начала передачи отсутствие адреса/настройки SMTP/тестовый адрес допускают
  повторную проверку после исправления. Очередь после рестарта возобновляется
  при явном повторе запроса КП; таймера автоматического восстановления пока нет.
- Общий SMTP-helper, MAX-worker, счета/оплаты и исторические сироты не меняются.

Храним состояние в существующем email_notification_status, без миграции.
Задание ссылается на получателя; адрес и текст читаются заново перед передачей.
Между подтверждённым захватом и внешним SMTP остаётся неизбежное окно изменения
доступа; повторная попытка не маскирует это обещанием exactly-once delivery.

Проверки: откат RFQ без SMTP; два конкурирующих worker → одна передача;
SMTP=False/исключение → неопределённость без повтора; успешная передача → одна дата;
чужая компания/скрытый получатель/отключённый пользователь/отозванное КП → без SMTP.
Настоящие письма тестами не отправляются.

Остаток P3.2: отдельное действие безопасного повтора после подтверждённого отказа,
сохранённые подробности попыток, захват MAX до сетевого вызова и проверка его
внешнего worker-протокола. Этот шаг не объявляет весь P3.2 завершённым.

Откат: старый runtime повторяет любой email-статус кроме «Отправлено». Поэтому
простой возврат старого commit после начала новых попыток ЗАПРЕЩЁН. При аварийном
откате выпуск сначала останавливает API и проверяет наличие queued/unconfirmed.
Если они есть, до старта старого API nginx закрывает request-kp (включая /api/
префикс) ответом503 для любого непустого сегмента ID, включая +1/1.0.
Nginx полностью перезапускается; публичные GET-пробы всех четырёх вариантов
должны вернуть503 до запуска старого API. Историю не переписываем. Прямой вызов старого request-kp,
минуя nginx, также запрещён. Карантин снимается только после возврата безопасного
runtime или отдельного согласованного разбора попыток.

Race проверки: после ожидания блокировки получателя заново читаем пользователя
и карточку поставщика; SHARE-блокировки удерживают active/роль/адрес до COMMIT.
Отключение пользователя во время ожидания не допускает передачи SMTP.
