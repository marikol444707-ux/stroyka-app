## Различие двух путей

В старом режиме `SupplySupplierInvoicesPanel.payInvoice` выполняет PUT счёта,
затем отдельный POST `/project-payments`. Его последовательность не атомарна.
Пакет [FH-04 из #395](https://github.com/marikol444707-ux/stroyka-app/pull/395/files)
предлагает отдельную legacy-команду и журнал с миграцией 0109, чей родитель
`0108_project_create_requests` отличается от установленного `0108_receipt_originals`.
Этот пакет нельзя просто применять поверх текущей схемы.

На проверенном сервере включены `SUPPLIER_PAYMENTS_ENABLED=1` и
`REACT_APP_SUPPLIER_PAYMENTS_ENABLED=true`. В браузере директору доступна
«Оплата и история», старая кнопка отсутствует. Флаги не менялись.
Действующий POST `/companies/{company_id}/supplier-payments` уже использует
UUID и одну транзакцию для счёта/связанных документов, движения денег и журнала.
Авторизация повторно выполняется перед возвратом сохранённой операции.

Таким образом, отсутствие модуля `legacy_supplier_payments` не доказывает
отсутствие атомарной оплаты в действующем интерфейсе. Старый режим и произвольные
прямые обращения к legacy API этим выводом не признаны безопасными.

## Фактические проверки

Отдельная локальная PostgreSQL 15, Python 3.12, socket-only disposable runner:

```sh
python scripts/run_supplier_catalog_postgres_tests.py --require-no-skips \
  backend.features.supplier_payments.test_routes_postgres.PaymentHTTPTests \
  backend.features.supplier_payments.test_engine_postgres.LedgerTests \
  backend.features.supplier_payments.test_access_postgres.PaymentAccessTests \
  backend.features.supplier_payments.test_policy_postgres.PolicyPostgresTests
python scripts/run_supplier_catalog_postgres_tests.py --require-no-skips \
  backend.features.supplier_payments.test_http_concurrency_postgres.PaymentHTTPConcurrencyTests
```

62 существующих + 3 новых PostgreSQL-теста PASS, без пропусков. Проверены реальные
HTTP/auth/SQL, повтор UUID, одинаковые отдельные оплаты, запрет переплаты, отказ
прав/чужой компании/плательщика, отзыв членства, откат, связанные документы и сторно.
Engine-only тесты используют синтетический policy, HTTP/access/policy — реальную
авторизацию и разрешение документов. Это различие не скрыто общим числом.

Добавлен один файл `test_http_concurrency_postgres.py`: две HTTP-операции
принудительно перекрываются на блокировке компании. Проверяются физические строки,
суммы, статус счёта, ID движения денег и история. Тот же UUID даёт одну запись;
два UUID с равными суммами — две оплаты; ошибка UPDATE откатывает шесть таблиц,
повтор исходного UUID после снятия искусственного сбоя создаёт ровно одну оплату.
Новый тест не выдаётся за подтверждение ранее существовавшей ошибки продукта.

Первый прогон новых тестов: 3 ошибки в проверочном коде (`id` вместо
`operationId` в истории). Исправлена проверка, повторный прогон 3 PASS. При
искусственных SQL-сбоях fixture пишет предупреждение об отсутствующем
`api_errors.owner_scope`: отказ логгера тестовой БД не скрыт, платежи и откат
проверены независимо. Рабочая БД этим тестам недоступна.

100 frontend-тестов в 7 наборах PASS: paymentClient, useSupplierPaymentDialog
(основной, cancellation, reversal), SupplierPaymentButton, SupplierPaymentDialog,
SupplySupplierInvoicesPanel.payments. Проверены потерянный ответ, повтор прежнего
UUID, двойной клик, смена контекста, поздние ответы и отмена попытки.
Исходники frontend не менялись, сборка повторно не запускалась.
