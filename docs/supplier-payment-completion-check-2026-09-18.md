# Завершение защиты старых путей записи: 18.09.2026

Работа локальная, в `stroyka-supply-reviewer-fallback`. Деплоя, рабочих миграций,
включения журнала оплат и реальных платежей не выполнялось.

## Проверенные изменения

- Явно отключённое членство больше не подменяется старым доступом из
  `users.company_id`. Настоящий legacy fallback при отсутствии любых записей
  членства сохранён. Отдельные права обзора аккаунта не становятся правом записи.
- Создание счёта из КП сериализовано с журналом оплат по компании. После ожидания
  проверяются актуальные пользователь и членство; зарегистрированные дубли и
  несогласованные обратные связи не изменяются. Мигрированная ветка не выполняет
  runtime DDL. Авторизованный повтор чтения существующего счёта сохранён.
- Автоматическая приёмка держит блокировки в порядке склад → компания → поставка.
  Проверяет счёт и накладную до побочных записей и повторно перед созданием
  накладной. Ошибка проверки больше не подавляется восстановлением при replay.
  В запись передаётся проверенный ID счёта, включая явное отсутствие источника;
  новый кандидат не подменяет его между проверкой и записью.
- Ремонт бухгалтерских связей проверяет обе стороны, включая очистку старой
  ссылки, до любой записи. Удерживает текущие права сессии/сотрудника/компании/
  членства до commit. При конфликте блокировок быстро возвращает «занято»,
  а не ждёт с частично захваченными таблицами. Preview остаётся только чтением.
- Объединение дублей ограничено выбранной компанией и её текущей финансовой
  ролью. Проверяет весь пакет до первой записи, включая обратные связи накладных.
  `forceReview` не обходит защиту журнала. Некорректный ID не превращается в
  команду обработки всех документов. Старые схемы готовятся до блокировки
  компании; новые не выполняют DDL из запроса.
- Добавлен внутренний серверный resolver документов: только явные взаимные
  связи, текущий доступ компании до подробных ошибок документа, затем доступ
  к точному договорному плательщику. Ни маршрута оплаты, ни политики разрешения
  нового платежа этот resolver не включает.
- Обычное создание/повторное использование счёта теперь атомарно и не меняет
  владельца документа. Поставщик, объект и взаимные ссылки должны совпасть;
  при обязательной привязке договора используется специальный маршрут КП,
  а не создание неподтверждённой связи общим обработчиком.
- Повторный запрос КП защищён от сброса условий управляемого счёта, включая
  старую связь только через заявку. Авторизация обновляется после ожидания;
  подготовка схемы отключена во вложенных recipient/notification helpers
  мигрированной ветки, но сохранена по умолчанию для прежних callers.

## Что не объявлено готовым

Защита старых путей записи сама по себе не включает новый платёжный сервис.
Управляемая журналом приёмка пока отклоняется до внедрения единой транзакции
приёмки и присоединения накладной. Адаптеры, default-off маршруты и отдельная
форма с устойчивым UUID подготовлены и проверены локально, но не подключены
к рабочим main/ship/receive и бухгалтерским кнопкам. Нужна сквозная проверка
браузер → настоящий API → PostgreSQL, полная регрессия и репетиция выпуска.
Текущий attachment допускает только одну полную однопозиционную накладную;
частичные/многопозиционные поставки, несколько накладных на один счёт, НДС
и правила распределения оплат не объявляются поддержанными. Спецификация
товарных строк счёта пока не является неизменяемым историческим snapshot.
Для непустых пакетов подготовлена добавочная миграция 0019 и проверена интеграция
серверных адаптеров. Исходные миграции и исторические baseline не переписывались.
Без 0019 сохраняется прежнее строгое ограничение; смешанные, повреждённые и
неопределённые пакеты не подменяются пустым значением.
При review RFQ подтверждена существующая отдельная проблема: SMTP вызывается
до commit, в отличие от MAX с transactional outbox. Поздний rollback базы не
отзывает отправленное письмо. Защита журнала не заявляется исправлением доставки
почты; нужен отдельный transactional outbox для SMTP и проверка повторов.

Владелец уточнил правило: график и приёмка не создают жёсткий потолок фактической
оплаты. Разрешены несколько частичных оплат в любые дни отсрочки, включая
досрочную; остаток уменьшается по каждой операции. Отклонение от графика —
контрольная информация, не запрет записи. Проверки прав, целостности, повторов
и суммы сверх долга сохраняются. Спецификация обновлена по этому ответу.

Миграции и активация не должны выполняться одновременно с рабочими writers.
Проверка наличия таблицы не является блокировкой развёртывания. Перед разрешением
рабочей активации нужен проверенный порядок остановки записывающих процессов,
миграции, проверки схемы и последующего запуска.

зеркала и исторические данные не переписывались.
