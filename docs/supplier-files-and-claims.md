# P12.2 — файлы поставщика и завершённая цепочка претензии

## Поведение

Поставщик прикрепляет PDF/изображение к КП, счёту и отгрузке. Загрузка проходит
через POST /supplier-offers/{id}/files. Сервер сам определяет компанию и объект
по доступному адресованному КП; имена, ID объекта и компания из формы не дают прав.
Подписка заказчика проверяется тем же middleware, что для ответа и отгрузки.
Файл регистрируется в существующем file_ownership, context supplier-offer-ID,
в каноническом namespace компании/объекта. Новая схема и флаги не нужны.

Скачивание tenant-files и защищённых legacy uploads каждый раз проверяет
текущую политику адресации/назначения заказчика. Руководитель видит свои документы,
менеджер — только документы назначенных заказчиков. Отключение/переназначение
отзывает последующие скачивания и ответы; уже скачанные копии не отзываются.
Удаление файлов заказчика поставщиком запрещено.

Старые зарегистрированные файлы разрешены по связям КП, счёта, отгрузки,
претензии и складской накладной при совпадении владельца. Складские фотографии
поддерживают прямую, обратную, через поставку и через запрос связь; в последнем
случае обязателен точный поставщик. Неоднозначная принадлежность остаётся отказом.
Прямые старые счета без КП доступны только руководителю согласно прежней политике.
Незарегистрированные и внешние ссылки не обходят серверную защиту.

Ссылку на иной файл нельзя присвоить своему КП, счёту или отгрузке. Повторное
использование старого PDF допускается только если он уже привязан к тому же КП
и зарегистрирован у той же компании. Generic POST /supplier-invoices для
поставщика возвращает 409 до БД: используется create-invoice у конкретного КП.
Это закрывает старый обход назначения через общий endpoint; внутренние счета,
оплаты и бухгалтерские операции не меняются.

Менеджеру доступны просмотр и ответ в претензии назначенного заказчика.
Команда удерживает блокировки текущих прав до фиксации истории. Закрывает
претензию директор заказчика; ответ не изменяет склад и расчёты. Повтор команды
с тем же UUID не добавляет повторную запись.

## Интерфейс

Файл скачивается авторизованным запросом; при отказе остаются сообщение и повтор.
Во время загрузки вложения отправка формы заблокирована. Поздний результат
закрытой/сменившейся формы не прикрепляется к другому КП. Повторный выбор того же
файла после ошибки работает. Показаны файлы КП, накладной, фото отгрузки и претензии.

## Проверки

- 6 HTTP/PostgreSQL сценариев: реальные загрузка/скачивание, чужие и несвязанные
  файлы, компания/объект, отзыв назначения, менеджер претензии, UUID-повтор,
  отдельные файлы заказчика по каждому типу связи, прямые старые счета и legacy PDF,
  запрет загрузки при истёкшей подписке заказчика.
- 4 HTTP/PostgreSQL сценария приёмки: полная, частичная, брак, нулевая;
  созданная претензия, ответ и решение, точный склад без повторных движений.
- 3 HTTP/PostgreSQL сценария нескольких отгрузок: остаток, конкурентная отправка,
  многопозиционный заказ и гонка приёмки/отгрузки.
- Frontend: скачивание/403/повтор, запрет внешней ссылки, ошибка загрузки,
  отсутствие позднего присвоения вложения другому КП; общий прогон и build.
- Независимое security review: замечания по подстановке файлов, старым связям
  и гонке загрузки исправлены.

Аудит зависимостей: без новых зависимостей; npm audit --omit=dev показывает
39 прежних замечаний (19 high, 0 critical), главным образом цепочка react-scripts
и инструментов сборки. Обновление build toolchain — отдельная задача; этот выпуск
не устраняет её и не публикует dev-server. Пересмотреть до 27.09.2026.
