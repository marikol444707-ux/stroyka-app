# Установка объединения поставщиков: безопасные границы

Этот документ описывает поведение установщика, а не подтверждает установку.
Изменение рабочего сервера и объединение реальных карточек требуют отдельного
согласования. Локальные тесты не заменяют приёмку существующей тестовой компании.

## Резерв и откат

Установщик сохраняет только текущий frontend из manifest и публичные файлы,
предыдущий SHA и текущий publisher. Помощник проверки берётся из закреплённого
TARGET, поэтому его наличие в старом checkout не требуется.

До запуска deploy-reviewed.sh новый backend ещё не обслуживал запросы. Ошибка
возвращает checkout к BEFORE через `git reset --keep`, сохраняя посторонние файлы
и отказываясь перезаписывать конфликтующие локальные изменения. Предыдущий
frontend восстанавливается только после успешного возврата checkout. Старый
работающий backend на этом этапе не перезапускался.

После начала deploy-reviewed.sh нельзя доказать отсутствие новых операций с
доступами: новый backend мог запуститься до последующей ошибки проверки.
Автоматически запускать старый backend опасно: он может не учитывать закрытый
доступ к истории. Поэтому установщик оставляет TARGET, пытается удалить только
созданный им режим объединения и перезапустить TARGET, сохраняет резерв и
помечает `manual-recovery-required`. Это НЕ успешный откат. Необходимо отдельно
проверить runtime, выключение режима, frontend и права доступа. Предыдущий код
не возвращается без проверки совместимости с уже совершёнными операциями.

## Что считается установленным, а что принятым

Проверяются health/backend SHA, DB revision, весь manifest.files вместе с
entrypoints (включая отложенные JS chunks), содержимое /app и режимы frontend.
Пути ресурсов должны быть локальными, без traversal и symlink-компонентов.

Успешная техническая установка пишет только `installed-pending.json`:
backend/database/frontend=true, browser=false. Она НЕ создаёт `deployed.json`
или `verified.json`, поэтому резерв не становится доступным автоматической
очистке. Только после фактической разрешённой браузерной приёмки и остальных
проверок можно создать оба завершённых маркера с точным полным SHA и четырьмя
true согласно docs/deployment-retention.md. Сам установщик браузерную приёмку
не имитирует и карточки не объединяет.

## Локальная проверка

`python3 scripts/test_participant_merge_release.py`

Тесты используют временный Git и поддельный systemctl/publisher: проверяют
ошибки после checkout, после запуска backend и после публикации frontend,
сохранность локальных файлов, отсутствие ложного отката, отсутствующие и
повреждённые lazy chunks, опасные пути, symlinks и незавершённые маркеры.
Они не запускают deploy, не подключаются к БД и не меняют сервер.
