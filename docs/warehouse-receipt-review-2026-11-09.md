## Подтверждённые дефекты

Независимые тесты до изменения runtime: старый PUT принимал без оригинала; флаг подтверждения без файла обходил контроль; отсутствующее количество превращалось в ноль/претензию; общий writer Telegram/MAX обходил проверку. Четыре отказа RED; контроль чужой компании уже проходил.

После интеграции найдены и исправлены:
- Оригиналы записывались после финализации финансовой связи: PostgreSQL отклонял приёмку `Allocation delivery provenance is frozen`. Теперь оригиналы поставки сохраняются до writer, все страницы накладной — при INSERT, в той же общей транзакции. После финализации проверка только читает связь/компанию/страницы. Финансовые ограничения не ослаблены.
- MAX превращал любой409 в успех по совпадению sourceId; preview мог раскрыть чужой документ/объект/склад. Обе ошибки воспроизведены отдельным агентом до исправления. Успешный повтор разрешён по собственному уже подтверждённому черновику, а не произвольному совпадению строки источника.
- «Ввести вручную» открывало форму без возможности прикрепить обязательный оригинал. Две frontend-регрессии сначала упали. Теперь ручной вход загружает оригинал и открывает сверку без обращения к OCR.

## Закрытые вопросы при продолжении

- MAX confirm терял проверенные поля оригинала из patch старого черновика. Теперь принимает `receiptDocument`, `originalUrls` и два явных подтверждения; идентичность источника, компании и объекта остаётся защищённой. Регрессия 2 RED → 2 PASS.
- Компактный экран MAX отправлял старый складской POST без сверки. Теперь использует общий upload/review/confirm; связанная отгрузка не создаёт дополнительный standalone POST. Ошибка сохраняет черновик. 4 frontend-регрессии, включая акт без поставщика.
- Существующий режим основного склада «Без поставщика и оплаты» получил оригинал `inventory_act`, не требующий выдуманных ИНН. Только директор/заместитель, номер/дата/положительные строки обязательны. Закупочные ссылки и чужие оригиналы запрещены; повтор не создаёт склад/долг. 8 PG и 5 frontend-регрессий. Это поддержка существующего пути, не новый механизм начальных остатков.
- Повторная документная приёмка возвращала `alreadyReceived`, обходя старые проверки складского движения, качества и финансовых связей. Теперь каждая завершённая строка проходит существующие проверки владения/ledger/качества без восстановления записей, финализации и фонового запуска. Повреждённая завершённая строка блокирует также оставшиеся строки той же накладной.
- Замена по претензии раньше создавалась с условным текстом вместо фактической накладной и без shipment batch. Новая операция требует реальный номер/дату, сохраняет их и batch в общей транзакции. Склад и долг на отгрузке не возникают. Прежняя успешная операция восстанавливается по своему requestId до проверки новых обязательных полей; новые команды старых вкладок без реквизитов отклоняются с понятным сообщением.
- 11 старых интеграционных файлов переведены с закрытого PUT на реальную загрузку → сверку → подтверждение. Положительных HTTP-тестов старого PUT больше не найдено; два оставшихся callsite проверяют отказ. Нет глобального перехвата API или отключённых проверок.

## Совместимость и ограничения перед установкой

1. Старые вкладки/боты с PUT `/supply-deliveries/{id}/receive` получают понятный409. POST `/warehouse-invoices` теперь тоже требует оригинал и явные подтверждения. Автоматического переноса/перезагрузки старых вкладок нет. До обновления сохранить и проверить отдельные копии черновиков, затем закрыть старые вкладки; после — открыть новый frontend.
2. Старый MAX draft можно дополнить проверенными полями через confirm API; черновик сохраняется после отказа. Компактный MAX web-экран использует общий процесс сверки. Внешние Telegram/MAX-боты не получают автоматически новый пользовательский диалог: если текущий бот не умеет собирать поля сверки, завершить приёмку надо в обновлённом приложении. Нельзя обещать прежнюю однокнопочную приёмку без оригинала.
3. «Без поставщика и оплаты» сохраняется для директора/заместителя на основном складе с настоящим актом, номером/датой и оригиналом. Без оригинала провести нельзя. Новые замены по претензии требуют номера/даты накладной. Открытые старые вкладки сохраняют черновик, получают отказ и требуют ручного перехода в обновлённую форму; автообновление с потерей правок запрещено.
4. Read-only проверка на текущем сервере не выявила открытых исторических отгрузок; автоматическое заполнение реквизитов не требуется. Новые/будущие записи с неполной замороженной идентичностью останутся на сверке. Перед переключением проверить изменение этого снимка.
5. Назначенные старые opt-in suites адаптированы и прошли83 теста. Весь pytest проекта, полный CI и все внешние интеграции не запускались; общий CI нельзя объявлять зелёным.
6. Не проверены внешнее распознавание, доставка сообщений Telegram/MAX и bot-token транспорт, объектное S3-хранилище, полный браузерный путь всех ролей через App. Браузерная проверка production не выполнена: подключение к открытой Chrome-сессии ранее остановилось на ошибке инструмента `Importing module "node:process" is not allowed in node_repl`.
7. Черновики сверки остаются в памяти страницы; это не серверное хранение черновиков. Закрытие окна сохраняет текущий черновик, перезагрузка/смена компании требует предварительного сохранения пользователем. Новую функцию долговечных черновиков этот пакет не добавляет.

Незакрытые условия установки: актуальное подтверждение черновиков/окна, проверенная резервная копия текущей БД и возможность выполнить авторизованный production browser workflow. В этой итерации установка не выполнялась; **releaseReady=false** до выполнения условий. Предыдущий установленный выпуск и его непроверенные браузером резервные копии здесь не изменялись.
