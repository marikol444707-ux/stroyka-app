# Инструмент и ответственность

## Цель и согласованный порядок
Один инструмент имеет инвентарный номер, текущее состояние, точного получателя и неизменяемую историю. Выдача/возврат и событие сохраняются одной транзакцией. При поломке или утере фиксируется происшествие; директор отдельно подтверждает сумму и договорное основание. Для подрядчика/бригады сумма включается в штраф акта выполненных работ, остаток переносится на следующие акты. Пользователь выбрал этот блок и порядок 19.09.2026.

## Поведение
- Выдача только исправного инструмента со склада активному исполнителю выбранной компании и объекта; получатель определяется ID, не ФИО. Договор при выдаче выбирается явно, его сторона и объект совпадают с получателем и объектом.
- Возврат исправного → «На складе», повреждённого → «На ремонте», утеря → «Утерян». Получатель снимается с текущего хранения, сохраняется в истории/происшествии. Причина обязательна для повреждения и утери.
- Завершение ремонта и обнаружение утерянного инструмента — отдельные события. Списание/архивирование — директорское решение с причиной. История не удаляется.
- Старые выдачи без точного получателя/объекта и записи «На объекте» уточняются директором через отдельное событие reconcile с обязательным основанием. Директор явно выбирает «На складе» либо точного получателя/объект/договор. Действие разрешено только до первой новой операции; исходные поля остаются в снимке истории. Миграция не переносит ответственность автоматически.
- Повтор запроса с тем же UUID и содержимым возвращает тот же результат. Другой запрос по устаревшему состоянию получает 409. Ошибки не закрывают форму, повтор после сетевого обрыва использует исходный UUID.
- Денежная ответственность не возникает автоматически от поломки, стоимости карточки или статуса возврата. Подтверждение требует суммы, документа стоимости, договорного основания и подписанного договора подряда. Работник может оспорить своё происшествие до включения штрафа в акт. История решений сохраняется.
- Подтверждённые штрафы инструмента и материалов вместе уменьшают сумму к оплате, не ниже нуля; одна сумма не удерживается дважды. Сформированные акты сохраняют снимок. Уже распределённое решение нельзя пересмотреть обычным редактированием.
- Компания, объект, получатель и договор проверяются на сервере. Старые записи не приписываются человеку по совпадению имени. Ранее проданные «в счёт зарплаты» инструменты не переводятся автоматически в новый учёт.

## API и данные
Новый модуль backend/features/tool_custody, существующий каталог /tools сохраняется. GET /tools/{id}/custody возвращает tool, expectedState, history, incidents, choices, canManage/canDecide. POST /tools/{id}/custody принимает requestId, expectedState, action (issue/return/repair/recover/write_off/archive/reconcile), recipientId/projectId/contractId для выдачи, condition/reason для возврата/происшествия. POST /tools/{id}/incidents/{incidentId}/decisions принимает requestId, decision, reason, amount, priceEvidence, contractEvidence.
Миграция 0029_tool_custody добавляет версию/договор хранения к tools и неизменяемые tool_custody_events, tool_incidents, tool_incident_decisions, tool_fine_allocations. Операции используют уже существующий журнал UUID work_material_operations. Старый PUT не меняет движение инструмента, POST истории не подделывает события, DELETE возвращает 409 с указанием использовать архивирование отдельной операцией. Новый контур включается TOOL_CUSTODY_ENABLED / REACT_APP_TOOL_CUSTODY_ENABLED; защита проведённых событий и финансов сохраняется при отключении.

## Границы
Счета и оплаты поставщикам ведутся другим чатом. Настройки зарплаты и автоматические удержания с сотрудников не добавляются. Старые данные и денежные снимки сохраняются; неясные исторические назначения требуют точного подтверждения, не угадываются. Продакшен проверяется без синтетических хозяйственных операций.
