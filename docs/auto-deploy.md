# Автоматическая выкладка сайта

После того как новый код попадает в ветку `main` и проверка CI проходит успешно, GitHub сам подключается к серверу и запускает обычный `deploy.sh`.

Пока секреты ниже не добавлены, выкладка не начнётся: задача остановится с текстом, какого секрета не хватает. Сервер при этом не меняется. Секреты лучше добавить до слияния этого изменения в `main`.

## Какие секреты добавить

Откройте репозиторий на GitHub: **Settings → Secrets and variables → Actions → New repository secret**.

Добавьте четыре обязательных секрета:

| Секрет | Что вставить |
| --- | --- |
| `DEPLOY_HOST` | Адрес сервера, имя или IPv4. Без `https://` и без пробелов. |
| `DEPLOY_USER` | Пользователь, под которым заходим по SSH. |
| `DEPLOY_SSH_KEY` | Весь приватный ключ, включая строки `BEGIN` и `END`. Ключ должен быть без пароля. |
| `DEPLOY_PORT` | Порт SSH. Обычно это `22`. |

И один необязательный, но желательный:

| Секрет | Что вставить |
| --- | --- |
| `DEPLOY_KNOWN_HOSTS` | Ключ самого сервера, чтобы GitHub не перепутал его с чужим. |

Как получить `DEPLOY_KNOWN_HOSTS` на своём компьютере (подставьте адрес и порт):

```bash
ssh-keyscan -p 22 -H адрес-сервера
```

Скопируйте весь вывод в секрет. Если этот секрет не задан, GitHub сам спросит ключ у сервера командой `ssh-keyscan`. Так проще, но если сеть в этот момент подменена, можно довериться не тому серверу. Поэтому лучше задать секрет заранее.

Ключ и адрес в журнал GitHub не печатаются. Ключ записывается во временный файл с доступом только для этого запуска и удаляется в конце.

## Как это работает

1. Кто-то отправляет код в `main`.
2. Запускается уже существующая проверка с именем **CI**.
3. Выкладка стартует только если CI закончился успешно, это был именно push в `main`, и коммит из этого же репозитория. Чужие ветки, pull request и форки сайт не выкладывают. Красный CI тоже не выкладывает.
4. Две выкладки одновременно не идут. Вторая ждёт. Если за время ожидания появилась ещё более новая, промежуточная отменяется, на сервер едет последняя. Если старая проверка CI закончилась уже после того, как на сервере стоит более новый коммит, старый коммит не выкладывается и сайт назад не откатывается.
5. Скрипт запоминает коммит, который сейчас на сервере в `/var/www/stroyka-app`.
6. Ставит на сервер ровно тот коммит, который прошёл CI, и запускает `deploy.sh`.
7. Обычный `deploy.sh` сам делает `git pull` и мог бы забрать более новый код. Автоматическая выкладка этого не позволяет: сервер остаётся на проверенном коммите.
8. Проверяется адрес https://stroyka26.pro/health. В ответе должно быть `ok: true`, а `version` — первые 12 символов нового коммита. Так сайт уже отвечает сейчас, отдельно менять программу не нужно. Проверка повторяется примерно минуту: сайт может подняться не с первой секунды.
9. Если `deploy.sh` упал или сайт не подтвердил версию, сервер возвращается на старый коммит, `deploy.sh` запускается ещё раз, и здоровье проверяется снова. Задача в GitHub становится красной, чтобы это было видно.

Вручную ту же выкладку можно запустить так: **Actions → Deploy → Run workflow**. Кнопка сработает только из ветки `main` и только если последний CI для этого коммита зелёный.

## Как выключить

1. Откройте **Actions**.
2. Слева выберите **Deploy**.
3. Справа нажмите `...` и пункт **Disable workflow**.

Пока workflow выключен, новые коммиты в `main` сами на сервер не поедут. Включить обратно: **Enable workflow**.

## Что уже должно быть на сервере

- Каталог `/var/www/stroyka-app` — обычная git-копия этого репозитория.
- Сервер уже умеет скачивать код с GitHub, как при ручном `git pull`. Новый ключ GitHub на сервер этот workflow не кладёт.
- Пользователь из `DEPLOY_USER` может без запроса пароля перезапускать службы. `deploy.sh` вызывает `systemctl` напрямую и не использует `sudo`. Обычно это пользователь root или тот же пользователь, которым выкладку запускают руками.
- Нужны запись в каталог приложения, файл блокировки `/var/lock/stroyka-deploy.lock`, `python3`, `npm` и миграции, как при обычном `deploy.sh`.
- У службы `stroyka` не должны быть заданы переменные `APP_VERSION` и `GIT_COMMIT`. Иначе сайт покажет их вместо реального коммита, проверка не сойдётся и выкладка откатится.

## Важная оговорка про базу

`deploy.sh` перед перезапуском обновляет базу (`alembic upgrade`). Откат возвращает старый код и снова запускает `deploy.sh`, но уже применённые миграции базы сам не отменяет. Если миграция несовместима со старым кодом, после отката сайт может не подняться. Тогда нужна ручная проверка.
