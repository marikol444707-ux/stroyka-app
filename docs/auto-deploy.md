# Ручная выкладка с GitHub

Обычное обновление сервер забирает сам. Как это включить, написано в [docs/pull-deploy.md](pull-deploy.md).

Этот файл описывает запасной путь: человек вручную запускает workflow **Deploy** в GitHub, и GitHub подключается к серверу по SSH. Сам по себе он больше не стартует после CI, потому что с серверов GitHub до нашего сервера нет доступа.

Пока секреты ниже не добавлены, выкладка не начнётся: задача остановится с текстом, какого секрета не хватает. Сервер при этом не меняется. Секреты лучше добавить до слияния этого изменения в `main`.

## Какие секреты добавить

Откройте репозиторий на GitHub: **Settings → Secrets and variables → Actions → New repository secret**.

Добавьте четыре обязательных секрета:

| Секрет | Что вставить |
| --- | --- |
| `DEPLOY_HOST` | Адрес сервера: имя или IPv4. Пробелы, перевод строки и невидимые символы по краям можно не стирать: скрипт уберёт их сам. Если вместе с адресом скопировались `ssh://`, `http://`, `https://`, `root@` или `:22` в конце, это тоже будет убрано. |
| `DEPLOY_USER` | Пользователь, под которым заходим по SSH. Лишний пробел или перевод строки по краям не мешает. |
| `DEPLOY_SSH_KEY` | Весь приватный ключ, включая строки `BEGIN` и `END`. Ключ должен быть без пароля. |
| `DEPLOY_PORT` | Порт SSH. Обычно это `22`. Лишний пробел или перевод строки по краям не мешает. Если порт написан и в адресе, и в этом секрете, берётся этот секрет. |

И один необязательный, но желательный:

| Секрет | Что вставить |
| --- | --- |
| `DEPLOY_KNOWN_HOSTS` | Ключ самого сервера, чтобы GitHub не перепутал его с чужим. |

Как получить `DEPLOY_KNOWN_HOSTS` на своём компьютере (подставьте адрес и порт):

```bash
ssh-keyscan -p 22 -H адрес-сервера
```

Скопируйте весь вывод в секрет. Если этот секрет не задан, GitHub сам спросит ключ у сервера командой `ssh-keyscan`. Так проще, но если сеть в этот момент подменена, можно довериться не тому серверу. Поэтому лучше задать секрет заранее.

Ключ и адрес в журнал GitHub не печатаются. Ключ записывается во временный файл с доступом только для этого запуска и удаляется в конце.

## Как это работает

1. Кто-то открывает **Actions → Deploy → Run workflow** на ветке `main`.
2. Уже существующая проверка **CI** для этого коммита должна быть зелёной. Чужие ветки и красный CI сайт не выкладывают.
3. Две выкладки одновременно не идут. Вторая ждёт. Если за время ожидания появилась ещё более новая, промежуточная отменяется, на сервер едет последняя. Если старая проверка CI закончилась уже после того, как на сервере стоит более новый коммит, старый коммит не выкладывается и сайт назад не откатывается.
4. Скрипт берёт тот же замок, что и обычный `deploy.sh`. Если выкладку уже запустили руками, автоматическая ждёт её окончания и не меняет файлы, пока та работает. Потом запоминает коммит, который сейчас на сервере в `/var/www/stroyka-app`.
5. Ставит на сервер ровно тот коммит, который прошёл CI, и запускает `deploy.sh`.
6. Обычный `deploy.sh` сам делает `git pull` и мог бы забрать более новый код. Эта выкладка этого не позволяет: сервер остаётся на проверенном коммите.
7. Проверяется адрес https://stroyka26.pro/health. В ответе должно быть `ok: true`, а `version` — первые 12 символов нового коммита. Проверка повторяется примерно минуту: сайт может подняться не с первой секунды.
8. Если `deploy.sh` упал или сайт не подтвердил версию, сервер возвращается на старый коммит, `deploy.sh` запускается ещё раз, и здоровье проверяется снова. Задача в GitHub становится красной.

Кнопка **Run workflow** сработает только из ветки `main` и только если последний CI для этого коммита зелёный.

## Как выключить

Обычную выкладку останавливает команда из [docs/pull-deploy.md](pull-deploy.md). Этот запасной workflow и так не запускается сам. Если нужно спрятать и кнопку: **Actions → Deploy → ... → Disable workflow**.

## Что уже должно быть на сервере

- Каталог `/var/www/stroyka-app` — обычная git-копия этого репозитория.
- Сервер уже умеет скачивать код с GitHub, как при ручном `git pull`. Новый ключ GitHub на сервер этот workflow не кладёт.
- Пользователь из `DEPLOY_USER` может без запроса пароля перезапускать службы. `deploy.sh` вызывает `systemctl` напрямую и не использует `sudo`. Обычно это пользователь root или тот же пользователь, которым выкладку запускают руками.
- Нужны запись в каталог приложения, файл блокировки `/var/lock/stroyka-deploy.lock`, `python3`, `npm` и миграции, как при обычном `deploy.sh`.
- У службы `stroyka` не должны быть заданы переменные `APP_VERSION` и `GIT_COMMIT`. Иначе сайт покажет их вместо реального коммита, проверка не сойдётся и выкладка откатится.

## Важная оговорка про базу

`deploy.sh` перед перезапуском обновляет базу (`alembic upgrade`). На сервере это делает таймер из [docs/pull-deploy.md](pull-deploy.md), когда CI уже зелёный. Откат возвращает старый код и снова запускает `deploy.sh`, но уже применённые миграции базы сам не отменяет. Если миграция несовместима со старым кодом, после отката сайт может не подняться. Тогда нужна ручная проверка.
