# Претензии по поставкам

Следующий блок после шаблонов заявок. При приёмке уже создаётся претензия,
но текущий PUT позволяет записать произвольный статус/дату, заменяет один текст
resolution и не оставляет историю. Поставщик видит только исходное описание.
На 2026-09-19 production имеет 0 претензий, схема0032, HEAD f41a2c1b.

## Поведение и границы

Открыта → В работе → Решена; для закрытия достаточно и исходной Открыта.
Руководитель может вернуть Решена/Закрыта в Открыта с объяснением. Старый статус
Закрыта считается завершённым. Неизвестные старые статусы доступны только чтению.
Разбор, комментарии и решение не меняют фактическую приёмку, остатки, накладные,
счета, оплаты и штрафы. Допоставка/возврат/возмещение оформляются соответствующими
документами; решение фиксирует результат разбирательства. Доставка с исторической
проблемой остаётся такой, рядом отображается отдельный статус её претензии.

Внутренние роли: директор/заместитель, снабженец, кладовщик, прораб могут взять
претензию в работу и комментировать; бухгалтер и мастер читают в прежней области
доступа. Поставщик отвечает только на свою адресованную открытую претензию.
Решение и повторное открытие — директор/заместитель (рекомендованный вариант
отправлен пользователю; до другого ответа используем это ограничение).
Все добавляемые тексты видны участникам претензии, включая поставщика; форма
объясняет это до отправки. Нет автоматических внешних уведомлений при QA.

## API и хранение

- GET /supply-claims сохраняет legacy array, но использует целостную связку
  claim→delivery→offer→request с одной компанией, проектом, поставщиком и пакетом.
- GET /supply-claims/cases: выбранная компания для внутренних пользователей;
  поставщик получает только явно доступные ему поставки. `{items,truncated}`,
  первые200 новейших. Фильтрация по проекту/пакету и действующему членству.
- GET /supply-claims/{id}/case: `{claim,history,historyTruncated,canComment,
  canStart,canReply,canResolve,canReopen}`; последние200 событий. Claim содержит
  прежние display-поля, companyId,supplierName,version. Повреждённые/чужие цепочки
  не раскрываются. Все чтения no-store.
- POST /supply-claims/{id}/case: `{action,text,expectedVersion,requestId,
  expectedCompanyId,expectedActorId,materialAccountingVersion?}`. Actions:
  start/comment/reply/resolve/reopen. Text — непустая строка до4000, безNUL.
  Неизвестные поля, подмена автора/даты/статуса отвергаются400. Версия и права
  проверяются на сервере; время и автор серверные. Ответ `{ok:true,id,eventId}`.
- Старый PUT закрыт409; доступный новый POST требует UUID и обе context pins.
  Replay возвращает исходный результат без нового события, changed content409;
  текущие права и адресация перепроверяются до replay. Совпадение названий/email
  поставщиков никогда не даёт доступ. Поставщик не нуждается в членстве покупателя.
- Используется существующий work_material_operations для идемпотентности;
  billing для нового supplier POST определяется по авторизованной связке,
  как у прежнего PUT. Нельзя подставить другую компанию с активной подпиской.
- Migration0033 добавляет version/updated_at и append-only supply_claim_events
  (claim_id,delivery_id,company_id,operation_id,actor_id,actor_name,action,text,
  before_state,after_state,created_at). Права чтения истории равны текущим правам
  чтения претензии. Факты претензии/владелец не редактируются, version++ на событие.
  Downgrade запрещён при событиях/изменённых версиях; исторические факты сохраняются.

## Интерфейс и проверка

Существующая вкладка Поставки получает список претензий с открытием карточки;
вкладка Претензии поставщика использует ту же карточку с серверными возможностями.
Никакого глобального кэша карточек: company/user remount, загрузка/ошибка/повтор,
запрет двойного отправления, recovery исходного UUID и текста. Черновик другого
события/карточки при recovery не очищается. Статус и история отдельно от текста
нового действия. 320px, клавиатура, ошибки серверной версии и обрыв связи.

Тесты: сначала real PG RED произвольного статуса/перезаписи resolution; затем
полный lifecycle, supplier isolation/revocation, права выбранного членства,
контекст/точная версия, concurrent replay, rollback, immutable facts/events,
подписка покупателя и byte-identical unrelated business tables. RTL+browser
на синтетике; frontend/backend full gates; миграция на приватной копии production,
проверка сохранности всех старых колонок; backup/release/smoke. Production QA
не создаёт претензий и не отправляет тексты поставщикам. Счета/оплаты — другой чат.


## Проверка реализации перед выпуском

- Real PostgreSQL RED подтвердил произвольный status/resolvedAt старого PUT и
  перезапись решения поставщиком после закрытия. Старый обработчик удалён;
  аутентифицированный PUT теперь409.
- Независимая ревизия нашла и закрыла два случая: чтение через legacy fallback
  без членства; повторная отправка устаревшей версии после ручного обновления.
  Неопределённая сохранённая отправка при обновлении сохраняет исходную версию.
- Общие проверки: backend3759,634 opt-in skips; отдельно PG12 для претензий и
  PG1 старой границы disclosure. Frontend174 suites/1091 tests, затем final
  targeted RTL10 (два дополнительных regression). Production build собран.
- Репетиция0033 на приватной копии production сохранила все исходные колонки
  и строки172таблиц. Рабочая база при репетиции не изменялась.
- Browser synthetic: директор взял претензию в работу; потеря ответа после
  commit и точный replay дали одно событие. На320px scrollWidth=320.
  Минимальная QA-база не содержит полной схемы соседних модулей: известные
  ошибки общего refresh /suppliers,/tools,/tool-history,/inventory,/crm/lead-summaries
  не относятся к маршрутам претензий. Реальные сообщения поставщикам не отправлялись.
- Поставщик отправил ответ в той же истории (2события); директор закрыл
  претензию (3события). Supplier UI320px также без горизонтального скролла.
