## Цель и границы

Заказчик видит только свои объекты, подтверждённый ход работ, фото, предназначенные
ему документы и гарантийные обращения. Внутренние закупочные цены, зарплаты,
маржа, чужие объекты и внутренние замечания не становятся клиентскими данными.
Кабинет владельца SaaS-аккаунта (`ClientAccountCabinet`) — другой интерфейс;
здесь дорабатывается `CustomerCabinetPage`. Счета/оплаты поставщикам не меняются.

Не добавлять новую модель объекта или новый способ авторизации без необходимости.
Использовать существующие роли, компания/объект по ID и защищённые файлы.
Согласование заказчиком не выдаёт прав на внутреннюю приёмку работ.

## Порядок

1. C1: проверить доступ и исправить существующие команды. Выбор объекта не должен
   предпочитать одноимённый объект правильному ID. Ошибка сервера не становится
   успешным согласованием; повторные нажатия блокируются на время запроса.
2. C2: проверить серверную выборку и набор клиентских полей; исключить выборку
   по одному названию при разных компаниях, показать загрузку/ошибку/пустые данные.
3. C3: ход работ и фото, этапы и честный прогресс без неподтверждённых объёмов.
4. C4: документы заказчика и защищённые вложения; не раскрывать внутренние документы.
5. C5: гарантийное обращение, фото и статус ответа; отдельная проверка прав записи.
6. C6: две компании, одноимённые объекты, отзыв доступа, мобильный браузер,
   независимое ревью, выпуск и проверка; резерв удалить после успеха.

## Следующий срез C2: точное владение записями

Реализовано локально после первоначального среза:
- RecordScope разрешает компанию через существующий company-context, затем
  проверяет эффективную роль членства. Роль основного профиля не заменяет роль
  выбранной компании. Все новые scoped endpoints используют только authentication
  dependency; роли проверяются внутри scope, а не до разрешения членства.
- /prescriptions и /warranty-defects, /project-documents и /project-letters
  читают через JOIN по company_id/project_id; записи без владельца не выдаются.
  Заказчик видит собственные замечания/гарантийные обращения и документы стороны
  customer. Внутренние notes документов не выдаются заказчику.
- Авторы записей и новые company_id/project_id задаются сервером. Заказчик не
  назначает ответственного и не ставит собственному новому обращению закрытый
  статус. Закрытие/повторное открытие своего замечания не стирает ответ подрядчика.
- Исправлены дополнительные writers документов из CRM и сверок смет. CRM отдаёт
  приоритет закреплённому projectId, запрещает переназначение на другой ID и
  отклоняет неоднозначное название. Обновление документа сверки тоже scoped.
- UI замечаний использует companyId/projectId/createdByUserId, а не имя/роль.
- Реальный запуск на свежей БД выявил отсутствие fix_photo_url/fix_notes в legacy
  init_db prescriptions. Миграция 0040 добавляет их через IF NOT EXISTS.

Проверки: 14 PostgreSQL/HTTP сценариев с двумя компаниями, дублирующимися названиями,
чужим автором, отзывом назначения и разными ролями; дополнительно отдельный тест
полного backend с настоящими auth tokens и company context, без подмены зависимостей
авторизации. Его исходный сбой на отсутствующих полях исправлен миграцией, повтор
прошёл. 11 UI-тестов и production build прошли. Findings независимого ревью по
