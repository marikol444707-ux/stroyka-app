## Цель и границы

Заказчик видит только свои объекты, подтверждённый ход работ, фото, предназначенные
ему документы и гарантийные обращения. Внутренние закупочные цены, зарплаты,
маржа, чужие объекты и внутренние замечания не становятся клиентскими данными.
Кабинет владельца SaaS-аккаунта (`ClientAccountCabinet`) — другой интерфейс;
здесь дорабатывается `CustomerCabinetPage`. Счета/оплаты поставщикам не меняются.

Не добавлять новую модель объекта или новый способ авторизации без необходимости.
Использовать существующие роли, компания/объект по ID и защищённые файлы.
Согласование заказчиком не выдаёт прав на внутреннюю приёмку работ.

## Порядок

1. C1: проверить доступ и исправить существующие команды. Выбор объекта не должен
   предпочитать одноимённый объект правильному ID. Ошибка сервера не становится
   успешным согласованием; повторные нажатия блокируются на время запроса.
2. C2: проверить серверную выборку и набор клиентских полей; исключить выборку
   по одному названию при разных компаниях, показать загрузку/ошибку/пустые данные.
3. C3: ход работ и фото, этапы и честный прогресс без неподтверждённых объёмов.
4. C4: документы заказчика и защищённые вложения; не раскрывать внутренние документы.
5. C5: гарантийное обращение, фото и статус ответа; отдельная проверка прав записи.
6. C6: две компании, одноимённые объекты, отзыв доступа, мобильный браузер,
   независимое ревью, выпуск и проверка; резерв удалить после успеха.

## Следующий срез C2: точное владение записями

Реализовано локально после первоначального среза:
- RecordScope разрешает компанию через существующий company-context, затем
  проверяет эффективную роль членства. Роль основного профиля не заменяет роль
  выбранной компании. Все новые scoped endpoints используют только authentication
  dependency; роли проверяются внутри scope, а не до разрешения членства.
- /prescriptions и /warranty-defects, /project-documents и /project-letters
  читают через JOIN по company_id/project_id; записи без владельца не выдаются.
  Заказчик видит собственные замечания/гарантийные обращения и документы стороны
  customer. Внутренние notes документов не выдаются заказчику.
- Авторы записей и новые company_id/project_id задаются сервером. Заказчик не
  назначает ответственного и не ставит собственному новому обращению закрытый
  статус. Закрытие/повторное открытие своего замечания не стирает ответ подрядчика.
- Исправлены дополнительные writers документов из CRM и сверок смет. CRM отдаёт
  приоритет закреплённому projectId, запрещает переназначение на другой ID и
  отклоняет неоднозначное название. Обновление документа сверки тоже scoped.
- UI замечаний использует companyId/projectId/createdByUserId, а не имя/роль.
- Реальный запуск на свежей БД выявил отсутствие fix_photo_url/fix_notes в legacy
  init_db prescriptions. Миграция 0040 добавляет их через IF NOT EXISTS.

Проверки: 14 PostgreSQL/HTTP сценариев с двумя компаниями, дублирующимися названиями,
чужим автором, отзывом назначения и разными ролями; дополнительно отдельный тест

## C3: журнал и расчёт прогресса (локально)

Карточка объекта и журнал для роли заказчик теперь используют явный список полей.
Из журнала исключены материалы, расчёты с бригадой, внутренние комментарии,

Расчёт клиентского прогресса отделён от внутренних затрат: полные активные сметы
и полный подтверждённый журнал загружаются с выбранной компанией. Общие загрузчики
приложения дают лишь summaries и первую страницу журнала, для процента этого мало.
Подтверждённое количество сопоставляется с точным positional estimateItemKey,
ограничивается плановым количеством и взвешивается стоимостью позиции работы.
Если запись не связана с активной сметой (включая допработы), нет полного состава
позиций или конфликтуют активные версии пакета — точный процент и выполненная
сумма не показываются. При отсутствии стоимостного плана сохранённый процент
подписан «Оценка подрядчика». Нестандартные ключи пока дают неизвестный расчёт,
а не приблизительное сопоставление по названию. Загрузка/ошибка не выдаётся за
пустые сметы, фото или журнал. Поздние ответы предыдущего объекта игнорируются.

подтверждённых записей/полей, production build. Независимое ревью обнаружило
summary/pagination и ложные empty-state сообщения; исправлены и проверены повторно.

показывают только customer-публикации точного объекта и компании; аннулированные

Гарантия: описание, дата обнаружения, необязательный телефон и JPG/PNG/WebP до

POST использует проверенный useCustomerCommands; draft очищается только после
ok:true, неопределённая запись/ошибка refresh блокирует повтор. Список содержит
только собственные обращения по immutable author ID, статус и ответ подрядчика.
Удаление файла заказчику не выдаётся; «Убрать из обращения» очищает только draft.

Единый источник строк сохранён в appMainState. Новый useCustomerRecordsLoader
встроен в общий data-loader; прежние customer-запросы/сетторы этих трёх ресурсов
отключены, чтобы они не дублировали запросы и не стирали снимок пустым fallback.
Каждый ресурс имеет status/scope/error. Только mode=company, выбранная компания
и точный доступный project ID разрешают загрузку. Legacy имя поддерживается
через существующий customerProject только при однозначной карточке. Чужая
компания, чужой projectId даже в той же компании и чужой автор не принимаются
в общее хранилище. Late responses/отозванный scope игнорируются, запросы abort
при смене scope/unmount. Refresh ошибки не выдаются за пустой успешный результат.

Проверки: 60 frontend tests (включая общий loader без двойного чтения/стирания),
3 authenticated PostgreSQL сценария полного backend; расширена цепочка

## Срез согласования допработ — локально завершён 20.09.2026

GET /unexpected-works/customer-visible публикует только доступные точные записи
company/project и клиентские поля. POST /unexpected-works/{id}/customer-decision
принимает только approve/reject и hash показанных условий; цена/объём/автор не
редактируются клиентом. Автор/московская дата и owned audit сохраняются атомарно;
повтор одного решения не добавляет события, противоположное или устаревшее
решение возвращает409. Согласование не создаёт факта работы в журнале.
Общий GET исключает customer-компании, сохраняя внутренние права mixed-role
all_companies аккаунта. Общий PUT заказчику по-прежнему недоступен.

Новый ресурс подключён к одному customer loader, прежние загрузчики его не
дублируют. Решение в UI отправляет только decision/revision; отказ сохраняется
в истории без печати согласованного допсоглашения. Проверки:4 authenticated PG,
63 estimate_changes unit,35 frontend,56 runtime/fingerprint,6 progress. Ревью
выявило mixed-role регрессию; воспроизведена тестом, исправлена и одобрена.
CI production build сначала выявила прежний no-loop-func в progress; эквивалентные
for-of циклы исправили предупреждение, повторная CI-сборка успешна.

объёмам, с точной привязкой к строке сметы; согласование допработ само по себе
не увеличивает выполненную сумму. Договоры берутся из опубликованных документов.
