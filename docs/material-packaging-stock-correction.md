# Корректировка упаковок на складе

## Статус

Проектный контракт. Автоматическая корректировка старых приходов запрещена.
Ручная сверка упаковки сохраняет решение и доказательства, но не изменяет
накладную, остатки или складскую историю.

## Проблема

Накладная может содержать кабель, металл, смеси или другую продукцию в
упаковках: бухта, пачка, коробка, мешок, палета, барабан. Смета и выдача
могут использовать базовую единицу: метры, килограммы, тонны, штуки, литры.

Нельзя исправлять исторический приход только по совпавшему названию: после
него материал мог быть выдан, перемещён, списан или смешан с другим приходом.
Текущие агрегированные остатки `warehouse_main` и объектных материалов не
несут прямую ссылку на исходную строку накладной, поэтому они не доказывают,
какая часть остатка относится к конкретной упаковке.

## Действующие правила

1. Подтверждённое правило упаковки применяется только при новом приходе.
   В накладной сохраняются исходные `documentQuantity/documentUnit` и
   нормализованные количество/единица.
2. Неизвестная упаковка остаётся в документной единице и получает
   `needs_review`; приход не блокируется.
3. Сверка старой накладной доступна директору и заместителю. Она требует
   решение, комментарий, автора и снимок доказательств, но не создаёт
   складскую операцию.
4. Для выдачи из накладной пользователь может выбрать исходную строку.
   Сервер проверяет компанию, склад/объект, материал, единицу и остаток
   именно этой строки. Совпадение названия не заменяет сохранённую ссылку.
5. Старые движения без `source_invoice_id/source_invoice_line_index` остаются
   legacy и не участвуют в автоматической корректировке.

## Условия для будущей автоматической корректировки

Операция разрешается только для нового прихода, если одновременно выполнены
все условия:

- есть подтверждённое правило с базовой единицей и содержимым упаковки;
- сам приход и все последующие выдачи/перемещения имеют точную ссылку на одну
  строку накладной;
- партия хранит отдельный доступный остаток, а не выводится из агрегированной
  карточки материала;
- количество к исправлению не превышает остаток этой партии;
- нет неразмеченных зависимостей, чужой компании, иной единицы или отменённой
  первичной накладной;
- создаётся отдельная обратимая корректировочная операция, а исходная
  накладная и её строка не переписываются;
- директор или заместитель подтверждает итоговый серверный preview.

## Требуемая модель данных

Перед включением apply нужен отдельный additive-срез с партиями прихода.

`warehouse_receipt_lots`:

- `id`, `company_id`, `project_id` (nullable только для основного склада);
- `warehouse_invoice_id`, `invoice_line_index` - уникальный источник партии;
- `material_key`, исходная и базовая единицы, исходное и нормализованное
  количество;
- `received_quantity`, `available_quantity`, `status`;
- `created_at`, `created_by`.

Любая новая выдача, перемещение, возврат или списание должна создавать
проводку лота с точным количеством. Агрегированный остаток остаётся
производным представлением, а не источником для корректировки упаковки.

`warehouse_lot_movements`:

- `lot_id`, `company_id`, `operation_type`, `quantity`, `unit`;
- ссылка на складскую операцию/ЖПР/возврат;
- `reversal_of_id` для отмены;
- `created_at`, `created_by`.

## Алгоритм apply

1. Сервер повторно строит preview и блокирует строку накладной и её лот.
2. Повторно проверяет правило, компанию, единицу, остаток лота и отсутствие
   неразмеченных зависимостей.
3. Создаёт `packaging_correction` с неизменяемым snapshot до/после и audit.
4. Создаёт компенсирующие lot-movement записи: минус документная единица,
   плюс базовая единица в рамках той же партии. Исходная накладная не меняется.
5. Обновляет производный агрегированный остаток в одной транзакции.
6. Отмена создаёт обратную операцию, а не удаляет историю.

Любая ошибка, конфликт количества, параллельная выдача или несовпадение
плана откатывает всю транзакцию.

## Очередность внедрения

1. Добавить read-only readiness report: количество исторических строк без
   источника, кандидаты новых партий и точные blockers. Реализовано как
   `npm run audit:material-stock-correction-readiness`; до появления таблицы
   партий он обязан возвращать `receipt_lot_schema_missing`.
2. Добавить таблицы партий и проводок без изменения существующих остатков.
3. Начать записывать партии только для новых приходов и источники только для
   новых движений; protected smoke подтверждает наследование компании.
4. Добавить preview и apply только для одной полностью связанной партии с
   обязательным подтверждением директора/заместителя.
5. Добавить отмену, роль, аудит, конкуренцию и smoke; только затем расширять
   на другие типы складов.

## Что не делать

- не менять старые `warehouse_invoices.items`;
- не пересчитывать остаток по названию материала;
- не связывать старую выдачу с накладной задним числом;
- не объединять разные поставки/партии в одну корректировку;
- не запускать массовый apply без отдельного плана, preview SHA и rollback.
