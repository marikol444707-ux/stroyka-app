# Завершение уведомлений поставщика — P3.2

Подготовка выпуска; результаты и версия добавляются после проверки.

## Поведение

- Перед SMTP сохраняется отдельная попытка с компанией, заявкой и получателем.
  В диагностике заказчик видит последние 20 попыток и безопасный код причины.
  Тела писем, адреса и текст ошибок провайдера в журнал не копируются.
- Явный повтор разрешён только для последней попытки с подтверждённым отказом.
  Он проверяет права заказчика и версию попытки; повторное нажатие не создаёт КП.
  Потеря ответа после передачи, старые ошибки и неизвестные результаты не повторяются.
- SMTP получает ровно одного адресата. Частичный/необычный ответ считается
  неопределённым. Ошибка QUIT после подтверждения не отменяет факт приёма SMTP.
- MAX атомарно захватывает только актуальное адресное уведомление; заявка,
  получатель и аккаунт блокируются до фиксации захвата, затем идёт сетевой вызов.
  Отправленным считается ответ с ID провайдера. Неизвестный исход не возвращается
  в очередь. Невалидные строки не занимают весь пакет обработчика.
- События запроса КП исключены из старого внешнего list/send/status протокола:
  отправлять их разрешено только через серверный dispatcher с durable claim.
  Остальные типы MAX-сообщений этим изменением не переделываются.
- Таймер email каждую минуту обрабатывает до 5 сохранённых, ещё не начатых отправок.
  Использует существующий внутренний worker credential, без входа пользователя.
  Не импортирует backend/main.py отдельным процессом и не запускает init_db.
  При занятом deployment lock возвращает отдельный код 75, остальные ошибки видны.

## Выпуск

Обязательна аддитивная миграция 0039 до запуска нового API. Остановить старый MAX
worker, дождаться завершения старого API, применить миграцию, проверить данные,
запустить новый runtime, затем включить email timer. Никаких автоматических
повторов исторических failed/unknown событий или исправлений сирот.

Откат к старому runtime после новых отправок требует карантина worker endpoints
и отключения таймеров: старый внешний status-протокол позволяет обойти claim.
Историю попыток не удалять. Простое понижение схемы запрещено.

## Границы

«Принято SMTP/MAX» не означает «Входящие» или «Прочитано». Доставляемость и строгая
DMARC-политика отложены пользователем; для этого выпуска реальные тестовые
письма/сообщения не отправляются. Счета и оплаты остаются в другом рабочем потоке.

## Проверки перед выпуском

- 19 PostgreSQL/HTTP сценариев в шести отдельных базах; внешние соединения запрещены.
  Конкурентная отправка, отзыв во время ожидания блокировки, неверные/чужие
  получатели, старый worker-протокол, неопределённый ответ, история и явный повтор.
- 202 frontend-набора / 1216 тестов; production build успешен с сохранением
  действующих флагов. Отдельное независимое ревью пройдено после исправления
  частичного SMTP-ответа, гонки отзыва, блокировки очереди и пустого MAX-ответа.
- Три неизменяемых снимка общего main.py в проверках warehouse preview обновлены
  после ревью изменений уведомлений. Реализация warehouse preview не менялась;
  все 56 его проверок пройдены. Итоговый общий backend-прогон фиксируется ниже.
