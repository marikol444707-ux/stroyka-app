# Возврат старых удержаний за инструмент

10.11.2026. Пользователь подтвердил порядок: сначала бухгалтер явно сверяет
возвращённые ранее суммы по документам (включая 0), затем отдельно подтверждает
фактический возврат остатка. Банковского перевода приложение не выполняет.

## Что изменено

В «Бухгалтерия → Закрытие → Инструмент в счёт оплаты» для проверенной выдачи
с ненулевой суммой «Ранее удержано» появился раздел «Возврат старых удержаний».

1. Однократная сверка прежних возвратов сохраняет сумму, основание, автора и ревизию
   в неизменяемом журнале. Не создаёт денежного расхода и не переписывается.
2. Фактический возврат требует суммы, основания, подтверждения и текущей ревизии.
   Сервер ограничивает сумму: старое удержание минус прежние и новые возвраты.
3. Новая отрицательная запись в `project_payments` и событие истории сохраняются
   в одной транзакции под общей блокировкой финансового реестра. При сбое аудита
   откатываются деньги и ревизия. 409 сохраняет ввод, автоматического повтора нет.
4. Исходные акты, зарплата, складская выдача и gross-сумма старого удержания
   сохраняются. Возврат не освобождает лимит для повторного удержания.
5. Компания/сотрудник/объект берутся из проверенного источника. Подмена их в запросе
   отвергается. Неоднозначное название объекта блокирует создание денежной записи,
   поскольку старый финансовый журнал всё ещё хранит название.

Новые маршруты: PUT `/tool-deductions/{id}/historical-refund-review` и POST
`/tool-deductions/{id}/historical-refunds`. Применяют существующие финансовые роли,
company scope, общую транзакцию и `expectedRevision`. GET реестра возвращает
серверное состояние `historicalRefund`; без подтверждённой сверки остаток `null`.

При проверке обнаружены и исправлены два дефекта чтения платежей:

- DISTINCT по сумме/дате/основанию скрывал второй реальный возврат. Для платежей,
  связанных с событиями инструмента, различимость теперь задаётся ID события.
  Старое поведение несвязанных legacy-записей и поставщицкого реестра сохранено.
- GET не возвращал точный ID объекта из выдачи. Теперь платёж получает `projectId`
  через связь company → событие → источник, без поиска владельца по названию.
  Экран платежей больше не требует лишней сверки принадлежности такого возврата.

## Установка и совместимость

Схема остаётся `0116_tool_deductions`. Миграций и зависимостей нет: используются
существующие source revision, журнал JSON-событий и связанный денежный платёж.
Старые вкладки работают с прежними API и ревизией; новые операции им недоступны.
Новые frontend-поля необязательны для старого клиента. Backend обновляется раньше
frontend, единым проверенным пакетом. Принудительно терять черновики не требуется.

Перед переключением: сверить commit/dirty/untracked/flags, сохранить текущие
manifest/public-файлы, БД и uploads. Во время обслуживания остановить писателей;
восстановить дамп в отдельную базу, сравнить все поля 83 наборов бизнес-таблиц,
запустить полный новый backend с запретом внешних соединений. Миграции не запускать.
После переключения: schema/health/данные, 325 frontend-файлов по хешам и публичному
HTTPS, доступность двух новых API через существующий nginx-префикс, запрет
анонимных запросов, кабинет директора — закрытие/инструмент, платежи и зарплата.
Не создавать пробные финансовые операции на production.

Только после четырёх отдельных проверок backend/БД/frontend/browser записать
`verified.json` и `deployed.json`, очистить резерв/staging согласно
`docs/deployment-retention.md`, проверить сервер после очистки.

## Откат

Пока новых исторических событий нет, допустим откат backend/frontend к base;
схема и БД не менялись. Если новые события уже записаны, сначала предпочесть откат
только frontend с сохранением нового backend: старый backend снова схлопывает
равные возвраты в списке платежей. Полный откат тогда требует аварийной сборки с
сохранённым исправлением GET. Историю и деньги не удалять, дамп поверх новых
операций не восстанавливать. Скрипт полного отката должен проверять отсутствие
новых исторических событий и отказывать иначе. После очистки старого staging
предыдущий UI пересобирается из Git с сохранёнными flags.

## Ограничения и остаток

- Бухгалтер отвечает за документальное подтверждение старых сумм; приложение
  не может установить, был ли возврат вне системы. Без сверки запись запрещена.
- Исправление ошибочно подтверждённой сверки прежних возвратов и сторно нового
  возврата не реализованы; история не переписывается. Это отдельная финансовая
  корректировка, а не удаление платежа из общего списка.
- Нет выдуманной связи старого удержания с конкретным актом или месяцем. Они не
  пересчитываются. Проверены реестр и связанный раздел платежей, а не все отчёты ERP.
- Покупки инструмента в v2-актах, частичная зарплата и финансовые корректировки
  после выплат остаются следующими блоками. Банковской интеграции здесь нет.
- Заполненный финансовый сценарий на production не выполняется без подходящих
  реальных записей; корректный пустой GET не доказывает проведение возврата.
