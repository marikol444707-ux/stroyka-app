# Архив поставщика: граница компаний

Статус: первый серверный этап, локально; не выпущено на рабочий сервер.

## Что меняется

- `supplier_documents.company_id` — компания-владелец записи архива, а не
  автоматически плательщик. NULL означает личную/неразобранную запись поставщика.
- Корпоративное чтение использует существующий проверенный контекст компании
  и эффективную роль в каждой компании. Режим всех компаний только для чтения.
- Роли архива: директор, заместитель, снабженец, кладовщик, бухгалтер.
- Новые корпоративные документы получают владельца из серверного контекста.
  `companyId` в теле не может переопределить выбранную компанию.
- Прикрепляемый файл корпоративного архива должен иметь защищённый адрес
  `/tenant-files/{id}/content`, того же владельца и не иметь проектного ограничения.
  Документ объекта пока нельзя повышать до общего архива компании.
- Поставщик читает записи только своих supplier IDs с `company_id IS NULL`; клиентский
  архив и заметки не передаются ему автоматически. Личные загрузки без компании
  остаются личными. Передача произвольного `companyId` поставщиком отклоняется.
- DELETE архивирует запись через `archived_at`, не удаляет строку или файл.
  Поставщик не может архивировать запись заказчика, даже если она относится к нему.
- Автор новой записи определяется сервером, а не полем uploadedBy клиента.

## Совместимость и миграция

1. До обновления API применить `0008_supplier_doc_ownership` на тестовой БД,
   затем проверить корпоративное чтение/создание и личный кабинет поставщика.
2. Миграция добавляет nullable ownership, archive marker, FK компании и индекс.
   Inline bootstrap также добавляет колонки и индекс; FK устанавливает Alembic.
3. Старые записи не изменяются и автоматически не распределяются по названиям,
   ИНН поставщика, текущему пользователю или компании по умолчанию.
4. Поэтому прежние общие документы перестанут появляться у заказчиков до
   установления владельца по проверенным основаниям. Это намеренное закрытие доступа.
   Поставщик сохраняет доступ к своим неархивированным личным/старым записям.
5. Механизм доказательного переноса старых записей ещё не реализован. До выпуска
   оценить число таких записей и согласовать процесс их разбора. Массовый перенос
   вручную или автоматический backfill в этом этапе не запускать.
6. Downgrade отказывается удалять новые поля при наличии ownership/archive данных.
   Возврат старого API снова откроет незащищённые списки: это не безопасный откат.

Ответ GET дополнен companyId и visibility. POST возвращает companyId.
Успешный DELETE возвращает `{ok: true, archived: true}`. Статусы signedAt/status
остаются пользовательскими данными и не являются доказательством ЭП.

## Границы проверки безопасности

Обработчик списка и мутации проверяют company ownership; выдача содержимого
по `/tenant-files` сохраняет отдельную существующую проверку доступа.
Данный этап НЕ добавляет поставщику membership заказчика или обход защиты файлов.
Метаданные и файл не следует считать полностью двусторонне доступными.
Глобальные contractUrl в карточке suppliers и старые прямые ссылки остаются
отдельным аудитом перед выпуском. Бухгалтерские backfill/dedupe здесь не изменялись.

## Следующие согласованные этапы

1. Связь сделки: компания-инициатор, сторона договора, плательщик, получатель,
   поставщик; смена плательщика не передаёт владение или доступ.
2. Версии договоров и подтверждённые снимки реквизитов каждой стороны.
   Распознавание предлагает поля; человек проверяет конфликт/неуверенные значения.
3. Адресные документы сделки и доступ к содержимому для участников без членства
   в чужой компании; отдельные права на внутренние заметки и коммерческие документы.
4. Все партии отгрузок и результаты приёмки, а не одна выбранная поставка.
5. Этапы предоплаты/постоплаты, распределение платежей, независимые события
   «заказчик сообщил об оплате» и «поставщик подтвердил поступление».
6. Единая история в кабинетах участников по разрешениям. Видимость всем участникам
   не означает право всем подтверждать оплату, приёмку или менять договор.
7. После проверки настоящего API обновить интерактивный прототип.

## Проверки

Новые тесты сначала воспроизвели пять нарушений существующего поведения (RED).
После исправления пройдены unit/SQL contract проверки и локальные PostgreSQL
проверки в TEMP-таблицах. Прикладные таблицы и рабочий сервер не изменялись.

Команда целевого набора:

```sh
RUN_SUPPLIER_DOCUMENT_PG_TESTS=1 python3 -m unittest \
  backend.features.supplier_documents.test_routes \
  backend.features.supplier_documents.test_migration \
  backend.features.supplier_documents.test_postgres \
  backend.features.company_context.test_service \
  backend.features.supplier_access.test_service \
  backend.features.document_access.test_routes \
  backend.features.document_access.test_service \
  backend.features.warehouse_receipts.test_policy
```

PostgreSQL-набор запускается явно, отказывается от нелокального host и создаёт
только TEMP-таблицы с search_path=pg_temp. При закрытии соединения они исчезают.
Миграция требует отдельного rehearsal перед выпуском; браузерный E2E не проводился.
