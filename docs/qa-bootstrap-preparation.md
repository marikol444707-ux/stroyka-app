# Подготовка чистого QA — локальная, не исполняемая процедура

Основа: 012c9984. Installer hold сохранён. Здесь нет команд reset, bootstrap,
upgrade, restore, stamp или запуска сервера. Новых контейнеров не требуется.

## Реализовано

`backend/bootstrap_schema.py` содержит точную строку прежнего первого SQL-блока
init_db как инертную константу. Она импортируется штатным init_db; существующее
поведение старта сохранено. Модуль не импортирует приложение, конфигурацию или
драйвер БД. Это отделение исходного материала схемы, а не готовый чистый bootstrap:
исторический batch также содержит legacy UPDATE и другие преобразования данных.
Теперь он хранится как 761 упорядоченная пара (категория, точный SQL):
735 schema, 2 seed, 24 repair. Отдельные SCHEMA_STATEMENTS, SEED_STATEMENTS,
REPAIR_STATEMENTS — только представления текста. Для старого init_db они
собираются обратно в первоначальном порядке и передаются одним cur.execute,
как прежде. Ни группировка, ни отдельное выполнение на старом пути не введены.

Четыре DO-блока вручную отнесены к schema: ограничения audit_log,
user_company_roles/staff, brigade_payments и project_payments. Два INSERT VALUES
с legacy идентификатором 1 относятся к seed; это не готовые учебные компании.
INSERT SELECT из users в user_company_roles — repair, а не seed.
Два SELECT setval тоже repair: они изменяют последовательности. Оба WITH UPDATE
(сопоставление платежей и закрытие повторяющихся AI-задач) относятся к repair.
Все 19 обычных UPDATE также repair. ALTER TYPE и проверки ограничений остаются
schema, но могут изменять/отклонять существующие данные; категория не является
разрешением исполнения. Лексический разбор не классифицирует новые DO/CTE
автоматически: новые формы должны получить review и тест.

`scripts/qa_bootstrap_plan.py` читает только исходные Python-файлы миграций через
AST, проверяет уникальность IDs, единственную ожидаемую вершину, отсутствие
циклов, потерянных родителей и отдельных компонент. Неожиданные merge/dependency
ветви требуют review. Возвращает полный порядок, перечень стадий и блокеров.
Любой запрос разрешения исполнения отклоняется без флага обхода.

Recovery validator принимает только явные boolean-отметки доказательств, требует
отдельной демонстрации восстановления, учитывает обоих writers и файлы. Он не
проверяет достоверность введённых отметок и не даёт разрешения на применение.

## Что ещё не реализовано и почему

Нет исполнителя подготовки/восстановления: сохранённый SQL содержит repairs,
autocommit допускает частичное применение, полный запуск чистой схемы и её
восстановление не приняты. Вынос только строки не решает эти вопросы. Создание
команды, исполняющей её сейчас, было бы неподтверждённым альтернативным путём
мимо hold. Не добавлены destructive команды даже с подтверждающим флагом.

Классификация первого batch завершена без неразмеченных команд. Остались inventory
транзитивных startup helpers и контракт итоговой схемы. Затем отдельно допустимая
проверка полного bootstrap/миграций/восстановления; запрещённый аудит не заменяется
новым runner. До неё нет утверждения о поддержке пустой базы.

Остаток init_db вне batch классифицирован по чтению: цикл seed_users — seed
учётных записей; следующий UPDATE 2FA — repair; циклы SITE_PRICE_RULE_DEFAULTS
и DEFAULT_MATERIAL_NORMS — seed справочников; _startup_repair_saved_estimate_adjustments
и три SQL операции own_expenses/expenses — repair. Они оставлены на своих местах:
переносить их в чистую схему нельзя. Следующий ensure_agent_jobs_schema — schema
helper, но его выполнение и транзитивные импорты здесь не принимаются.

Конкретные причины не запускать одни schema-фрагменты на старой базе: repairs
перед FK/CHECK платежей очищают некорректные связи; membership INSERT SELECT
зависит от существующих users/companies; seed компаний и accounts использует
ID 1; sequence setval меняет состояние независимо от наличия строк. На действительно
пустой базе эффект отличается — это требует отдельной разрешённой проверки.

## Операционный контракт будущего допуска

1. Зафиксировать оба backend, QA-подключение, общий storage и frontend; исключить
   всех writers перед согласованным backup. Конфигурацию хранить защищённо.
2. Проверить восстановимость базы, uploads, кода обоих backend, текущего frontend
   и его manifest. Одного успешного dump или health недостаточно.
3. После отдельного допуска: пустая согласованная QA-область → базовый DDL без
   repair/seed → полный граф от 0001 → проверка схемы → безопасный synthetic seed.
4. Запускать candidate только с соответствующим frontend. Первый контейнер
   сохранить остановленным до доказанной совместимости startup DDL и writes.
5. При отказе восстанавливать согласованный комплект целиком, сохранив сведения
   о новых операциях. Git checkout и downgrade не являются универсальным откатом.
6. Не удалять backup до всех проверок; не создавать verified.json заранее.

Разрешены только тесты AST и локальных mock-данных. Реальная база, сеть, приложение,
контейнеры, браузер, миграции и старый запрещённый audit-run не запускались.
