# Кабинет поставщика — план реализации по прототипу

Статус на 2026-09-19: P1 выпущен56c0d2ac; P2 выпущенb48eff7d; P3.1 выпущенb9b5cf39; P3.2 и P4–P14 ожидают выполнения.
ПроверкиP1: [загрузка входящих](supplier-inbox-loading.md).
ПроверкиP2: [ответ поставщика](supplier-quote-response.md).
Основание: присланный пользователем экран интерактивного прототипа и аудит рабочего
кода/сервера версии961e2ef8. Исходники самого прототипа не предоставлены:
его невидимые экраны и поведение кнопок не считаются проверенными требованиями.

## Цель

Один кабинет компании-поставщика: получить адресную заявку от заказчика,
подготовить КП, увидеть решение, исполнить заказ, передать документы и обработать
претензию. Руководитель видит общую работу, менеджер — разрешённые ему задачи.
Каждый раздел использует реальные данные; демонстрационные50заявок/6заказчиков
и счётчики со скриншота не переносятся в рабочую базу.

## Что сохраняем из работающей системы

- Согласования заявки, адресацию выбранным поставщикам и изоляцию данных.
- КП по нескольким позициям, условия поставки/оплаты, выбор предложения заказчиком.
- Связь отгрузок с приёмкой и претензиями.
- Проверенный каталог: импорт XLSX/XLS/UTF-8 CSV, ручное добавление/удаление,
  общую блокировку операций в одной вкладке и обработку неопределённых ответов.
- Существующие ограничения отгрузки по условиям оплаты. Изменение счетов/оплат —
  отдельный чат; здесь только согласование интерфейсов и проверка интеграции.

## Основные решения

1. Заявка на стороне заказчика, запрос КП конкретному поставщику, предложение,
   отгрузка и приёмка — разные записи. Новый интерфейс не заменяет их одним статусом.
2. «Новая/В работе» — организация работы поставщика. «Ждём заказчика» — отправленное
   КП; «Заказ подтверждён» — предложение действительно выбрано заказчиком.
   «Отгружено» определяется фактами отгрузки, не означает «Принято» или «Оплачено».
   Отклонённые/отозванные запросы остаются доступными в истории.
3. «Доступно в кабинете», «уведомление в очереди», «передано провайдеру»,
   «доставлено» и «прочитано» различаются. Доставка/прочтение показываются только
   при наличии соответствующего подтверждения; успех SMTP сам по себе их не доказывает.
4. Компания-поставщик и компания-заказчик — разные границы доступа. Членство
   менеджера в команде поставщика не делает его сотрудником заказчика.
5. По умолчанию новый запрос не назначен менеджеру. Предлагаемый порядок:
   руководитель назначает/переназначает; менеджер работает с назначенными запросами.
   Автораспределение и право самостоятельно забирать общую заявку пока не включаем.
   Это проектное допущение для этапа команды, а не уже согласованная бизнес-политика.
6. Повторная отправка и двойное нажатие не должны создавать второе КП/заказ/отгрузку.
   Для операций с неопределённым результатом нужен серверный механизм безопасного
   повтора либо явная сверка результата; одной блокировки кнопки недостаточно.
7. «Заказы» сначала представляют выбранные КП с существующими отгрузками.
   Отдельную сущность заказа вводить только если выявятся необходимые данные,
   которых нет в текущей модели; не создавать дубли закупок ради экрана.
8. Срок ответа задаётся явно заказчиком. Если срока нет — показывать «Не указан»;
   не выдумывать срочность по возрасту записи. Часовой пояс и правило просрочки
   фиксируются в контракте API и показываются пользователю.

## Порядок работ и критерии готовности

### Этап1. Поставщик действительно видит заявку и может ответить

**P1. Загрузка входящих (M, 3–5файлов; без зависимостей).**
- При обычном входе без специального URL загружаются доступные запросы/КП.
- Загрузка, пустой список и ошибка — разные состояния; есть повторная загрузка.
- Смена аккаунта/компании и запоздавший ответ не раскрывают чужие записи.
Проверка: сначала тест текущего дефекта; RTL загрузки и ошибок; браузер с реальными
сессиями двух поставщиков и двух заказчиков в изолированной базе.
Файлы: data-loaders/useAppDataLoaders, SupplierCabinetPage и их тесты.

**P2. Ответ поставщика возвращается заказчику (M; послеP1).**
- Полный сценарий: согласование → выбор адресатов → запрос КП → вход поставщика →
  ответ по позициям → просмотр/выбор заказчиком. Само создание заявки не рассылает её.
- Потеря ответа, повторное нажатие и повторный вход не создают лишних предложений;
  при ошибке черновик сохраняется.
- Невыбранный поставщик не видит запрос; отзыв доступа действует сразу.
Проверка: реальный HTTP/PostgreSQL сценарий + два браузерных аккаунта, включая
отказ/отзыв доступа. Файлы: supplier_offers/routes, supplierPortalActions и тесты;
при необходимости отдельным малым изменением исправить обновление экрана заказчика.

**P3. Честные уведомления (M; послеP2).**

P3.1 выполнен: [факты очереди и обновление КП](supplier-notification-evidence.md).
P3.2 остаётся: сохранённые попытки, ошибки провайдеров и безопасный явный повтор.
Аудит уточнён:12исторических получателей ссылаются на отсутствующие заявки;
6отметок очереди MAX принадлежат этим строкам. Они не относятся к2текущим заявкам.

- Сверить связи получателей с очередью MAX: в аудите есть отметки очереди без
  соответствующих записей отправки. Ничего автоматически не пересылать и не удалять.
- Показать подтверждённое состояние email/MAX, причины отказа, время попытки;
  повтор уведомления не создаёт новый запрос КП и не дублирует уже выполненную отправку.
- Отказ внешнего канала не скрывает запрос из кабинета.
- ВыполненоP3.1: «Обновить КП и уведомления» перечитывает карточку ответа и
  диагностику адресатов вместе; ошибки/неподтверждённая очередь показаны явно.
Проверка: подменённые провайдеры, обработчик очереди, отказ/повтор/восстановление.
Настоящее тестовое письмо или MAX-сообщение — только указанному пользователем
получателю по отдельному явному поручению; без этого внешняя доставка не сертифицируется.
Файлы: адресация/уведомления supplier_access, messenger, представление статуса и тесты;
если затронуты оба канала существенно — отдельные подзадачиP3-email/P3-MAX.

**Контрольная точка1:** воспроизводимо работает цепочкаP1–P2; поP3 отдельно зафиксировано,
что подтверждено тестами, очередью и реальным провайдером. Только после этого
можно говорить «заявки видны и ответы доходят», не обещая неподтверждённую доставку сообщений.

### Этап2. Экран заявок как в прототипе

**P4. Реестр заявок (M; послеP2).** Таблица/мобильные карточки: номер, заказчик,
объект, материалы, время получения, фактическое состояние КП. Сайдбар и маршрут
«Заявки» по прототипу; сохраняется открытие конкретного запроса после перезагрузки.
Проверка: реальная выборка, длинные названия, пустые состояния, мобильный экран320px.
Файлы: новые небольшие компоненты supplier workspace, существующая маршрутизация, RTL.

**P5. Поиск, фильтры и CSV (M; послеP4).** По номеру/материалу/объекту, заказчику,
статусу; пагинация и счётчики по всей доступной выборке, а не загруженной странице.
CSV соответствует фильтрам и правам; значения защищены от формул при открытии в Excel.
Проверка: больше одной страницы, сброс фильтров, Unicode, права и CSV с опасными префиксами.
Файлы: supplier query/API, реестр/фильтры, тесты.

**P6. Сроки и карточки внимания (M; послеP5).** Источник срока ответа согласован
и хранится; «Сегодня», «Просрочено», «Ждём заказчика», «Можно готовить к поставке»
рассчитываются по данным. Отсутствующий срок явно обозначен; готовность учитывает
текущие ограничения отгрузки. Клик карточки применяет соответствующий фильтр.
Проверка: границы суток/часовой пояс, отозванное КП, отсутствие срока, ограничения оплаты.
Файлы: контракт срока/при необходимости миграция, query, карточки и тесты.

### Этап3. Заказы и несколько заказчиков

**P7. Заказы (M; послеP2/P4).** Отдельный список подтверждённых КП с составом,
условиями, заказчиком, объектом и ссылками на существующие отгрузки/документы.
Невыбранное КП не становится заказом; частичная отгрузка не закрывает остаток.
Проверка: выбранное/отозванное предложение, несколько позиций, частичная поставка.
Файлы: проекция orders/API, экран заказов и тесты.

**P8. Заказчики (M; послеP5/P7).** Список фактически связанных заказчиков и фильтр
«Все заказчики» только в пределах прав поставщика. Карточка даёт историю запросов,
заказов и доступных документов; реквизиты/контакты лишь разрешённые для передачи.
Проверка: два заказчика у одного поставщика и другой поставщик без доступа; документы
и КП одного заказчика не подмешиваются в другой заказ.
Файлы: customer projection/access, список/карточка, интеграционные тесты.

**Контрольная точка2:** реестр и заказы на живых данных, фильтры/счётчики согласованы,
мобильная версия проверена, нет доступа по совпадению названий компаний.

### Этап4. Команда поставщика и ответственные

**P9. Права команды (M; послеP8).** Зафиксировать модель membership компании-поставщика,
руководителя и менеджера, серверную проверку действий и отзыв доступа. Сначала
проверить пригодность существующих таблиц; не использовать membership заказчика.
Проверка: подмена supplier/customer ID, менеджер чужой компании, отозванное членство.
Файлы: supplier team policy/schema (если нужна), API и PostgreSQL тесты.

**P10. Назначение ответственного (M; послеP9/P4).** Руководитель назначает/переназначает,
менеджер видит разрешённые запросы; фильтр менеджера, состояние «Не назначен»,
история назначения. «В работе» не меняет согласование заявки у заказчика.
Проверка: одновременное назначение с конфликтом версий, отзыв роли, смена исполнителя.
Файлы: assignment command, реестр и тесты.

**P11. Управление командой (M; послеP9/P10).** Приглашение, принятие, роль, отключение;
отключённый сотрудник теряет доступ, история сохраняется, запросы не исчезают.
Не терять последнего руководителя и не предоставлять роль по одному email.
Проверка: просроченное/повторное приглашение, отключение активной сессии,
судьба назначенных запросов. Файлы: team API, экран команды и тесты.

### Этап5. Общая сборка кабинета

**P12. Отгрузки и документы в новой навигации (M; послеP7/P8).** Подключить существующие
действия и претензии. Договориться с другим чатом о данных счета/оплаты; не переписывать
его логику. Ошибка загрузки документа не выглядит как отсутствие документов.
Проверка: заказ → частичная отгрузка → приёмка → претензия; права на вложения.
Файлы: supplier workspace, existing fulfilment/document adapters, интеграционные тесты.

**P13. Тариф и профиль (S/M; послеP9/P12).** Подключить только подтверждённые реальные
условия/ограничения поставщика. Надписи «Бесплатно на старте» и коммерческие обещания
со скриншота не вводить без согласованных условий. Профиль использует текущие реквизиты.
Проверка: отсутствие тарифа, доступная роль, совпадение показанных ограничений с сервером.
Файлы: supplier profile/tariff view, существующий billing contract, тесты.

**P14. Финальная приёмка и выпуск (M; послеP1–P13).** Сквозные проверки в двух компаниях
заказчиков с командой поставщика, мобильный экран/клавиатура, независимый review,
резервная копия и проверка после выпуска. Сначала каждый законченный этап может
выходить отдельным обратимым обновлением; не ждать гигантского общего выпуска.
Проверка: PostgreSQL сценарии, RTL, production build, браузер, read-only smoke;
никаких пробных реальных закупок или массовых уведомлений в рабочей базе.

## Условия перед началом соответствующих этапов

- ПередP3 с реальной отправкой: тестовый получатель и явное поручение на сообщение.
- ПередP9–P11: подтвердить предложенную политику менеджеров/самоназначения.
- ПередP13: фактические тарифы, лимиты и полномочия изменения тарифа.
Эти пункты не блокируютP1–P2 и разработку реестра. Не повторять запросы о владельцах
старых склада/шаблона: тот отдельный вопрос остаётся открытым и сюда не относится.

## Готовность и доказательства

Задача отмечается выполненной только после проверки поведения, а не наличия кнопки.
Для каждого выпуска: перечень сценариев и ограничений, результаты тестов, версия,
резервная копия/способ отката и проверка сервера. Миграции — отдельная проверка на копии
базы с сохранением истории; не объединять компании и не назначать владельцев по имени.
Порядок основного пути: P1 → P2 → P3 → P4 → P5 → P6 → P7 → P8 → P9 → P10 → P11 → P12 → P13 → P14.
Следующий рабочий блок: **P2 — ответ поставщика возвращается заказчику**.
