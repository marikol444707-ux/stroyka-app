## Что изменено

Новый POST /supplier-invoices/{id}/legacy-payments принимает companyId, UUID
requestId, сумму отдельной оплаты, expectedPaidAmount и paidAt. Это запись уже
совершённого платежа в учёте; банковских действий нет.

Общий worker в backend/main.py сохраняет существующие проверки владельца,
проектного доступа, графика, приёмки и претензий. Новый путь также проверяет права
на расход проекта, утверждённый статус счёта и точный остаток. Для старого PUT
сохраняется API; проверки не продублированы во второй реализации.

Одна транзакция записывает счёт, связанную накладную, расход объекта и результат
команды. Worker не открывает соединений и не делает commit. Внешняя команда
выполняет один commit либо rollback. Проверка expectedPaidAmount и блокировки
запланированы против конкурирующих изменений; их реальная работа в PostgreSQL
ещё НЕ проверена. Сравнение остатка не используется как идентичность платежа.

Журнал legacy_supplier_payment_requests хранит company/request UUID,
invoice ID, actor ID, SHA-256 нормализованного запроса и полный результат.
Повтор проходит текущую авторизацию; тот же fingerprint возвращает сохранённый
результат без повторных записей, другой payload/документ/автор с тем же ключом
отклоняется. Журнал защищён от UPDATE/DELETE/TRUNCATE. ID документов — исторические
снимки без каскадных FK: существующее удаление/исправление исходных документов
не должно удалять журнал или становиться запрещённым лишь из-за новой таблицы.
После удаления/утраты доступа к счёту повтор не обходит текущую авторизацию.
Сохранённый результат доказывает прежнюю операцию, не текущий баланс после
последующих исправлений.

UI заменяет два запроса одной командой. UUID и исходное тело сохраняются в
localStorage до отправки и очищаются только после подтверждённого ответа и
успешного обновления списка. При потере ответа, конфликте или ошибке обновления
сохраняется та же попытка; новый UUID автоматически не генерируется. Кнопка
«Проверить сохранённую оплату» доступна и для уже оплаченного счёта.
Повторный клик в процессе запроса блокируется; поздний ответ другой компании
не очищает попытку и не запускает обновление текущего списка.

## Обязательная оставшаяся приёмка

1. Применение 0109 на разрешённой синтетической БД через штатный upgrade,
   сохранность старых данных, триггер неизменяемости и отказ downgrade.
2. Реальные commit/rollback и сбой соединения до/после commit; повтор с тем же
   UUID и конкурирующие UUID/старый PUT/складские writers, порядок блокировок.
3. UI разных ролей, refresh/back, две вкладки/устройства, отзыв доступа,
   переключение компании и старые счета с расхождениями связей/остатков.
4. Серверная авторизация и видимость результата между назначенными участниками.
5. Согласованная процедура ручной сверки конфликтной попытки. Автоматического
   сброса pending нет: при конфликте UI сохраняет её и блокирует новую оплату.
   Очистка localStorage пользователем не является отменой серверной операции;
   другое устройство не имеет локальной копии UUID. Это предел клиентского
   восстановления, а не обещание глобальной блокировки новых платежей.

Старый PUT и общий POST /project-payments сохранены для совместимости. Новый
атомарный контракт относится к новой команде и обновлённой кнопке; произвольная
последовательность запросов старых клиентов не становится атомарной автоматически.
Счёт без разрешённого однозначного объекта не проводится этой командой — расход
нельзя молча отнести к объекту по догадке. Требуется корректировка контекста.

До этой приёмки исправление подготовлено локально, но не принято к эксплуатации.
Ни HTTP, SQL, БД, браузер, массовые ролевые/security-прогоны, ни прежний запрещённый
стенд не запускались. Полный аудит не объявляется завершённым.
