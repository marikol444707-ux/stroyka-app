# Инструмент в счёт оплаты: сверка выдачи и ручное распределение

Работа 10.11.2026. Ветка fix/tool-deduction-allocation-20261110.
Исходная финансовая версия 35edf5f / 0115. Для установки включена уже находящаяся
на сервере версия 91abeaa (публичный сайт): она сохранена без изменения её исходников.
Новая миграция 0116_tool_deductions, предшественник 0115_performer_retention.

## Правила, подтверждённые пользователем

Бухгалтер выбирает конкретную выдачу и вручную распределяет подтверждённую стоимость
по актам или месяцам зарплаты. Общая сумма, включая удержанное до нового реестра,
не превышает стоимость выдачи. Старые записи не удерживаются автоматически.
Возврат на склад не меняет деньги. Отмена неоплаченного распределения или фактический
возврат удержанных денег требуют отдельного решения, основания и подтверждения.

## Найдено и исправлено

Пять падающих регрессий воспроизвели вычитание цены карточки из каждого акта/месяца,
вычитание по совпадению ФИО другого сотрудника и другой компании. Теперь акт,
кабинет мастера и печать используют только серверный toolDeductionAmount;
зарплата — подтверждённый снимок конкретного staff/month. Удержание уменьшает
сумму на руки ровно на указанную сумму, не уменьшает начисление для расчёта НДФЛ.
Дополнительный падающий тест подтвердил возможность отдельно сторнировать новый
возврат денег в платежах, оставив возврат удержания в силе. Этот обход закрыт.

| Действие | Результат | Проверка |
|---|---|---|
| Сверить выдачу | Неизменный снимок, точные company/staff/project, стоимость, прежние удержания | HTTP/PostgreSQL, браузер |
| Распределить 1000: акт 600, зарплата 400 | Единый остаток 0; сверх лимита отказ | HTTP/PostgreSQL, браузер |
| Две вкладки | Первый ответ сохранён, второй 409; ввод не теряется, автоповтора нет | PostgreSQL с конкурентными запросами, две браузерные вкладки, React |
| Оплатить акт 10000 с удержанием 600 | Денежная оплата 9400, остаток 0, статус оплачен | API, реальное окно оплаты, SQL |
| Выплатить зарплату 10000 с удержанием 400 | При существующей формуле НДФЛ сумма на руки 8300 | API, реальный зарплатный компонент, SQL |
| Подтвердить возврат 600 | Отдельное событие и денежная запись; акт: cash10000, tool0 | API, браузер, перезагрузка, SQL |
| Физически вернуть инструмент | Распределение и деньги не меняются | Изменение складской карточки в тестовой БД и проверка реестра |
| Старый клиент без снимка зарплаты | 409, выплата не создана | HTTP/PostgreSQL и браузерный API |
| Изменить цену/название карточки | Подтверждённая стоимость и название выдачи сохраняются | PostgreSQL |
| Сторнировать денежный возврат отдельно | 409 без новой денежной операции | Регрессионный тест обработчика |

## Архитектура и границы

Новый реестр: tool_deduction_sources, tool_deduction_allocations,
tool_deduction_events. Источник подтверждается один раз; операции используют
expectedRevision, транзакцию и общий ledger lock с авансами/оплатами. Никаких
финансовых сумм из ФИО или текущей цены инструмента. tools.master_id — user ID,
interim_acts.master_id — staff ID: при наличии user ID проверяется точная активная
связь user_company_roles.staff_id. Без старого ID бухгалтер явно выбирает сотрудника
после документальной сверки. Объект не может принадлежать другой компании.

Акты учитывают аванс, гарантию, инструмент и денежную оплату совместно. После денег
распределение не переписывается; возврат создаёт отдельную запись project_payments,
не банковский перевод. Сумма возвращённого удержания не становится доступной для
повторного удержания. Выплата зарплаты хранит снимок; повтор месяца, изменение
удержаний после выплаты и удаление выплаты с удержанием отклоняются.
События защищены от UPDATE/DELETE; составные внешние ключи защищают компании;
денежный возврат связан внешним ключом с событием. SQL-триггеры защищают акт и
зарплатный снимок от обхода старым обработчиком. Общий лимит распределения защищён
транзакционным сервисом; произвольный прямой SQL не является разрешённым API.

## Переход и установка

Старый JS зарплатной формы игнорирует HTTP-ошибки. Новый сервер отклоняет запрос
без expectedToolState и ничего не записывает, но уже загруженный старый JS может
сам показать старое сообщение об успехе. Обновление нового frontend не исправит
код в открытой вкладке. Нельзя допускать такую форму к дальнейшей работе.

1. До переключения пользователи сохраняют работу; незаписанные черновики отдельно
   копируют и проверяют. Старые формы закрывают только после сохранения.
2. Подготовить точный пакет поверх актуального server HEAD, сверить его хеши и флаги;
   не заменять незакоммиченные или посторонние серверные файлы.
3. На время переключения закрыть запросы maintenance-режимом, остановить backend
   и фоновые писатели. Сохранить текущие публичные файлы и manifest-ресурсы frontend,
   Git HEAD, настройки nginx, файлы пользователей и согласованный pg_dump.
4. Восстановить dump в отдельную тестовую БД, сравнить бизнес-таблицы, применить
   0116 и запустить полный backend с запретом внешних подключений. Повторить сравнение.
5. Только после успешной репетиции применить 0116 на рабочем сервере и согласованно
   переключить backend/frontend. Миграция не распределяет ни одного старого удержания.
6. Сверить прежние бизнес-поля (исключая только новые колонки), backend/DB, все
   публичные файлы и выбранные feature flags; войти в кабинет, открыть сверку
   инструмента и зарплату, проверить сетевые ответы/отображение/перезагрузку.
   Финансовые тестовые записи на production не создавать.
7. После всех четырёх проверок записать verified.json/deployed.json; удалить резерв
   и staging по docs/deployment-retention.md, оставить маленькую квитанцию выпуска.

Откат: до завершения проверок резерв остаётся. При ошибке оставить maintenance,
сохранить журналы и исправлять вперёд. downgrade 0116 намеренно запрещён: это
финансовая история. Если новых операций ещё не было, возможно согласованное
возвращение к предыдущему коду и его frontend с сохранением добавочной схемы, но
финансовые формы нельзя открывать, пока не проверены ограничения и старое поведение.
После появления распределений/возвратов простой откат на старый frontend небезопасен.
Восстановление рабочей БД из dump — отдельное решение после сверки новых операций,
не автоматический шаг и не разрешение потерять данные.

## Ограничения и непроверенное

- Старые удержания без точного источника платежа не переписываются и не возвращаются
  автоматически. Бухгалтер сверяет их до новых выплат; история старых актов могла
  иметь недостоверный интерфейсный вычет, который сервер ранее не сохранял.
- Исправление ошибочно подтверждённого получателя/стоимости и возврат неприкреплённых
  старых удержаний — отдельная процедура; здесь они намеренно не угадываются.
- tool_custody/tool_fine_allocations (поломка, утрата, договорные v2-акты) не смешиваются
  с покупкой «в счёт зарплаты». Распределение покупки реализовано для legacy interim
  acts и staff/month; v2-акты не поддерживаются этим реестром.
- Складской lifecycle в этом блоке не переписан. Проверено отсутствие финансового
  эффекта изменения карточки; полный физический цикл всех custody-ролей не повторён.
- Общий налоговый/зарплатный движок, частичные выплаты месяца и банк-интеграция не
  добавлялись. Существующие ставки/локальные корректировки зарплаты не пересмотрены.
- Реальный браузер проверял импортированные рабочие компоненты с настоящими HTTP
  и PostgreSQL на изолированном стенде. Production-проверка отдельно фиксируется
  после установки; успешный API сам по себе не заменяет её.
- Предупреждения окружения: устаревшая caniuse-lite, Node fs.F_OK, websockets legacy.
  В первой локальной браузерной обвязке отсутствовал favicon (404); ошибок React нет.

## Уточнение после проверки установки

Первые внешние проверки обнаружили, что nginx не направлял новые пути
/tool-deductions и /salary-tool-deductions в backend: вместо JSON приходил HTML
страницы с HTTP200. Поэтому установка не объявлялась завершённой, резерв сохранён.
Добавлены scripts/ensure_tool_deduction_nginx_routes.py и
scripts/test_tool_deduction_nginx_routes.py: три точных location, сохранение прочего
конфига, резерв до записи, идемпотентность и отказ при конфликте/дрейфе. 3 теста
прошли. Перед завершением установки обязательны применение helper к активному
конфигу, nginx -t, reload, повторная проверка JSON/401 и браузера. Добавлять маршруты
нужно до открытия новых форм; текущие API-пути не заменяются широким catch-all.
Исходный результат отказа проверки сохранён в public-first-failure.log.
