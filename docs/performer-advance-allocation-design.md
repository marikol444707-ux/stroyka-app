## Утверждённые правила и поведение

Пользователь подтвердил разделение подотчёта и зарплатного аванса и ручное
распределение бухгалтером по пакетам. Пропорционального распределения нет.

1. При выдаче выбирают «Подотчёт на расходы» или «Зарплатный аванс».
   Исторические выдачи получают `unclassified`, без угадывания по назначению.
2. В «Бухгалтерия → Закрытие → Подотчёт и зарплатные авансы» бухгалтер проверяет
   тип старой выдачи. Выдачу с отчётами/расходами нельзя превратить в зарплатную.
3. Для зарплатного аванса выбирают сохранённый акт конкретного пакета и полную
   сумму зачёта этой выдачи в акт. Например: 10 000 ₽ → 6 000 ₽ отделка + 4 000 ₽ электрика.
   Повторное сохранение заменяет долю, а не прибавляет её. Незачтённый остаток виден отдельно.
4. Зачёт хранится на сервере, доступен после обновления/на другом устройстве.
   Дата выдачи может предшествовать месяцу акта. Зачёт не создаёт второй платёж.
5. До денежной оплаты сумму можно изменить, ноль отменяет зачёт. После денежной
   оплаты изменение блокируется. При полной отмене возвращается предыдущий статус акта.
6. Остаток акта = начислено − реальные денежные оплаты − сохранённый зачёт.
   Подотчёт, неизвестный тип и нераспределённая часть аванса не уменьшают оплату работ.
7. Конфликт ревизии возвращает 409; форма сохраняет ввод и не повторяет запись.
   После ручного обновления бухгалтер сверяет суммы и явно принимает загруженную ревизию.

## Что исправлено

Первоначальный RED: две группы по 200 ₽, одна выдача 100 ₽ давала общий вычет
200 ₽. Сохранён источник воспроизведения. Теперь закрытие использует зачёты актов,
а не повторяет всю выдачу в каждом пакете. Дополнительный RED: зачёт 0,15 ₽
показывался как 0 ₽ из-за округления. Закрытие теперь отображает копейки.

Миграция **0114_performer_advances**, родитель **0113_warehouse_transfer_drafts**:
тип и ревизия выдачи, таблица зачётов, журнал изменений, прежний статус акта,
составные внешние ключи владельца и защитные триггеры. Исторические выдачи не
классифицируются автоматически. Программного downgrade нет: он явно отказывается
удалять финансовую историю.

Проверка ревизии, лимитов и запись выполняются одной транзакцией. Runtime выдаёт
соединения с autocommit=True, поэтому писатели явно включают транзакцию; тесты
повторяют этот режим. Зачёты, классификация, отчёты о расходах и изменения актов
согласованы блокировкой. Денежные суммы зачёта/оплаты проверяются через Decimal.
Обычный PUT/DELETE акта не обходит зачёт; триггер защищает и старый SQL-путь.
Сервер проверяет компанию, ID сотрудника, объект и пакет. Одноимённые объекты внутри
компании требуют сверки: старый акт хранит имя проекта, поэтому угадывать ID нельзя.

## Ограничения и непроверенное

- Расчёты v2 с материалами и дневные контрольные акты не поддерживают этот
  зачёт; сервер отказывает. Доли не привязываются к несохранённому пакету.
- После денежной оплаты нет переноса зачёта/сторно/возврата. Нужен отдельный
  согласованный финансовый процесс; ручное изменение БД запрещено.
- Старые акты без точной компании/сотрудника, неоднозначное имя объекта и
  исторические денежные значения с долями меньше копейки требуют сверки.
  Мастер без подтверждённого staffId получит понятный 403, без подбора по ФИО.
  Для API актов выбирается одна компания, общий режим компаний не поддержан.
- Старые 5% гарантийного удержания и удержания за инструмент остаются отдельными
  расчётами интерфейса, не новым серверным реестром удержаний. Максимум оплаты
  на сервере равен сумме акта минус cash и advance. Для таких удержаний нельзя
  обещать равенство всех экранов. Их унификация в этот блок не входила.
- Зачёт хранится по акту целиком; закрытие месяца показывает акты с точно
  совпадающими границами месяца. Произвольный многомесячный акт не распределяется
  автоматически между месяцами; его остаток проверяется в «Актах».
- Журнал зачётов хранит автора/ревизию, но отдельного экрана аудита и DB-запрета
  административного UPDATE журнала нет. Через API изменения истории не предоставлены.
- Глобальная advisory-блокировка сериализует операции даже разных компаний;
  нагрузочный тест большого числа бухгалтеров не проводился.
- Создание выдачи и старый endpoint оплаты не получили общего idempotency key.
  При потере ответа на создание/частичную оплату сначала сверять список, не повторять
  запрос вслепую. Ревизия и абсолютная сумма защищают именно операции зачёта.
- В браузере проверены Closing/Acts на HTTP/PG-стенде. Полный production-вход всех
  ролей, другие устройства физически, мобильная вёрстка и все остальные связанные
  экраны не проверялись браузером. Изменённые расчёты покрыты указанными unit-тестами
  и сборкой; успешный API не считается доказательством всех этих UI-сценариев.
- Полный startup использует синтетическую предыдущую схему; это не восстановление
  свежей production-копии. Совместимость фактической схемы/новых изменений сервера
  нужно проверить перед установкой. Зависимости проекта не обновлялись.

## Согласованная установка и откат (ещё не выполнены)

Предоставленные пользователем правила AGENTS.md: «Never ... apply production
migrations automatically». Разрешение на 0113 не является разрешением на новую
0114. Нужна отдельная команда на эту установку после ознакомления с отчётом.

1. Сверить фактические HEAD, локальные изменения сервера, Alembic=0113 и схему
   ownership (A11: company_id, company_scope_verified и связи). Ничего не
   перетирать при расхождении. Проверить свежий резерв восстановлением в отдельную БД.
2. Объявить окно. Каждый пользователь сохраняет и проверяет отдельные копии
   незаписанных черновиков **до закрытия старых вкладок**. Старый frontend не умеет
   обработать обязательный paymentKind и мог сообщить ложный успех; новый bundle
   сам по себе уже открытые вкладки не исправляет. Подтвердить сохранность и закрытие.
3. На время переключения остановить приём записей/приложение. Резерв БД и только
   текущего frontend manifest/public, текущий backend/конфигурация без вывода секретов.
   Не делать полный Git bundle и не сохранять старые static chunks.
4. Установить согласованный backend/frontend из проверенного пакета. В штатном
   окружении сервиса выполнить `python -m alembic upgrade 0114_performer_advances`.
   Не запускать старые worker-процессы на новой схеме. Миграция и смена кода — в одном окне.
5. До открытия доступа проверить: полный startup/health и новые маршруты; версия
   0114/constraints/triggers, сохранность прежних сумм и неизвестный тип legacy;
   hashes всех файлов manifest и feature flags; реальный браузер бухгалтера,
   директора/заместителя и мастера (точные права, чтение существующих данных).
   Финансовые действия проверять только в отдельно разрешённой тестовой компании,
   не создавать пробные платежи в рабочих объектах.
6. Для приёмки воспроизвести 6000+4000, вторую вкладку/409, обновление страницы,
   остатки, расходы и изоляцию. Не считать health достаточным. При отсутствии
   браузерной/DB-проверки оставить выпуск незавершённым и сохранить резерв.
7. Только после четырёх фактических проверок backend/database/frontend/browser
   записать matching-head verified.json со всеми true, затем deployed.json;
   завершить очистку по docs/deployment-retention.md. До этого резервы сохраняются.

Откат: downgrade 0114 запрещён самим файлом миграции. До допуска пользователей и
новых записей можно вернуть согласованный старый backend/frontend вместе с
проверенным предустановочным резервом БД в закрытом окне. После новых финансовых
записей восстановление старого резерва потеряет операции: его не применять.
Оставить 0114 и выпуск, совместимый с ledger, закрыть записи и подготовить forward-fix
со сверкой истории. Откат только frontend или только backend недопустим. Триггеры
не заменяют совместимый интерфейс и не разрешают игнорировать сохранённые доли.
