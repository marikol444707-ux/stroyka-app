## Подтверждённая проблема и исправление

Возврат сохранялся только в памяти открытой формы. Закрытие страницы или переход на другое
устройство теряли количество и основание; серверного API такого черновика не было.
До реализации три PostgreSQL-теста получили 404, два frontend-теста не смогли сохранить/восстановить ввод.

Добавлены личные серверные черновики возврата, отдельно от черновиков выдачи. Ключ — пользователь
и компания; доступ проверяется сервером по действующему членству и роли. Сохраняются точный ID
исходного распределения, количество строкой (в том числе незавершённое `1.`), основание и ревизия.
Серверные данные доступны на другом устройстве под тем же пользователем в той же компании.
Флажок физического подтверждения **не хранится**: после восстановления его нужно отметить заново.

GET/PUT `/warehouse-distributions/return-draft` используют существующие авторизацию и транзакции.
PUT содержит `expectedRevision` и UUID сохранения; проверка ревизии и запись выполняются атомарно.
Конфликт даёт 409 и сохраняет локальный ввод; автоматической перезаписи новой ревизии нет.
При неизвестном результате сохранения повторяется исходный UUID/снимок, затем сохраняются новые правки.

POST возврата передаёт `X-Warehouse-Return-Draft-Revision`. Сервер сверяет ревизию, точное распределение
и нормализованное содержимое. Существующая складская команда выполняет возврат; очистка черновика
и сохранение ID результата происходят в той же транзакции. Ошибка остатков оставляет черновик.
Повтор проведённой команды проверяется прежней идемпотентностью и не очищает следующий черновик.
Тело команды и его хеш не менялись. Исходная партия/накладная выбираются существующей серверной
логикой по распределению, без поиска по названию и без предположений о физической принадлежности.

Общий транспорт черновиков вынесен из `useWarehouseBatchDraft` в `useWarehouseDraft`, чтобы не
дублировать защиту ревизии, сессии, восстановления при переходе и предупреждение о закрытии вкладки.
Ключ временного буфера дополнительно содержит тип черновика. Выдача и возврат не перезаписывают друг друга.
Форма восстанавливается автоматически; провести её можно только после загрузки актуального
распределения в истории и нового физического подтверждения. Отмена очищает личный черновик через CAS.

синтетическая, серверный resolver ролей настоящий, сметная аннотация подменена. Оригиналы накладных
и другая компания не изменились. Результат виден в истории, а связанные остатки сверены SQL;
отдельные страницы каждого объекта и браузер каждой роли в этом блоке не обходились.
Это не доказательство сквозной работы всех кабинетов на рабочем сервере.

## Установка и совместимость

1. Пакет подготовлен, но новая production-миграция требует отдельной команды пользователя
   по переданным правилам AGENTS. До неё миграция существует только как файл/в тестовой БД.
2. Перед обновлением сохранить отдельные копии незавершённых старых форм возврата и проверить их.
   Неподтверждённые операции сверить с историей; не создавать новую команду с другим UUID наугад.
   Только после сохранения копий закрыть старые вкладки. Новая версия не может выгрузить ввод из чужих старых вкладок.
3. Сверить серверный HEAD с базой пакета, схему 0111, незакоммиченные изменения и действующие флаги.
   Снять резерв БД/uploads и только текущих frontend-ресурсов по manifest/public, без исторических чанков
   и полного Git bundle. Восстановить резерв отдельно, проверить миграцию 0112 и полный запуск.
4. Под maintenance/deployment lock остановить запись, применить `.venv/bin/python -m alembic upgrade
   0112_warehouse_return_drafts`, согласованно обновить backend/frontend. Не использовать stamp вместо миграции.
5. До миграции новый API отдаёт 503. Старый POST без заголовка остаётся совместимым, но не потребляет
   серверный черновик возврата. Смешивать действующие старые/новые формы нельзя. Новая форма всегда передаёт ревизию.
6. После установки отдельно проверить backend, БД/сохранность прежних записей, хеши frontend и браузерный
   путь директора «Склад → Перемещение». Не проводить тестовые складские операции в рабочей базе.
7. Только после четырёх PASS создать `verified.json` с точным установленным HEAD, затем `deployed.json`;
   удалить резерв/staging по `docs/deployment-retention.md`. При незавершённой проверке сохранить резерв.

## Откат и ограничения

- Downgrade запрещён: автоматическое удаление таблицы потеряло бы черновики. При проблеме остановить
  складскую запись (`WAREHOUSE_DISTRIBUTION_ENABLED=0`), сохранить данные и диагностику; предпочтительно
  исправление вперёд. Для отката к предыдущему коду сохранить таблицу/файл миграции и не понижать stamp.
  До сверки проведённых операций с черновиками старый интерфейс записи не включать.
- Один личный черновик возврата на компанию. Слияния конфликтов, push-обновлений и импорта JSON-копии нет.
- Между устройствами переносится только подтверждённый сервером ввод. При принудительном завершении
  браузера до подтверждения последние символы могут потеряться; предупреждение beforeunload не гарантируется ОС.
- Для нового возврата нужен актуальный источник из истории. Если он скрыт фильтром/пагинацией, форму
  можно сохранить, но перед проведением нужно загрузить распределение. Изменившиеся права/остатки
  сервер проверяет повторно; сохранение черновика ничего не резервирует.
- Не проверены: установка 0112 на сервер, свежий production backup, реальная cookie-сессия после установки,
  мобильные Safari/Android, аварийное завершение ОС. Независимый агентский аудит не выполнялся.
  Итоговые локальные проверки проходят; эти ограничения не объявляются пройденными проверками.
