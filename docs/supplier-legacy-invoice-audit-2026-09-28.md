# Сверка старых счетов — первый этап

Добавлена операторская проверка `scripts/audit_supplier_legacy_invoices.py`.
Это инвентаризация признаков исходных данных, а не разрешение на миграцию,
платёж или приёмку. API и интерфейс пользователей не меняются.

Запуск из корня проекта с доступом PostgreSQL через стандартные переменные
`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` (или `.pgpass`):

```sh
python scripts/audit_supplier_legacy_invoices.py --company-id 2
```

ID компании нужно указывать явно. Не передавайте пароль в командной строке.
Нужна схема как минимум 0050. Отсутствующая схема завершит проверку ошибкой,
а не пустым «успешным» отчётом.

Один согласованный снимок REPEATABLE READ, транзакция READ ONLY, затем rollback.
Отчёт выводит только счета выбранной компании, суммы и признаки:

- `missingOriginalLineEvidence`: нет сохранённых исходных строк счёта;
- `legacyReceiptLink`: есть старая прямая/обратная связь с накладной;
- `historicalPaymentWithoutLedger`: ненулевая оплата без регистрации в журнале;
- `invalidOrMissingPaidAmount`: сумма оплаты отсутствует или некорректна.

`sealed` означает только наличие исходных строк и отсутствие перечисленных
признаков. Это не проверка всех договоров, полномочий, остатков или проводок.
`admissionGranted` всегда false. Отчёт нельзя использовать как разрешение
на автоматическое заполнение строк задним числом или повторное создание долга.
Операторский доступ к БД не заменяет права пользователей; публичного маршрута нет.

Следующий этап: на основании отчёта согласовать отдельные сценарии старых
счетов и накладных, затем реализовать подтверждённую сверку с неизменяемыми
доказательствами. Текущий механизм новых строк требует их создания вместе
со счётом; обходить эту защиту для исторических данных нельзя.

Проверки: изолированные PostgreSQL-тесты для нового счёта, старого оплаченного,
границ компаний и запрета неверного контекста транзакции. Реальные исторические
данные и сервер этим изменением не затронуты.
