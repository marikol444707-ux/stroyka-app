# JEVA: автономная QA-проверка без оператора

## Что уже автоматизировано

После отдельной приёмки и ручного включения systemd сможет запускать **только read-only smoke** через локальный
QA worker на `127.0.0.1:18088`. Worker открывает
`https://stroyka-qa-gateway/app` и проверяет наличие меню `Склад`.
В scheduled read-only режиме цикл действий Jev (`agent.run()`) вообще не
запускается: доступны только наблюдение DOM/URL и детерминированная проверка.
Тест считается успешным только при проверках
`read_only_observation`, `expect_text[0]:present`,
`expect_url_contains[0]:present` и отсутствии ошибок/boundary violations.

Это **не** полноценный автономный тест перемещения. Он отдельно потребует
изолированных тестовых данных, подтверждения тела запроса, проверки БД и
семантики ожидаемого отказа. Не следует засчитывать `failed` как PASS
только потому, что HTTP 400 и БД не изменилась.

## Что система НЕ делает

- Не открывает production и не запускает миграции/деплой.
- Не получает доступ к Docker socket, БД, SSH, сессии пользователя или ключу Timeweb.
- Не обновляет автоматически образы JEVA.
- Не публикует скриншоты, введённые значения, секреты или сырые ошибки модели.
- Не отправляет уведомления без отдельного токена GitHub.
- Не запускает несколько браузерных задач одновременно (worker имеет очередь).

## Обязательная read-only проверка QA-хоста перед установкой

На существующем `stroyka-dev-agent` сначала выполнить из проверенного
checkout ветки PR **только**:

```bash
python3 scripts/jev_qa_host_preflight.py
```

Скрипт ничего не устанавливает, не вызывает worker HTTP API, не читает
токены, не останавливает контейнеры и не меняет сервер. Ему нужен только
доступ к метаданным Docker. Результат `blocked` запрещает переход к
установке. `review_required` **не означает готовность**, а подтверждает
только отсутствие перечисленных конфликтов в инвентаризации.

Особенно проверить владельца порта 18088. Ранее на сервере этот порт
использовал экспериментальный `stroyka-jev-dialog-test`, тогда как
watcher ожидает основной `stroyka-jev-qa`. Прежнюю конфигурацию не
считать актуальной без повторной проверки. Запретить публичный bind
Jev API, привилегированные контейнеры и `seccomp=unconfined` на
предполагаемой QA-среде.

Даже после чистого preflight **не включать авторизованный scheduled watcher**
до исправления #345 (write-on-GET в supply history) и #346
(серверно подтверждённое восстановление пользовательской сессии).
Независимые security review и live QA tenant-verifier остаются
обязательными воротами приёмки. Никаких production deploy/migrations.

## Однократная установка (только после review и проверки PR)

На QA-сервере, из проверенной версии репозитория:

```bash
sudo bash scripts/install_jev_qa_watch.sh
```

Установщик не изменяет Docker-контейнеры, Caddy и production. Под `root`
он однократно читает сильный `DEV_CONTROL_API_TOKEN` из
`/etc/stroyka-jev-qa.env`, выводит из него односторонний scoped
`JEV_WATCHER_TOKEN` и записывает в `/etc/stroyka-jev-watch.env`
**только scoped read-only credential** и порт 18088. Общий worker-token,
ключ Timeweb и QA session туда не копируются.

Watcher подписывает каждый запрос к фиксированным `/watcher/*` endpoint'ам
HMAC по method/path/timestamp/nonce/body hash. Сервер сам формирует
фиксированный read-only smoke; scoped credential не авторизует общий
`/jobs`. Сам watcher выполняется под пользователем `stroyka`, а не root.

```bash
systemctl is-active stroyka-jev-watch.timer
systemctl is-enabled stroyka-jev-watch.timer

# Пока не закрыты #345 и #346, статус должен быть inactive/disabled.
# НЕ запускать service, НЕ включать timer до отдельного release gate.
```

Установщик **только размещает файлы**: таймер не запускается и не
включается автоматически. Если он уже активен или включён, установщик
откажется продолжать до ручного аудита. После отдельного разрешения
владельца и закрытия блокировок расписание может быть включено:
08:00 по часовому поясу сервера с разбросом до 15 минут.
Текущий PR не разрешает включать его.

При неуспехе watcher возвращает код 1 и фиксирует только категорию ошибки
в `/var/lib/stroyka-jev-watch/last.json`. Подробности доступны в
защищённом worker evidence (TTL ограничен). Для диагностики:

```bash
sudo journalctl -u stroyka-jev-watch.service -n 30 --no-pager
```

## Уведомления в GitHub (необязательно)

Для автоматического комментария в задаче #311 нужен отдельный
**fine-grained GitHub token** только с разрешением `Issues: Read and write`
для репозитория `marikol444707-ux/stroyka-app`.
Добавить его как `JEV_WATCH_GITHUB_TOKEN=...` в
`/etc/stroyka-jev-watch.env` (не в репозиторий, не в goal, не в логи).
Токен хранится на сервере, `root:stroyka`, mode 0640.
Без него отчёт остаётся локальным, поэтому удалённые уведомления пока
не гарантируются.

Watcher отправляет **только** UTC-время, идентификатор задания,
результат, коды проверок и обобщённые категории ошибок. Запрос идёт
только на фиксированный endpoint GitHub issue #311.

## Перед полноценной автономией

1. Закрепить Caddy static QA route в постоянном конфиге (текущий reload временный).
2. Заменить краткосрочный Chrome SPKI pin на доверие к QA CA.
3. Убедиться, что на сервере активен только один QA worker, не множество
   экспериментальных Chrome.
4. Провести несколько последовательных успешных read-only smoke.
5. Отдельно разработать сценарии склад/снабжение/проекты с детерминированными
   проверками и тестовой ролью, не имеющей доступа к production.

Откат автоматизации: `sudo systemctl disable --now stroyka-jev-watch.timer`.
Это не удаляет worker и не затрагивает приложение.

## Автоматическое восстановление временных сетевых сбоев

Watcher самостоятельно повторяет чтение состояния `/watcher/health` и
`/watcher/jobs/{id}`: до трёх попыток с паузами 1 и 2 секунды.
Повторяются только временная недоступность, таймаут соединения и HTTP
429/502/503/504. Запросы создания задания и отмены вслепую не повторяются.
Потеря ответа создания не означает, что задание не было создано:
отчёт получает `JOB_CREATION_UNCONFIRMED` и `job_status=unknown`, а не
ложное утверждение, что запуск не начинался.

Восстановление и наблюдение используют общий срок 120 секунд; после его
окончания watcher пытается отменить известное задание. Если чтение состояния
не восстановилось за три попытки, также отправляется одна отмена этого же
задания. При неудаче отмены сохраняется отдельный код ошибки.
Отказы HTTP 400/401/403/404, неверная подпись ответа, неправильная QA-среда
и непроверенный результат не считаются временным сбоем и не обходятся.

Этот механизм не устанавливает worker, не включает таймер, не меняет
сетевые ограничения и не разрешает действия в приложении. Текущий scheduled
сценарий по-прежнему ограничен входом и меню с `data_status=NOT_TESTED`.
До полноценной автономной приёмки остаются QA runtime, отдельные разрешённые
сценарии действий и независимая проверка их бизнес-результата по #311.

## Ограниченная проверка входа и меню (bootstrap_only)

Авторизованный `read_only` запуск теперь проверяет **только восстановление
тестовой сессии и настоящее меню приложения**, а не загрузку складских или
проектных данных. Это промежуточная проверка перед полноценным QA; она не
закрывает #344/#345/#346 и не разрешает включать таймер.

- В новом BrowserContext cookie остаётся HttpOnly/Secure. Public user берётся
  только из проверенного GET `/api/users/qa-readonly-context/identity`.
- Только поля `id`, `companyId`, `role`, `name`, `email` попадают в
  `localStorage.user` этого временного контекста. Токены не сохраняются.
- Приложение повторно открывается в том же контексте; серверная личность
  проверяется ещё раз и должна совпасть. Роль или компания не подменяются.
- До первого открытия страницы действует положительный сетевой список:
  `/app`, файлы `/static/js|css|media/`, явно перечисленные favicon/manifest/
  logo и точный identity GET. Все остальные backend GET, в том числе пути
  без `/api`, прерываются **до отправки**. Фальшивых JSON-ответов нет.
- Сетевые ошибки исключённых запросов данных учитываются отдельно; внешние
  запросы, непредусмотренные записи и диалоги по-прежнему завершают проверку
  ошибкой. Interception не отключается до уничтожения BrowserContext, чтобы
  не возобновить запросы, оставшиеся в очереди при завершении.
- Требуется `.app-authenticated-shell` и видимая настоящая кнопка
  `button[aria-label="Склад"]`. Текст «Склад» на публичной странице не PASS.
  Если у серверной роли нет этого меню, тест честно не проходит; менять роль
  ради результата нельзя. У прораба меню зависит от inventory build flag.

В `result.json`, ответе watcher и Jev Live явно показываются
`scope=bootstrap_only`, `data_status=NOT_TESTED` и число заблокированных
запросов данных. Скриншот показывает состояние оболочки с недоступными API,
а не успешную загрузку/проверку склада. Успех этого сценария не является
приёмкой бизнес-функций или автономных действий модели Jev.

Перед реальным запуском отдельно проверить точный QA SHA, sandbox, сессию,
что `/app` и разрешённые static paths обслуживаются как статические файлы,
а identity URL проксируется на новый QA backend с read-only маршрутом.
Сам по себе положительный сетевой список не доказывает конфигурацию VPS.
Никаких новых ключей, флагов frontend, мостов или изменений production для
этого локального исправления не требуется.

### Проверка совместимости с изоляцией служебного доступа

Identity-маршрут внесён в точный перечень альтернативной аутентификации после
проверки его QA-only/cookie-only границы. Исходная роль пользователя также
должна быть одной из разрешённых ролей компании: пройденная 2FA и оставшееся
членство не превращают platform/support/account/supplier-пользователя в
пользователя компании. Известный platform_account_id пользователя должен
совпадать с аккаунтом выбранного членства; прежний NULL остаётся допустимым.
Эти проверки выполняются внутри read-only resolver до выдачи public user;
внутренние поля глобальной роли/аккаунта не попадают в UI-проекцию.
