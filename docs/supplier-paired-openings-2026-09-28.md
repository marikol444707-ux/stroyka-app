# Начальный остаток старой пары счёт–накладная

Локальный этап: API, неизменяемое подтверждение и существующий интерфейс сверки.
Рабочие данные не переносились, выпуска на производственный сервер нет.

## Область поддержки

Только одна взаимно связанная старая пара без зарегистрированных документов
журнала и без новых исходных строк счёта. Компания, плательщик, поставщик,
объект, пакет работ, полная и оплаченная суммы должны совпадать. Счёт и накладная
должны быть допущены к оплате существующей финансовой политикой.

Предпросмотр включает `warehouseId`; интерфейс показывает номер накладной и
поясняет, что прежняя оплата не суммируется. Хеш сверки включает полные снимки
обоих документов, поэтому изменение любого из них потребует повторной сверки.

Подтверждение в одной транзакции создаёт исходные записи двух физических
документов и одно доказательство сверки. Для накладной сохраняется её отдельный
снимок и ссылка на запись журнала. Денежных операций, расходов, складских
движений, новых связей и строк НДС не создаётся.

Пара сохраняет прежний платёжный механизм: один реальный платёж, отражённый
в обоих физических документах. Начальный остаток и обязательство не складывают
между счётом и накладной. Пример: 200/оплачено 50 в обоих документах → долг 150;
после одной доплаты 20 оба показывают оплачено 70 и долг 130. Сторно доплаты
восстанавливает оплачено 50 в обоих документах.

## Включение

Миграция `0058_supplier_paired_openings` после 0057 и дополнительный серверный
флаг `SUPPLIER_PAIRED_OPENINGS_ENABLED=1`. Также нужны прежние флаги подтверждения
остатков и платёжного журнала, а для UI — соответствующие сборочные флаги.
По умолчанию новый сценарий выключен. Replay уже подтверждённой пары сохраняется
при выключении флага пар, пока основной сервис подтверждений включён.

0058 сохраняет прежнее определение ограничения и восстанавливает его при откате.
Пустой upgrade/downgrade/upgrade проверен. При наличии подтверждённой пары downgrade
запрещён, чтобы не потерять доказательство накладной. Обхода защит 0057 нет:
одиночный счёт по-прежнему не может иметь незаявленную накладную.

## Проверки

- 17 PostgreSQL/HTTP-тестов на схеме 0058, включая прежние сценарии 0057,
  доплату/сторно пары, несовпадение сумм, одностороннюю связь, устаревший снимок,
  полный откат обеих регистраций при повреждённом доказательстве и защиту downgrade.
- 11 PostgreSQL/HTTP-тестов отдельного счёта на прежней схеме 0057.
- 16 frontend-тестов сверки, включая проверку номера накладной в ответе.
- Реальный Chromium + локальный API + одноразовый PostgreSQL: предпросмотр пары,
  подтверждение с намеренной потерей ответа после commit, перезагрузка, точный
  повтор и доплата 20. Проверены одна запись подтверждения, один платёж и
  paid_amount=70 в счёте и накладной. Осмотрена мобильная форма 390×844.
- Сборка интерфейса с включёнными флагами.

Предупреждение старой тестовой фикстуры об `api_errors.owner_scope` относится
к её журналированию ошибок; перечисленные финансовые проверки проходят.

## Что не исправляется автоматически

Расхождения сумм/поставщика/пакета, несколько накладных, односторонние ссылки,
уже зарегистрированная только одна сторона и отсутствующие суммы требуют
отдельной сверки. Данные не выравниваются и ссылки не восстанавливаются по догадке.
Исторические строки материалов/НДС не реконструируются. Возвраты и корректировки
с распределением по частичным поставкам остаются следующим финансовым этапом.
