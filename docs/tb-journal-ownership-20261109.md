## Подтверждённые ошибки

- API журнала выбирал и удалял записи по названию объекта без сохранённого владельца. Записи чужой компании попадали также в профиль одноимённого сотрудника. Проверено для компаний одного владельца платформы — это не разрешает общий доступ к архивам.
- Неудачный POST создавал локальную запись, а форма закрывалась как после успеха.
- Поздняя генерация ИИ могла заменить новый текст; ответ сохранения мог закрыть уже другую форму.
- Список, счётчик журналов, ЖПР и комплект исполнительной документации отбирали инструктажи по названию объекта.
- Реальная проверка в браузере обнаружила, что печать подставляла стандартный инструктаж вместо сохранённого текста, теряя программу и имя инструктора.

## Исправление

Миграция `0110_tb_journal_owner` следует за 0109: nullable `company_id`, `project_id`, `created_by_user_id`, проверка полноты пары владельца, составной FK на `projects(id,company_id)` и индекс. Исторические строки остаются без владельца и недоступны через API. Автоматического присвоения по названию нет. Downgrade запрещён, чтобы не уничтожить подтверждённую принадлежность.

CRUD использует существующий `RecordScope`: актуальное членство в выбранной компании, разрешённую роль и точный объект. POST возвращает полную подтверждённую запись. Подставленный companyId/createdByUserId не определяет владельца. Чужой или бесхозный ID при удалении даёт 404. ИИ проверяет доступ до обращения к существующему model gateway; путь провайдера и ограничения gateway не менялись.

Frontend добавляет запись только по успешному подтверждённому ответу, проверяет projectId/companyId, обновляет список функционально. Ошибка оставляет форму и текст. Сессия открытия и снимок формы защищают от поздних ответов; повторное нажатие во время текущего сохранения заблокировано. Старый ответ не закрывает новую форму и не показывает в ней старую ошибку. Списки и связанные счётчики используют точные ID. Печать использует сохранённые текст, программу и инструктора, экранирует пользовательские поля; стандартный текст остаётся только для записи без собственного текста.

## Ограничения и отсутствующие связи

- Участники хранятся как строки ФИО. Связи participant → staff ID, отметки обучения/допуски сотрудника, подтверждение прохождения и подпись участника не реализованы. Новое назначение работ не добавлялось. Профиль сотрудника использует прежнюю связь masterName; она не превращается в связь участников и остаётся неоднозначной для тёзок внутри одной компании.
- Физическая печать, PDF через драйвер, фото/вложения ТБ, внешний ИИ, мобильный браузер, браузер директора/заместителя и браузер профиля сотрудника в этом пакете не проверены. Фото-поле существовало в API, новой загрузки фото не добавлялось.
- Защита от двойного нажатия не является серверной идемпотентностью. Если сервер сохранил запись, но ответ потерян, ручная повторная отправка может создать дубль. Перед повтором нужно проверить список; автоматического повтора нет.
- Старый клиент без projectId может записать только в один однозначно доступный объект выбранной компании; неоднозначность даёт 409. Старые вкладки всё ещё имеют старую ошибочную обработку отказов — их код обновляется только после сохранения черновиков и обычного обновления страницы.
- Совместная работа браузера со всеми соседними модулями на полном снимке схемы и production smoke ещё не выполнены. Браузерная проверка здесь покрывает конкретные действия журнала, а не всё приложение.
