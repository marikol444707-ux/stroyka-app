# Локальный этап: обращения о подключении поставщика

Дата: 12.10.2026. Ветка: `codex/participant-support-stage1`.
Baseline: `d788bce9ef2d0845e9c6acfeff93c4dbf56afeed`.
Это описание подготовленного локального PR, не опубликованный PR и не production.

## Описание PR

**Название:** Показывать причину отказа приглашения и обращения по организации.

Раньше существующий кабинет и общая карточка нескольких покупателей давали один
отказ с советом обратиться к администратору; отдельного обращения и места его
разбора не было. Теперь сервер различает причины, а пользователь может нажать
«Сообщить о проблеме». Контекст организации, пользователя и карточки определяет
сервер. Диагностика сохраняется после rollback исходного приглашения; обращение
создаётся отдельной командой, без повторной регистрации или приглашения.

В существующем кабинете владельца платформы у каждой организации добавлен
раздел «Участники и доступ»: реальные поставщики, поиск, пагинация, обращения,
причина, происхождение карточки, история и статусы. Автор читает ответ в
Снабжение → Поставщики → «Мои обращения», даже после закрытия формы приглашения.

Служебные записи имеют неизменяемые company/account/reporter и связь с точной
диагностикой; история append-only. Повторы и конкурентные обращения не создают
дубли. Статус требует актуальную версию; закрытие — результат и отметку проверки.
Это подтверждение администратора, а не автоматическое доказательство успешного
подключения бизнес-кабинета: такое подключение в этом этапе не выполняется.

Код не меняет владельцев кабинетов, назначения, aliases, документы, реквизитные
snapshots, оплаты или склад. Старый глобальный `/suppliers/{id}/link-user` новый
экран не вызывает. Все новые administrative API запрещены platform_support;
существующая запись support session сама не выдаёт полномочий.

## Браузер

Реальный Chromium через Playwright CLI; локальная оболочка импортирует настоящие
React-компоненты и `createUserAccessActions`, запросы идут в настоящий FastAPI
через Unix socket к изолированной тестовой БД. Fetch и ответы не замоканы.
Оболочка содержит переключатели «Покупатель»/«Администратор» и две синтетические
организации. Это component integration E2E, **не весь production app shell**.

Пройдено: 409 → явное обращение → admin карточка и источник «Из накладной» →
new/in_progress/resolved/closed → ответ в «Мои обращения». Закрытие используется
только для проверки служебного workflow, бизнес-доступ не изменён. Переключение
на B убрало карточку/обращение A; B показывает собственные данные и пустую очередь.
Проверено отсутствие горизонтального overflow при 320/390/768/1280/1440 px у
покупателя и администратора; Tab переводит фокус на доступный control.
Поздние ответы/ошибка/пустота дополнительно проверены RTL.

Скриншоты локальной синтетической проверки (не в Git):
`output/playwright/participant-support/admin-mobile.png`, `admin-desktop.png`.
Консоль первой цепочки имела ожидаемый failed resource 409; после пересборки
оболочки нет runtime JS errors. Письма и сообщения не отправлялись.

## Производительность

Локальный baseline реестра: 20 последовательных authenticated API запросов,
limit=25, поиск среди 111 связей выбранной компании, общий supplier связан с
50 организациями двух аккаунтов. MacBookPro13,3, x86_64, 16 GiB RAM,
Python 3.9, PostgreSQL 15.17 Homebrew, Unix socket/TestClient.
Заключительный замер: median **30,28 мс**, p95 (nearest rank) **35,43 мс**.
Отдельный повтор при параллельном frontend-прогоне: median 35,45 мс, p95 64,77 мс.
Локальный контрольный бюджет при тех же условиях: 2×35,43 = **70,86 мс** p95.
Это не проверка 50 полных бизнес-цепочек подрядчика/поставщика и не production SLA.
Для повторения на другом оборудовании нужен свой baseline; целевой критерий
регрессии реестра — p95 не более 2× baseline на одинаковом стенде/объёме.

## Включение и восстановление — только будущий выпуск

Сейчас `PARTICIPANT_SUPPORT_ENABLED=0`; интерфейс скрыт без frontend-флага.
До отдельно разрешённого выпуска нужны reviewed migration, backup, Linux CI,
canary и маршрутизация `/participant-support/` к backend в рабочем reverse proxy.
Существующий `/system/` также проверяется в canary. Команды production здесь
намеренно не выполнялись.

Выключение флага/возврат старого кода сохраняет служебные таблицы. Downgrade
запрещён при любых данных; это проверено в PostgreSQL. Чистые таблицы создаются
повторно идемпотентно. Legacy владельцы не назначаются; неопределённая принадлежность
остаётся неопределённой. Реальный «Сатурн» не читался: его причина не доказана.

## Точка продолжения

Следующий срез — реальные сотрудники и приглашения выбранной организации,
без смешения users.id/staff.id/contractor_id. Затем server-built preview и
отдельная операция подключения существующего supplier account; reuse company
merge из PR360 с current membership/version/ownership checks, идемпотентностью
и аудитом. Не использовать старую глобальную очистку suppliers.user_id.

Остаются этапы 2–5 полного плана: support capabilities, многоклиентский подрядчик,
команда/бригады/назначения, расширенная поддержка, архивы/отзывы/jobs/WS/exports,
полная матрица ≥50 клиентов и отдельная согласованная приёмка/выпуск.
Спорная выдача прав и любые реальные подключения/merge требуют отдельного
подтверждения точного reviewable результата. Публикация и production запрещены
текущим заданием, даже если ранее в переписке разрешался deploy.
