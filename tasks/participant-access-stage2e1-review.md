# Stage 2e1 — назначенный доступ поддержки к диагностике

## Граница этапа

Администратор выбранной организации выдаёт конкретному действующему
`platform_support` право `diagnostic.read` на одно существующее обращение.
Пользователь поддержки получает отдельное рабочее место; никаких членств,
имперсонации, доступа к архивам и бизнес-команд эта выдача не создаёт.

Обнаружено: `platform_support_sessions` содержит scope/expiry/status, но чтение
бизнес-данных эти записи не использует. Существующий список доступен роли поддержки
глобально. Эти записи оставлены историческим журналом; ни одна не преобразуется
в новое разрешение. При включении нового режима обычные защищённые HTTP-маршруты
для `platform_support` закрываются в существующей общей зависимости аутентификации.
Остаются GET рабочего места и GET точной диагностики. Публичные ресурсы, вход,
выход и получение CSRF продолжают пользоваться своей прежней политикой.
Администратор/владелец сохраняет самостоятельные права своего обычного кабинета,
но не может использовать разрешение, выданное другому сотруднику.

## Полномочия и угрозы

| Сценарий | Серверная проверка / доказательство |
| --- | --- |
| Подмена company/account/ticket | Составной FK, исходный ticket из выбранной компании, UUID не содержит новых полномочий |
| Другой сотрудник скопировал UUID | Точный assignee_id, текущий аутентифицированный actor; чужой UUID → 404 |
| Заголовок компании или «сессии поддержки» | Не расширяет scope; прямые счета/метаданные файлов/контент/jobs/legacy read routes → 403 |
| Изменён статус обращения | ticket_version фиксируется при выдаче; изменение версии прекращает доступ |
| Сотрудник/выдавший отключён, роль заменена и возвращена | Текущая роль/active и existing supplier_team_epoch обоих, защита от ABA |
| Истёк срок, отозван доступ | clock_timestamp после блокировок; отзыв окончателен, повторный отзыв идемпотентен |
| Просмотр одновременно с отзывом | SHARE на grant до записи события и commit; отзыв ждёт завершения уже разрешённого чтения |
| Попытка продлить/переназначить grant или стереть события | Неизменяемые scope/action/actor/expiry и append-only events, DB triggers |
| Нет feature/schema | 503, новые полномочия не выдаются |
| Повторная выдача | Старый grant отзывается, новый UUID и срок; не продлевает старый UUID |

Роли и активность читаются из PostgreSQL, без auth dependency overrides.
Заголовки и ID клиента не считаются доказательством владения. Применены
локальные таймауты lock=3s, statement=15s; конкуренция → 409 без частичного результата.

## Что видно пользователю

- Администратор: организация → Участники и доступ → Проблемы и обращения →
  Разобрать обращение → Доступ сотрудника поддержки.
- Выбор действующего сотрудника (имя/ID, без email), причина и срок 1–1440 минут.
  Это технический верхний предел разрешения, не обещание срока решения проблемы.
- Выданные доступы, отзыв, последние 25 действий по каждому доступу.
- Поддержка: только назначенные обращения с точной организацией, причиной и сроком.
  Детали открываются отдельным запросом; показываются сохранённые диагностические
  сведения, сообщение автора и результат, без списка других участников/документов.
- Каждый успешный показ в списке и открытие диагностики сохраняет событие.
- Ответы диагностики/списка/истории имеют `Cache-Control: private, no-store`.
  Истечение срока также очищает уже открытый контекст в интерфейсе.

## Схема и включение

Миграция `0097_participant_support_access` после `0096`: две пустые таблицы,
индексы и guards; никаких бизнес-backfill или конвертации legacy-сессий.
Пустой downgrade разрешён; при сохранённой истории downgrade отказной.

Backend: `PARTICIPANT_SUPPORT_ENABLED=1`, `PARTICIPANT_SUPPORT_ACCESS_ENABLED=1`.
Frontend: соответствующие `REACT_APP_PARTICIPANT_SUPPORT_ENABLED=1` и
`REACT_APP_PARTICIPANT_SUPPORT_ACCESS_ENABLED=1`. Новые флаги по умолчанию выключены.
Включать только согласованным выпуском backend/frontend после отдельного разрешения.
Изменение режима глобальной роли поддержки специально связано с этим флагом;
при старом режиме старые права не объявляются исправленными.

## Проверки

- RED: практический сценарий выдачи/чтения сначала упал на 404 отсутствующего API.
- PostgreSQL: 17 новых тестов, включая signed bearer, настоящую cookie-сессию,
  expiry, role/active ABA, company mismatch, закрытие, отзыв и конкуренцию,
  миграцию, triggers и legacy label. CI запускает точный класс, без дублирования
  импортированных базовых unittest-классов.
- Регрессия: существующие обращения и подключение кабинета запускаются отдельно.
- UI: выдача, защита от повторного клика, отзыв, ошибки, смена организации,
  поздний ответ, истечение срока и скрытие старого контекста.
- Браузер: реальный React и HTTP к изолированному backend/PostgreSQL; только
  синтетические пользователи. Проверка ширин 320/390/768/1440.
- Итог: 17 новых PG + 11 существующих обращений + 11 подключений = 39 PASS,
  без skipped в этих PG-классах. Shared auth: 14 unit PASS; platform_admin: 112
  tests / 22 opt-in skipped / 90 executed PASS; expense_reports: 10 PASS.
- Полная frontend suite: 301 suites / 1854 tests PASS. Production build с новыми
  UI флагами: Compiled successfully; исходная подсказка Browserslist о возрасте
  базы осталась, новых ESLint warnings нет.
- Tenant registry: 141 entries, failures=[]; git diff --check и Python compile PASS.
- Chromium: grant → scoped list → diagnostic → revoke → empty assigned list;

## Осталось, без преувеличения готовности

Это первый законченный диагностический доступ, не весь контур поддержки.
Не выданы права на исправление/слияние/платежи/склад/файлы; следующий этап должен
создавать отдельные точные команды с preview и audit. Отдельно остаются исправление
ошибочной связи и масштабирование исторического объединения (Stage 2d2).
Старый административный центр и клиентский dashboard ещё показывают legacy-журнал;
новые grants находятся в карточке обращения. При закрытии обращения доступ
прекращается через version; повторное открытие не оживляет прежний UUID.

Уже прочитанные сведения невозможно «забрать назад»: отзыв запрещает следующие
запросы и не прерывает уже разрешённую короткую транзакцию. Интерфейс очищает данные
при следующей ошибке, уходе с экрана или expiry; мгновенный push об отзыве отсутствует.
Отказные обращения не записываются в новый grants audit; он фиксирует успешное
использование и управление. Общий security-denial audit, background-job/WS инвентарь
и отдельный полный App E2E относятся к следующему системному аудиту, а не к
доказанным возможностям этого ограниченного этапа. Новых WS/job маршрутов здесь нет.

На production ничего не применено; push, PR, деплой и включение не выполнялись.
