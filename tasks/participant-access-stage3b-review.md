# Этап 3б: точный выбор сотрудника или пользователя

18.10.2026. Ветка `codex/typed-contractor-selection`, исходный код `217c974b`.
Срез меняет существующие формы выдачи работ по смете и создания договора бригады.
Новый кабинет, организация подрядчика и управление его командой не добавлены.

## Что изменилось

Выбор сотрудника и выбор пользователя имеют разные ключи (`staff:23`, `user:23`).
Их одинаковые имя, email или числовой ID больше не объединяют варианты в форме.
Дедупликация аккаунта сотрудника использует только сохранённый accessUserId.
При одинаковых именах список показывает «сотрудник» или «учётная запись».

Формы отправляют `contractorRef={type:'staff'|'user',id:...}`. Сервер проверяет
текущую компанию, активность пользователя и действующее членство с ролью
мастер/субподрядчик/бригадир. Для staff также проверяются подтверждённая компания
карточки, активный статус и точный `user_company_roles.staff_id`.
Name/email fallback в этой ветви отсутствует. Без одного подходящего аккаунта
возвращается 409: нужно проверить доступ в карточке сотрудника.

Выбранные строки членства удерживаются FOR UPDATE до конца транзакции команды,
в порядке, совместимом с существующим обновлением scope (членство → пользователь).
Нельзя переназначить эту staff-связь или отключить членство посреди сохранения.
Неактивное членство не заменяется legacy `users.company_id`.

Явный null, неизвестный тип/лишние поля, boolean/дробный ID, конфликт старого ID
с выбранной ссылкой и разные ссылки в корне/assignee отклоняются, не включая
прежний resolver. Переданный 0 не исчезает из проверки через `or`.

`POST /brigade-contracts` возвращает канонический contractorId пользователя.
Форма сохраняет его вместо ID staff. Выбранная карточка сотрудника всегда
проходит команду сервера, даже когда старый договор уже виден в списке: локальный
поиск дубликата не обходит свежую проверку связи. Если сервер возвращает reused,
форма открывает подтверждённый договор через прежнее обновление списка.

## Доказательства

Два новых теста воспроизвели смешение совпадающих user/staff ID до правки.
Дополнительные UI-тесты проверяют payload точного выбора, сохранение канонического
user ID и запрет открытия ранее видимого договора без проверки сервера.

В реальной PostgreSQL/API fixture сотрудник намеренно имеет одинаковые ID,
имя и email с одним пользователем, но сохранённую связь с другим. Явные user
и staff варианты создают договоры для разных точных аккаунтов. После добавления
работ каждый исполнитель видит только свой договор. Выдача работ из сметы
использует ту же проверку; другой аккаунт не получает позиции.

Отдельно проверены уволенный сотрудник, чужая компания, отозванное членство,
ошибочные ссылки, сохранность таблиц при отказе и PostgreSQL lock timeout
параллельного отзыва, пока транзакция держит выбранное членство.
Итоговый набор добавлен к обязательному CI.

Фактический итог локальных проверок:

- Frontend: 307 suites / 1944 tests — PASS.
- Профильные backend unit/route: 47/47 — OK.
- PostgreSQL: аудит идентичности 9/9, runtime-аудит 1/1, новый typed выбор 6/6 — OK.
- Production build, сверка режимов, ESLint, Python compile, CI YAML и diff check — OK.

Первый PG-прогон остановился на недостающем alias fixture в новом тесте; следующий
уточнил, что пустой договор без работ не показывается исполнителю. Итоговый
сценарий создаёт работу обычным API и проверяет её точную видимость. Эти замечания
исправлены в тестовой подготовке, прежние правила видимости не ослаблялись.

## Совместимость и остаток

Срез не переписывает исторические договоры, реквизиты, акты и оплаты и не создаёт
членства покупателя. Для действующего исполнителя переиспользуется прежняя
выдача project/package scope существующему членству.

Клиенты без contractorRef пока используют старый resolver. Ручная бригада и
выбор существующей legacy-бригады без доказанной typed ссылки остаются в прежнем
режиме. Поэтому это не закрытие всех name/email fallback проекта: следующие
срезы должны сохранять типизированное происхождение новых ручных/legacy назначений
и провести отдельный разбор спорной истории по аудиту 3а.

Новых миграций/флагов нет. Для typed staff нужны существующие schema 0006 и
staff.company_scope_verified. При будущем выпуске сначала устанавливается и
проверяется backend, затем frontend: старый сервер не подтверждает новый typed
контракт. При откате сначала возвращается совместимый frontend.

Полный browser E2E, общий backend discovery, удалённый CI и установленный сервер
не проверялись. Прогоны PostgreSQL изолированы в Docker без TCP-портов и сети,
только через Unix socket; рабочая `.env` и реальные карточки не используются.
Артефакты: `/workspace/stroyka-verification/typed-contractor-selection/`.
Публикация, установка, миграции и production enablement не выполнялись.
