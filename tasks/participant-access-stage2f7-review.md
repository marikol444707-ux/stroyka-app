# 2е7 — отдельные счета при ошибочном подключении

Локальный результат в `codex/participant-support-stage1`, после 2е6.
Backend savepoint: `009295d6`.
Production не изменялся; новые команды и UI выключены по умолчанию.

## Поведение

В существующем окне последствий администратор проверяет список документов,
указывает причину и закрывает ошибочный доступ. Поддержаны отдельные счета без
КП/заявки, точно связанные накладные и смешанная история с обычными КП.
Заявки или КП ради хранения отдельного счёта не создаются.

Счета, оплаченные суммы, реквизиты, КП, поставки, приёмки, склад и исходные
документы не редактируются. В архиве покупателя всё остаётся. Закрывается одна
связь и доступ к указанным документам, включая оригиналы и фото накладных.
Связи другого покупателя, команда поставщика и новые ID не затрагиваются.

Статус «Неактивный» сам по себе не запрет. Сервер сохраняет точные отдельные
invoice ID в private profile этой company/supplier link. Обычный API карточки
сохраняет это поле и не принимает его из запроса пользователя. Повторная
активация каталога или выключение флага команды не открывают старые ID.
Последующая привязка закрытого счёта к новому видимому КП также не возвращает
доступ: общая SQL-проверка действует на список счетов и оригиналы через КП.
Этот обход воспроизведён до исправления отдельным HTTP/PG тестом.

## Реализация

- Отдельный mode `revoke_invoice_access`, два `invoice-access-plans` POST пути;
  прежние unused/RFQ/quote/issued paths не получают новых полномочий.
- `PARTICIPANT_INVOICE_ACCESS_CORRECTIONS_ENABLED=1` и frontend
  `REACT_APP_PARTICIPANT_INVOICE_ACCESS_CORRECTIONS_ENABLED=1`, вместе с базовыми
  support/corrections flags. Новый UI mode приоритетен, но всё ещё требует
  обычных server-side admin/owner/company/version checks.
- Используется прежняя 0099: неизменяемый manifest, 15 минут, operationId,
  fresh admin/owner epochs, exact source/target/link, reason, атомарные audit и
  completion, проверенный идемпотентный повтор.
- Новая SELECT-only проекция сочетает закрытых адресатов и точные invoice ID.
  Политики чтения и файлов до/после используются реальные. Независимый доступ
  к оригиналу, чужой/удалённый файл или неполная связь блокируют применение.
- Новой миграции нет. Чтение не зависит от correction-plan таблицы или флага.
  Bootstrap-only link без private profile сохраняет прежний режим; применять
  команду можно только на полном migrated каталоге. Для SQL проверяется metadata
  через `to_jsonb`, без несуществующей колонки на старой bootstrap схеме.
- В DTO/план/audit входят ID/счётчики/хеши, а не raw финансовые строки или URL.

## Проверки

Новые 16 PostgreSQL сценариев: отдельный частично оплаченный счёт; прямые и
обратные накладные; оригинал без КП; отдельное фото накладной; смешанная цепочка;
другой покупатель/новый счёт; flags/roles/company; drift оплаты/новый документ;
неясная заявка/накладная/shared original; конкурентный повтор с одним audit;
rollback при сбое audit; реальный PUT карточки с попыткой очистить server field;
лидер команды; expiry/смена владельца/wrong mode/повреждённый replay;
SELECT-only guard; read-only CTE diagnostic; последующий accounting link repair.

Последние логи:

- `/tmp/invoice-access-final-runtime.log`: 16 новых + 19 issued + 3 multicompany +
  8 team — 46 PASS. Неоднозначные финансовые/архивные строки не удалялись.
- `/tmp/invoice-access-originals-regression.log`: 14 quote + 14 RFQ — 28 PASS.
- `/tmp/invoice-access-final-admin.log`: 13 unused + 8 preview + 9 financial +
  9 security + 17 capability — 56 PASS. Итого 130 разных PG сценариев, без skips.
- `/tmp/invoice-access-unit-final.log`: 13 unit PASS.
- `/tmp/invoice-access-ui-full.log`: 306 suites, 1904 tests PASS.
- `/tmp/invoice-access-build.log`: production build с новым UI flag PASS.
- `/tmp/invoice-access-red.log`: новые HTTP пути первоначально давали 404;
  UI red — 2 новых failure при 17 старых PASS.
- `/tmp/invoice-access-link-repair-red.log`: закрытый invoice ID вновь появлялся
  в кабинете после связи с новым КП; после исправления не появляется, файл 403.

В первом расширенном fixture проверка expiry попыталась изменить неизменяемую
строку плана — DB guard отказал; исправлен fixture с заранее истёкшей копией.
Owner epoch меняется реальным owner transition, а не ручной записью счётчика.
Старый multicompany fixture не имел profile: регрессия выявлена и совместимость
обычного чтения восстановлена без ослабления проверки новой команды.

Предупреждения synthetic auto-AI owner и старого api_errors.owner_scope из
multicompany fixture остаются вне этого среза. Они не доказывают готовность
AI/общего audit. Build выдаёт прежние Browserslist/bundle/Node warnings.

## Браузер

Playwright CLI, отдельная сессия `invoice-access`, реальные компоненты и
HTTP-прокси к socket-only disposable PG. Это локальная интеграция, не полный
production login. Пройдены оба подтверждения: отдельный счёт и смешанная цепочка
КП/двух счетов/поставки/приёмки с одним оригиналом. Отчёт показывает сохранение
документов; после «Готово» каталог отражает неактивную связь. Фокус Tab/Shift+Tab
остаётся внутри окна, при смене компании прежнее окно удаляется.
Ширины 320/390/768/1440 без горизонтального overflow; screenshots просмотрены.
В browser console только React DevTools info, без JS исключений.

Артефакты в ignored `output/playwright/participant-support/`:
`invoice-access-plan-390.png`, `invoice-access-plan-1440.png`,
`invoice-access-success-390.png`, `invoice-access-mixed-success-390.png`.
После закрытия backend сравнивает все business snapshots с исходными и удаляет
свою временную БД/uploads/private context. Реальные аккаунты не использовались.

## Остаток

Договоры, претензии, счета только с request без точного КП, накладные без
подтверждённых родителей, общие внешние оригиналы, уже изменённые связи и
историческое ошибочное объединение требуют следующих отдельных команд.
Автоматического восстановления доступа или очистки списка запретов нет.

До включения на production сохраняются задачи 2е6: согласованные company writer
locks вместо глобальных SHARE, большие архивы/нагрузка, storage/CDN проверка,
интеграция и отдельная приёмка релиза. Этот шаг не завершает весь раздел.

## Черновик описания изменения

После ошибочного подключения отдельные счета оставались доступны поставщику
напрямую. Новая company-scoped команда показывает точный список и закрывает
доступ к счетам/файлам, сохраняя финансовую основу и архив покупателя. Старый ID
не открывается после активации каталога или позднего accounting link repair.
Новые mutation/UI flags default-off, без изменения производственных данных.
