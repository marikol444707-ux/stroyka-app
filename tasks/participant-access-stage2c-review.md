# Подключение существующего кабинета к покупателю

13.10.2026. Продолжение локального `2d5fc080`, ветка
`codex/participant-support-stage1`. Публикации, production apply и включения нет.

## Подготовленное описание PR

Администратор в выбранной организации находит существующий кабинет и создаёт
запрос владельцу. Владелец видит покупателя в «Заказчики → Подключение к покупателям»
и принимает или отклоняет запрос. Администратор видит результат и может отозвать
непринятый запрос. Срок — два дня; письмо/секретная ссылка не создаются.

Добавляется только `company_supplier_links` точного покупателя к уже существующей
карточке кабинета. Не создаются пользователи, членства в покупателе, карточки
юрлица, назначения менеджеров или копии документов. `suppliers.user_id` не
переписывается. Карточка из накладной и её архив остаются отдельными до специально
проверенного объединения. Подключение не является согласием открыть старую историю.

Новый запрос не нужен уже подключённому кабинету. После принятия UI различает
готовую связь и проверку исторических документов, без повторного предложения
подключить того же покупателя.

## Границы операции

- Инициатор: действующий system_owner/platform_admin, конкретные company/account
  и существующая исходная связь. Это ограниченная административная операция;
  общий buyer self-service и support capabilities остаются следующими срезами.
- Получатель: аутентифицированный активный **прямой владелец** target.user_id.
  Делегированный team leader/manager не заменяет владельца при этом действии.
  ИНН/ОГРН находят кандидат, но не позволяют принять запрос от имени владельца.
- Только один точный действующий кабинет, без противоречивых юридических ключей;
  неоднозначный поиск, изменившиеся/неактивные карточки запрещают подключение.
- Создание хранит source version, source/target legal evidence, точного владельца,
  epochs пользователей-владельца/инициатора и epoch владельца карточки.
  Восстановление прежней роли или user_id после отзыва не оживляет старый запрос.
- Принятие повторно проверяет текущую авторизацию, buyer/account, состояние,
  версии, реквизиты, срок и уникальность кандидата. Lock order: company → legal
  advisory keys → supplier rows → users → source link → request. Ключи совпадают
  с существующей регистрацией/созданием каталога.
- Один pending request на buyer/target; создание повторяется по UUID operation
  key с проверкой исходного payload/инициатора. Повтор решения возвращает тот же
  результат только после текущей авторизации; чужой запрос недоступен.
- При ошибке аудита откатывается и новая связь. Ни оплаты, ни складского движения,
  ни повторного invite/письма, ни изменения issued snapshots не выполняется.
- Общий billing middleware классифицирует только точные accept/decline URLs
  доказанного прямого владельца; бизнес-маршрут заново авторизует под блокировками.
  Покупательские финансовые операции сохраняют прежние правила подписки.
- Shared source/документы неизвестной компании блокируют выдачу исторического
  доступа, но не препятствуют отдельной связи с кабинетом: source не передаётся.
  Адресаты invoice/offer/file/contract и назначения команды не изменяются.

## API / схема / UI

POST/GET `/system/companies/{company_id}/participants/{supplier_id}/connection-requests`;
POST того же пути `/{request_id}/revoke`.
GET `/supplier/connection-requests`, POST `/{request_id}/accept|decline`.
Типизированные вход/выход, UUID, строгие числа/confirmation, запрет лишних полей,
постраничные списки 25, максимум 100. Администратору — история точного source;
поставщику — только актуальные pending запросы его прямого владения, без контактов,
сумм, архивов покупателя или данных других владельцев.

Миграция **0095** после 0094: пустая таблица запросов, composite company/account
и source-link FK, индексы, immutable evidence и финальные состояния; downgrade
блокируется при истории. Добавляется служебный `suppliers.participant_owner_epoch`
и trigger смены user_id; существующие legal snapshots и владельцы не назначаются.
Повтор upgrade проверен. Схему надо отдельно проверить на production-size canary;
на рабочем сервере она не применялась.

Backend требует прежний `PARTICIPANT_SUPPORT_ENABLED=1` **и новый**
`PARTICIPANT_CONNECTIONS_ENABLED=1` (default 0). UI требует отдельный
`REACT_APP_PARTICIPANT_CONNECTIONS_ENABLED=1`; в сборке проверки включены оба флага.
Старый GET preview остаётся `canApply=false`: запрос — отдельная команда.
