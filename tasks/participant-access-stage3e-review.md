# Этап 3д: восстановление ручной отправки после перезагрузки

19.10.2026. Локальная реализация на ветке `codex/manual-command-recovery`.

## Поведение

В создании бригады без аккаунта и выдаче работ из сметы браузер сохраняет
точное тело запроса и UUID до отправки. После обрыва связи и перезагрузки
в той же вкладке можно повторить исходную отправку. Автоматической повторной
отправки нет. Пока результат неизвестен, новый черновик не заменяет запрос.

Запись sessionStorage разделена по пользователю, компании, типу операции,
объекту/смете и разделу работ. Смена контекста отменяет активный запрос и
блокирует применение запоздалого результата. Сервер заново проверяет права,
expectedActorId и expectedCompanyId; эти поля не заменяют авторизацию.
Повреждённое или недоступное хранилище блокирует новую отправку.

После подтверждённого POST сохраняется квитанция с manualRequestId.
Если обновление списка не удалось, кнопка повторяет только чтение списка.
Запись удаляется после успешного обновления, до закрытия формы.

Сервер распознаёт уже выполненную ручную выдачу до создания нового снимка
сметы. Повтор возвращает исходный договор без добавления строк или события
выдачи, даже если смета изменилась. Для ещё не выполненной команды expectedSource
проверяет исходные название, единицу, объём и цену; изменения дают 409 с откатом.
Существующие user/staff/contract ссылки сохраняют прежний маршрут.

## Проверки

- Полный frontend: 309 suites, 1966 тестов — успешно.
- Backend unit/route для manual и work_assignment: 12 тестов — успешно.
- Новая PostgreSQL fixture: 4 реальных HTTP/БД сценария — успешно до замены
  среды исполнения. Проверены потерянный ответ и изменённая смета без новых
  снимков/строк, отказ изменённого исходника, чужой actor/company и отзыв роли.
  Серверный код после этого прогона не менялся. После замены среды этот PG
  прогон не повторялся: отсутствуют зависимости, установка ограничена sandbox.
- Сборка frontend завершилась успешно; предупреждение о смешанных операторах
  в новом helper устранено скобками. Последующий ESLint изменённых файлов чист
  (кроме уведомления об устаревшей базе Browserslist).
- Python compilation и git diff --check — успешно.
- Новая PG fixture добавлена в CI; удалённый CI не запускался.

Компонентные тесты проверяют размонтирование/повторное открытие обеих форм с
другим черновиком, точный повтор тела, смену компании/пользователя, поздний ответ,
смену browser login до обновления props, ошибку хранилища и обновления списка.

Отдельный Chromium-прогон не завершён: sandbox первоначально блокировал
запуск, после разрешения запуска политика браузера запретила file:// переход.
Повтор с HTTP-стендом не завершён. Поэтому полноценная браузерная приёмка
перезагрузки и установленного приложения не заявляется.

Сохранившиеся локальные логи: `/workspace/stroyka-verification/recovery-frontend.log`,
`recovery-build.log`, `recovery-eslint.log`, `recovery-unit.log`.
Лог PostgreSQL был во временной среде и после её замены не сохранился;
результат выше отражает выполненный прогон, а не повторную проверку.

## Выпуск и границы

Новой миграции нет; требуется схема 0101 из этапа 3г. При совместимом выпуске
сначала backend с manualRequestId, затем frontend. На сервер ничего не
устанавливалось, production данные и миграции не менялись.

Восстановление действует в той же вкладке браузера, не между устройствами
или после закрытия вкладки. Неопределённые результаты, включая поздние отказы
401/403/409, сохраняются; безопасная отмена такой команды отдельным действием
не реализована. Исторические unlinked записи, юридическая сторона без аккаунта,
приглашение/привязка аккаунта и собственная команда подрядчика остаются
следующими самостоятельными этапами. Этот срез не означает готовность всего кабинета.
