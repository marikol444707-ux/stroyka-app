# Проверка кабинета поставщика в выбранной организации

13.10.2026. Локальная ветка `codex/participant-support-stage1`, продолжение
`ee092f13`. Публичные push/PR и production apply не выполнялись.

## Описание подготовленного изменения

В «Аккаунты/компании → организация → Участники и доступ → Поставщики» появилась
кнопка «Проверить кабинет». Такой же вход есть в карточке обращения поставщика.
Результат раскрывается рядом: существующая связь, найденный кабинет, неоднозначные
карточки, документы выбранной компании и конкретные препятствия.

Это законченный срез **диагностики**, не команда подключения и не полный план
выдачи исторического доступа. `canApply=false`; в интерфейсе нет кнопки выдачи
прав. Существующему подключённому кабинету не добавляется обязательное согласование.

## API и границы

GET `/system/companies/{company_id}/participants/{supplier_id}/connection-preview`
доступен только действующему system_owner/platform_admin, под прежним флагом
PARTICIPANT_SUPPORT_ENABLED и схемой 0094. Новых миграций/зависимостей нет.
companyId/supplierId — положительные целые. Ответ типизирован Pydantic;
401/403/404/422/503 различаются, write-route отсутствует.

Начало проверки — точная company/account/supplier связь каталога. Счётчики
накладных, счетов и КП всегда ограничены этой компанией и этой исходной карточкой;
суммы, файлы и чужие документы не возвращаются. Название, email, телефон и aliases
не используются для поиска кабинета. Поиск потенциальной зарегистрированной
карточки допускается только по точному валидному ИНН/ОГРН. Возвращается минимум
юридического профиля и typed supplier/user IDs, без контактов и чужих покупателей.
Несколько совпадений — спор, а не выбор первого или автоматическое объединение.

Сохранённый suppliers.user_id и включённая роль поставщика показывают текущее
состояние связи, **не доказывают юридическое владение**. Для нового подключения
остаётся OWNER_VERIFICATION_REQUIRED. Неполные/противоречивые реквизиты, команда
исходной карточки, merged profile, shared source, другой/неизвестный владелец
документов и неактивная связь показаны отдельными причинами. Существующий
company_merge.check_company_documents переиспользован без раскрытия чужой истории.

Для уже связанной карточки отдельные currentVisibility счётчики используют
существующие supplier invoice/offer disclosure policies и реальные actor IDs
(team access_ids при включённой команде). Внешняя выборка всё равно ограничена
исходным supplierId/companyId. Для потенциального подключения эти значения NULL:
число buyer-owned документов не выдается за будущий разрешённый архив. Файлы,
договоры, печать и будущие менеджеры требуют своих отдельных проверок.

Весь ответ читается из одного REPEATABLE READ snapshot; company pin сохранён.
Это информация на момент запроса, не долговременный capability/preview token и
не защита будущего изменения. Следующая команда обязана заново авторизовать,
проверить доказательство владения/версии/получателей и выполнить свой аудит.
Старый глобальный link-user не вызывается и не переносится в новый интерфейс.

UI отменяет запрос при закрытии/смене карточки/вкладки/компании; запоздалый ответ
игнорируется. Ошибка не заменяется «кабинет не найден». Диагностические IDs и
причины скрыты в раскрываемом блоке. Карточки на компьютере не растягивают соседей.

## Проверки локального среза

| Проверка | Результат |
|---|---|
| TDD | Первые 6 PostgreSQL тестов падали на отсутствии route; затем реализовано чтение |
| Новый PostgreSQL/FastAPI/auth | 10 PASS: точная компания/аккаунт, чужие/NULL владельцы, неоднозначность, конфликт реквизитов, name/contact exclusion, team-only карточка, отключение/роль, архив против новых закупок, отсутствие write и изменений данных |
| Масштаб | Один кабинет у 50 покупателей двух независимых аккаунтов; у каждого только собственный счёт, суммы и другие связи не раскрываются |
| Visibility | Скрытая заявка/КП и связанный счёт учитываются в истории покупателя, но не объявляются доступными поставщику; проверено с team/customer flags 0 и 1 |
| Существующие PG цепочки | Обращения 11 PASS, company merge/registration 10 PASS; отдельные socket-only БД |
| Frontend | Полный прогон 295 suites / 1829 tests PASS; после финальной CSS коррекции профильные 9 tests PASS, включая abort/retry/scoped entry |
| Сборка | Финальная сборка после CSS коррекции PASS с PARTICIPANT_SUPPORT, WORK_MATERIAL_ACCOUNTING и WORK_ACCEPTANCE флагами |
| Старые routes/release runner | 29 PASS. При параллельной сборке один fake-host deployment test превышал собственный 20s timeout; после освобождения машины повторный полный набор прошёл. Проверки не ослаблялись |
| ESLint/compile/diff | PASS; только существующее предупреждение Browserslist |
| Общий backend/Linux CI | Полный backend в этом срезе повторно не запускался. Предыдущий прогон: 5687 tests, 7 известных baseline PDF-сбоев на Mac, 1907 skipped; Linux CI остаётся обязательным перед выпуском |
| Рабочий сервер | Не проверялся и не изменялся; release/enablement не выполнялись |

Локальная измеренная серия: 20 запросов уже связанной карточки, 50 покупателей
двух аккаунтов, финальная серия median 25.22 ms / p95 26.62 ms (предыдущая серия
30.28/36.79 ms при параллельной работе). Это socket-only синтетическая БД
на данном Mac, не production SLA и не нагрузочная проверка спорного legacy-архива.

Chromium проверяет реальные компоненты, FastAPI и изолированный PostgreSQL,
а не полный App shell или production. Проверены подключённый кабинет, кандидат
в другой компании, спор двух кабинетов, переход из обращения, сброс после смены
компании; ширины 320/390/768/1280/1440, клавиатура и отсутствие горизонтального
переполнения, кнопки панели ≥44 px. Synthetic preview screenshots остаются в
игнорируемом `output/playwright/participant-support/`; cookies/tokens не включены
в коммит. Временные тестовые БД, серверы и файл тестовой авторизации удаляются.

## Следующий ограниченный этап

Подтверждаемая владельцем связь существующего кабинета с точным покупателем.
Отдельно: доказательство через действующую идентичность кабинета; адресаты
конкретных исторических документов/файлов; версии и отзыв proof; повторная
проверка и idempotency под блокировками; аудит точных сторон без изменения issued
snapshots. Подключение, объединение и смена владельца — разные команды.
Текущий просмотр сам не выдаёт такого доказательства или прав.
