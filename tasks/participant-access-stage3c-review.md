# Этап 3в: выбор точного существующего договора

18.10.2026. Ветка `codex/exact-contractor-contract-selection`, база `73dbd365`.

Форма выдачи работ из сметы раньше скрывала договоры с совпавшим названием,
а сервер искал подходящий договор исполнителя, отдавая приоритет договору
с работами. Поэтому выбранная карточка могла привести к другому договору.

Теперь договоры выбранного объекта/раздела показаны отдельно, с номером.
Форма отправляет `contractorRef={type:'contract',id:...}`. Сервер проверяет точные
company/project/package, статус договора, пользователя, его действующее членство
и роль исполнителя. Затем использует именно подтверждённый ID, без поиска
дубликата по исполнителю или названию. POST создания договора поддерживает
такой же точный reuse и возвращает канонический contractorId.

Общая с read-only аудитом проверка исторической идентичности вынесена в
identity/evidence: у неподписанного договора неоднозначный user/staff ID
требует проверки; сохранённые стороны должны иметь правильный hash и точные
IDs компании/объекта/договора/пользователя. Подписанный договор без этих
доказательств, unlinked legacy, чужой объект/компания/раздел, аннулированный
договор и отозванное членство блокируются с 409. Имя/email не заменяют связь.

Порядок блокировок совместим с существующей командой: членство → advisory lock
company/project → договор. После получения блокировки доказательства читаются
повторно. Параллельное переназначение договора или отключение выбранного
членства ждёт завершения транзакции; PostgreSQL lock-timeout тест это проверяет.

При точном выборе не обновляются название/тип/исполнитель и сохранённые стороны
договора. Позиции добавляются существующим механизмом lineage; повтор не меняет
выданные цены. total_amount, как и раньше при назначении работ, пересчитывается
из позиций. Это не изменение правил выпуска или перепечатки документов.

PG-сценарии используют настоящие HTTP API и отдельные свежие тестовые базы.
Проверены более приоритетный дубль, повтор с иной ценой, неизменность остальных
полей подписанного договора, конфликт/hash сохранённых сторон, чужая scope,
спорная числовая ссылка, отзыв и блокировки. Отказные команды сравнивают
состояния договоров/позиций/пользователей/членств/смет/версий до и после.

## Границы

Новых миграций и изменений реальных данных нет. Нет автоматического исправления
исторических ссылок или выдачи членств покупателя. Ручная новая бригада и старые
клиенты без contractorRef пока сохраняют прежний resolver; их происхождение и
доступ требуют следующего среза. Новый кабинет и команда подрядчика ещё впереди.

Сначала должен выпускаться совместимый backend, затем frontend; при откате —
обратный порядок. Установленный сервер, удалённый CI, общий backend discovery
и полный browser E2E в этом срезе не проверялись. Публикация и установка не
выполнялись. Локальный тестовый PostgreSQL работал без TCP-портов/сети Docker,
через Unix socket, без загрузки рабочей .env.
