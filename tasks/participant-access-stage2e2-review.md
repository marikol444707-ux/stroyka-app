# Stage 2e2 — отказной аудит и проверка прямых маршрутов

Сотрудник поддержки не может открыть бизнес-раздел напрямую с разрешением на
диагностику. Отказ по собственному назначенному обращению виден администратору
в его карточке: «Доступ сотрудника поддержки» → «Попытки открыть без доступа».
Кнопка «Обновить историю» загружает последние сведения, без обновления страницы.

## Что изменено

Миграция 0098 создаёт пустую participant_support_denials. Записываются только
ID действующего аутентифицированного сотрудника, категория маршрута, HTTP-метод,
код отказа и время. Нет URL/query/body, IP, email, cookies, токенов и текста ошибки.
Только UUID, назначенный этому сотруднику, позволяет серверу добавить точный
company/account/ticket. Подмена X-Company-Id и чужой UUID оставляют событие
в области платформы и не загрязняют историю другого покупателя.

Таблица защищена от UPDATE, DELETE и TRUNCATE. Downgrade с историей запрещён;
пустой downgrade/upgrade и повторное upgrade проверяются вместе с 0097.
Отказ записывается отдельной короткой транзакцией после rollback чтения.
Если журнал/соединение недоступны, отказ сохраняется, без выдачи данных;
операционная ошибка SUPPORT_DENIAL_AUDIT_UNAVAILABLE не содержит исключение
или SQL-параметры. Полнота истории в момент отказа БД не обещается.
Ответы 403/404 этого контура имеют Cache-Control: private, no-store.
История конкретного grant показывает последние 25 отказов.

Новый режим поддержки не запускается при публичном /uploads или public-read
S3 ACL. Существующий default-off режим не изменён. Проверка конфигурации не
проверяет bucket policy, ранее опубликованные объекты, CDN, Nginx или отозванные
внешние ссылки: это отдельные обязательные storage-проверки перед включением.
Ничего на сервере не включалось и не менялось.

## Инвентарь и границы доказательства

| Поверхность | Проверка |
| --- | --- |
| 558 зарегистрированных API с общей auth dependency | 2 точных GET рабочего места разрешены; остальные 556 операций проверены настоящими signed HTTP-запросами и получили 403 |
| Счета, платежи, экспорт, документы, метаданные/контент tenant-files | Общий get_current_user отказывает до бизнес-handler; заголовки доступа/компании не расширяют права |
| Legacy /uploads/{path} | При закрытом публичном mount используется тот же auth; HTTP-отказ проверен; небезопасная конфигурация нового режима запрещена при старте |
| Jobs: list/detail/cancel/AI launch | Прямой доступ поддержки закрыт; сервис enqueue требует точный project/company и активное членство автора; diagnostic grants не создают jobs |
| Workflow/MAX/Telegram/AI service API | Отдельные секреты интеграций; UUID grant не заменяет Workflow secret (проверено с синтетическим настроенным ключом), AI fallback (403), MAX без ключа (503) |
| Публичный сайт, login/reset/register, MAX miniapp, payment webhook | 39 альтернативных маршрутов и их реальные dependency зафиксированы в alternative_auth_inventory.json; CI отказывает при изменении этого списка. Их политики не заменяются поддержкой; полный аудит внешних подписей не объявлен выполненным |
| OpenAPI/Swagger/Redoc | 4 стандартных публичных описания API; список non-API routes проверяется отдельно, новые mounts требуют явного review |
| WebSocket | В зарегистрированном backend нет APIWebSocketRoute; rg backend/src также не обнаружил WS implementation. Если она появится, нужна отдельная авторизация |

Тест открывает default-off router gates распределения/платежей в изолированной
БД, чтобы ранний 404 выключенного модуля не маскировал проверку полномочий.
Сервисные ключи не позволяют имперсонацию поддержки и не выдаются с grant.
Уже существующие системные jobs не конвертируются и не объявлены jobs поддержки;
общая ревокация бизнес-полномочий в каждом worker относится к этапу масштабирования.

## Приёмка

- RED: отсутствовали таблица отказов и поле denials в истории; отдельный RED
  подтвердил, что сломанные rollback/close могут заменить 403 ошибкой сервера.
- Изолированный PostgreSQL: 9 security + 17 существующих capability = 26 PASS,
  без skips; обязательный точный класс добавлен в CI. Никаких production,
  внешних отправок, настоящих платежей или движений склада.
- 73 unit: storage configuration, отказ при сбое аудита, существующие file/job
  policies и public-exposure report. Все PASS.
- 3 UI suites / 11 tests PASS: scoped history, выдача/отзыв, late response,
  entry routing, expiry; production build с обоими UI-флагами.
- Chromium: выдача → отзыв → HTTP 403 → отказ в карточке администратора;
  реальный React/HTTP и отдельный Unix PostgreSQL, синтетические actors.
  Это компонентный стенд, не полный App login. Мобильный снимок проверен
  визуально; горизонтальное переполнение проверено на 320/390/768/1440.
- Дополнительно отдельный PG-прогон инвентаря подтвердил список 4 non-API
  описаний/mounts. Временные браузер/HTTP/Unix PG остановлены; файл с
  синтетическими tokens удалён.
- Tenant registry: 142 entries, failures=[]; compile/diff check PASS.
- Сборка Compiled successfully; существующие подсказки Browserslist/Node и
  размера bundle, без новых ESLint warnings. Общий frontend/backend здесь
  повторно не запускался, результаты полного предыдущего прогона — в 2д1.

## Что остаётся

Полный App login E2E остаётся следующим блоком: useCompanyContext пока делает
/users/company-context для любого вошедшего пользователя, а общий initial loader
может запрашивать проекты/журнал до вывода SupportWorkspace. Эти запросы сервер
отказывает; нужно отдельно исключить ненужную загрузку и проверить настоящий
вход/выход, обновление страницы, переключение роли и поздние ответы.

Отказы без собственных grant хранятся в области платформы; отдельный обзор
таких попыток в административном UI ещё не создан. Нет общего журнала всех
неаутентифицированных попыток, websocket/job полномочий поддержки, мгновенного
push об отзыве или production readiness. Исправление ошибочной связи и снятие
глобальных SHARE-блокировок исторического merge остаются по полному плану.
