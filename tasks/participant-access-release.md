# Подготовка выпуска: участники организаций и поставщики

Дата проверки: 15.10.2026. Это локальный кандидат, не установленный выпуск.
Проверенный GitHub baseline: `d788bce9ef2d0845e9c6acfeff93c4dbf56afeed`.
Код до подготовки CI/настроек: `6a973877` (40 коммитов поверх baseline).
Публикация ветки/PR, merge, production migration, включение флагов и deploy
в этом срезе не выполнялись. Запись не заменяет Linux CI и проверку сервера.

## Что входит и почему нельзя выкатить только последний коммит

- Организация → «Участники и доступ»: карточки поставщиков, сотрудники,
  приглашения, обращения и ограниченные служебные полномочия.
- Подключение существующего кабинета с согласием владельца; отдельный план
  объединения истории с повторной проверкой прав и состава документов.
- Исправление ошибочного подключения: неиспользованная связь, заявки без ответа,
  полученные КП, точное закрытие доступа к оформленным документам и договорам.
- Подготовка правил упаковки к согласованной записи и выключенный пилот
  сокращённой блокировки при объединении.

Пилот использует history_merge, добавленный предыдущими коммитами, и цепочку
миграций 0094–0100. Отдельный cherry-pick последнего изменения на baseline
не является самостоятельным релизом. Изменения подрядчиков, большой редизайн
программы и полный перевод остальных таблиц на новые замки сюда не добавляются.

Старые глобальные `/suppliers/{id}/link-user` и `/link-duplicate` прекращают
перепривязку карточек независимо от новых флагов. Выключение пилотов не возвращает
эти небезопасные операции. Новые кнопки раздела могут показывать сообщение о
недоступности функции, пока соответствующий серверный флаг выключен.

## Проверенные зависимости и пробел CI

Граф Alembic локально имеет один head: `0100_packaging_history_guard`.
Последовательность: 0094 обращения → 0095 согласие кабинета → 0096 планы истории →
0097 ограниченный служебный доступ → 0098 отказы поддержки → 0099 исправления →
0100 DB guard правил упаковки. Это проверка графа, не выполнение upgrade на сервере.

В CI не хватало шести PostgreSQL fixture: самостоятельные счета, версии договоров,
server-schema merge, пилот упаковок, DB guard/pin и HTTP-писатель упаковок.
Они добавлены отдельным обязательным шагом с тем же disposable socket-only runner.
Используются точные классы unittest, чтобы discovery не повторял импортированные
базовые fixture в одной базе. YAML разобран, все шесть классов существуют.

Новые переключатели не были полностью перечислены в `.env.example`.
Теперь все 13 флагов participant support из runtime-кода явно заданы как 0.
Рабочие `.env` не менялись, автоматическое включение не добавлено.

## Установка и поэтапное включение

1. Проверить кандидат на Linux CI, затем выполнить браузерную приёмку по сценарию
   ниже на тестовой установке. Публичную ветку/PR не публиковать без разрешённого
   этапа публикации; для окончательной команды установки сначала нужен конкретный
   SHA в origin/main и подтверждённый состав релиза.
2. На сервере прочитать текущий SHA/ветку, tracked/untracked изменения и текущую
   ревизию Alembic. Не стирать `.env`, uploads, пользовательские резервные файлы
   или неизвестные локальные изменения ради чистого git status. Старый отчёт
   пользователя о head 0093 не заменяет повторную проверку перед установкой.
3. Проверить backup текущих данных и возможность восстановления. Порядок хранения
   материалов — [deployment-retention.md](../docs/deployment-retention.md).
4. Установить согласованный код и явно согласованную цепочку миграций при всех
   participant-флагах 0. `deploy.sh` сам вызывает `alembic upgrade head`: запуск
   этого скрипта включает изменение схемы, а не только копирование интерфейса.
5. Сверить backend SHA/health, фактический Alembic head, схему/guard без записи,
   frontend manifest/файлы и вход в кабинет. Проверить отсутствие роста ошибок.
   Один health или smoke без авторизации недостаточен.
6. Включать перечисленные ниже группы по одной, с перезапуском нужного backend
   процесса и отдельной проверкой. Существующие supplier/team/contract флаги
   сохранять по установленной конфигурации, не включать их пачкой для обхода отказа.

Все строки таблицы первоначально равны 0; `PARTICIPANT_SUPPORT_ENABLED` — базовый
серверный предохранитель для новых API. Установка схемы сама флаги не включает.

| Группа | Флаги | Что проверить до следующей группы |
|---|---|---|
| Обращения и каталог | `PARTICIPANT_SUPPORT_ENABLED` | Выбранная организация, reporter, происхождение карточки, версии статусов, чужие обращения закрыты |
| Подключение кабинета | `PARTICIPANT_CONNECTIONS_ENABLED` | Точные юридические данные, согласие основного владельца, повтор без дубля, документы другой компании не открываются |
| Просмотр истории | `PARTICIPANT_HISTORY_PREVIEW_ENABLED` | Read-only просмотр, адресные файлы, неподтверждённая принадлежность блокирует применение |
| Объединение истории | `PARTICIPANT_HISTORY_MERGE_ENABLED` | Свежий план и права, отмена/повтор, неизменность originals/оплат; сначала обычный SHARE |
| Служебное рабочее место | `PARTICIPANT_SUPPORT_ACCESS_ENABLED` | Миграции 0097/0098, обычный login/2FA/cookie, expiry/revoke, запреты прямых API/файлов/экспортов, logout и новый вход |
| Разбор исправления | `PARTICIPANT_CORRECTION_PREVIEW_ENABLED` | Реальные последствия, неизвестные цепочки не объявляются безопасными |
| Исправление связи | `PARTICIPANT_CORRECTIONS_ENABLED` | План/причина/подтверждение/аудит; сначала только неиспользованная связь |
| Отзыв заявки без ответа | `PARTICIPANT_RFQ_CORRECTIONS_ENABLED` | Нет нового ответа во время применения; повтор не создаёт новых действий |
| Отказ от полученного КП | `PARTICIPANT_QUOTE_CORRECTIONS_ENABLED` | Оформленные финансовые основания блокируют этот режим; оригинал сохранён |
| Закрытие выданного доступа | `PARTICIPANT_ISSUED_ACCESS_CORRECTIONS_ENABLED` | Точные адресаты и цепочки поставок/претензий; склад и оплаты сохранены |
| Самостоятельные счета | `PARTICIPANT_INVOICE_ACCESS_CORRECTIONS_ENABLED` | Точные счета/накладные/фото, отсутствие КП не даёт обхода, чужие документы не затронуты |
| Версии договоров | `PARTICIPANT_CONTRACT_ACCESS_CORRECTIONS_ENABLED` | Точные версии и приложения, печать и кабинет учитывают запрет, архив покупателя сохранён |
| Пилот блокировок | `PARTICIPANT_PACKAGING_HISTORY_LOCKS_ENABLED` | Последним: migration 0100, точный guard/pin, реальная запись другого поставщика проходит, источник ждёт, fallback SHARE работает |

Флаги не имеют встроенного allowlist организации: включение действует на весь
процесс. Не называть его включением «для одной компании». Перед широким включением
нужна отдельная тестовая установка и согласованное окно наблюдения.

## Сценарий браузерной приёмки

- Desktop и телефон: открыть участников именно выбранной организации, поиск,
  страницы, обращение и ответ; переключить компанию при открытом окне.
- Поставщик с карточкой из накладной: проверить связь/согласие, объединение по
  свежему плану и повтор; один кабинет, старые документы и оплаты сохранены.
- Другая организация/другой пользователь: прямые URL, файл/печать и повтор старой
  формы не раскрывают документы. Отзыв прав во время ожидания останавливает команду.
- Закрыть точный разрешённый доступ на тестовых документах; проверить одновременно
  кабинет поставщика, оригинал покупателя, файлы/договор и сохранность расчётов.
- Поддержка: login/2FA/reload/logout/вход другим пользователем, истечение/отзыв
  полномочия, прямые business API и старые формы.
- Пилот упаковок: источник ждёт, независимое правило сохраняется; таймаут и повтор
  понятны пользователю. Проверка этого сценария не доказывает перевод остальных таблиц.

Тестовые данные создавать на отдельной установке с фиксацией точных ID и удалением
только этих данных. Не разыгрывать закрытие настоящих документов на production ради smoke.

## Откат и сохранение истории

Первое действие — выключить флаг проблемной команды; для пилота упаковок 0
возвращает прежний SHARE при следующем подтверждении. Это не отменяет уже
завершённые объединения и не восстанавливает ранее закрытые права.

Сохранять поддержку запретов чтения `closedStandaloneInvoiceIds` и
`closedContractVersionIds` в `company_supplier_links.profile`. Возврат старого
backend, который не знает эти поля, может снова открыть закрытые документы.
Поэтому после первого применённого закрытия доступа нужен совместимый исправляющий
релиз, а не безусловный checkout старого baseline. Не исправлять user_id, snapshots,
суммы оплат или deny-списки вручную и не удалять append-only планы/аудит.

Downgrade 0094–0099 с историей специально блокируется. Отключение флага — основной
способ остановить новую команду. DDL guard обновлять только после табличной
SHARE ROW EXCLUSIVE блокировки, как делает 0100; на время миграции выключать пилот.

Резерв не удалять до фактических четырёх проверок backend/database/frontend/browser.
`verified.json` заранее не создавать. После успешного выпуска очистить материалы
по существующему retention-процессу, без накопления копий.
