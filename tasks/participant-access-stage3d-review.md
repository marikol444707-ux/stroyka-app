# Этап 3г: ручная бригада без аккаунта

18.10.2026. Ветка `codex/manual-brigade-identity`, база `44eb2fad`.

Ранее ручное название могло подобрать аккаунт пользователя, договор без
contractor_id открывался одноимённому исполнителю, а выбор аккаунта мог
присвоить существующий unlinked договор с тем же названием.

## Реализовано

Обе формы отправляют явную команду `contractorRef={type:'manual',requestId:UUIDv4}`
для новой бригады без карточки аккаунта. Сервер требует пустой contractorId,
не ищет пользователя и не меняет пользователей/членства. Форма создания договора
объясняет отсутствие доступа к программе. Существующий договор выбирается
по номеру и проходит серверную проверку; автоматическое открытие по имени убрано.

Миграция 0101 создаёт пустой `manual_brigade_contract_origins`: точные company,
project, contract, автор, UUID запроса и SHA256 всей команды с источником.
Исторические строки не обновляются и не получают происхождение задним числом.
Триггеры проверяют исходную компанию/объект/отсутствие аккаунта, запрещают
изменение/удаление происхождения и перенос/привязку такого договора к аккаунту.
Downgrade отказывается удалять уже используемый реестр.

Повтор одной команды возвращает тот же договор, включая параллельную отправку.
Другая команда с тем же названием создаёт отдельную бригаду. Тот же UUID с иными
полями, автором или источником даёт 409. В открытой форме ключ сохраняется при
сети/5xx; изменённая команда не замещает уже сохранённую. Повторы не меняют цены.
Сохранённый ручной договор можно повторно выбрать точной contract-ссылкой;
unlinked legacy без нового происхождения и подписанные ручные записи блокируются.

Видимость договоров/позиций, получение project/package scope, разрешённые строки
сметы и выбор договорной позиции для ЖПР больше не используют brigade_name как
доказательство аккаунта. Для исполнителя нужны точный contractor_id и текущая
компания. Договор без аккаунта остаётся в управлении уполномоченных сотрудников
компании. Выбор пользователя больше не присваивает unlinked договор по имени.

## Границы и выпуск

Сначала нужны миграция 0101 и совместимый backend, затем frontend. На установленной
базе миграция не применялась; проверена только на свежих изолированных тестовых БД
в Docker без сети/TCP, через Unix socket, без рабочей .env. Изменений реальных
данных, публикации или установки нет. При откате приложения реестр происхождения
нужно сохранять: прежний код не должен обходить новый запрет привязки к аккаунту.

Это draft/назначение работ без аккаунта. Подписание требует подтверждённой стороны
по существующему механизму; самостоятельная юридическая карточка без аккаунта,
приглашение/привязка ручной бригады и команда подрядчика ещё не реализованы.
Старые договоры, доступные ранее только по имени, больше не дают такого доступа
исполнителю: требуется отдельная проверка принадлежности без переписывания истории.

Старые клиенты без contractorRef всё ещё используют legacy resolver создания;
он не используется новыми формами. Это не устранение всех name/email эвристик
проекта. UUID живёт в открытой форме, восстановления неподтверждённой команды
после закрытия/перезагрузки пока нет: перед новым созданием нужно сверить список.
Full browser E2E, общий backend discovery, удалённый CI и VPS не проверялись.
Аудит 3а всё ещё классифицирует null contractor_id как не связанную с аккаунтом
историю; новый реестр происхождения не является разрешением на миграцию аккаунтов.
