# 2е8 — договоры при ошибочном подключении поставщика

Локальный следующий шаг, без production и реальных компаний.

Новая отдельная операция `contract-access-plans` / `revoke_contract_access`,
флаг `PARTICIPANT_CONTRACT_ACCESS_CORRECTIONS_ENABLED` (+ frontend prefix),
default-off. Сохраняет authority, immutable plan, срок, роли, компанию, версии,
epochs, повтор, audit и предыдущие ограничения 2е7.

Поддержать сохранённые версии договоров (отдельных и связанных с проверенными
КП), приложения и общие оригиналы внутри закрываемой цепочки. Registry,
snapshot, номера, статусы, оплаты и привязки документов не изменять. Список
закрываемых contract-version ID сохранять в server-owned profile точной связи.
Новая версия или другая компания не получает запрет только из-за имени/файла.

Проверить все пути: кабинет договоров, история версий КП, оригинал/приложение,
contract-context счёта/поставки. Прямой invoice context должен применять общую
invoice policy, а не только совпадение supplier_id. Никакой новой обычной
проверки/передачи/перезагрузки договора для поставщика.

Неоднозначные стороны/registry mapping/общий оригинал за пределами цепочки,
повреждённые JSON/чужие файлы/неизвестные родители блокируют команду. Проверить
полный состав registry, чтобы отзыв последней версии не показал старую.
Проекция SELECT-only; фактическая политика оригиналов до/после, digest полного
контрактного набора и повторная проверка под теми же predicate locks.

Приёмка: реальные save/revise/addendum API, standalone и mixed chain,
чужая компания, shared original, неизменность бизнес-строк, поздняя версия,
повтор/откат/конкуренция, команда поставщика, metadata/file refusals, UI/mobile.
Претензии, неправильный исторический merge, большие архивы и production writer
locks остаются следующими задачами.
