# Этап 3а: проверка старых ссылок исполнителя

18.10.2026. Ветка `codex/contractor-identity-audit`, исходный код `ec22e419`.
Этот срез выполняет предусмотренный этапом 3 dry-run старых привязок. Он не
создаёт организацию подрядчика, команду или новый пользовательский кабинет.

## Зачем нужна проверка

`brigade_contracts.contractor_id` хранит ссылку на пользователя, но старые формы
выбирают также staff ID. Существующий resolver пытается различить совпадающие
числа по имени/email. Перед переходом к явным ссылкам `user`/`staff`/`contractor`
нельзя автоматически считать любое старое число точной идентичностью.

Новый `backend.features.contractor_identity.report` проверяет одну компанию и
одну страницу договоров. В результат входят только ID договора, фиксированная
причина, кандидат ссылки `user`, счётчики и SHA-256 проверенных данных.
Имена, контакты, суммы, реквизиты и пути к оригиналам не возвращаются.
Frozen snapshot читается внутри проверки для сверки его hash/точных ID.

## Правила

- Проверяются активность компании и её platform account, точный владелец объекта,
  активность пользователя, активное членство в выбранной компании и роль
  мастер/субподрядчик/бригадир. Членство другой компании не подходит.
- Отсутствующее или отозванное членство не заменяется `users.company_id`.
  Новое членство покупателя эта проверка никогда не создаёт.
- При совпавшем user/staff ID требуется точная сохранённая связь staff с тем же
  пользователем либо проверенный frozen snapshot с явным userId. Имя и почта
  не являются доказательством. Staff ID не превращается автоматически в ID
  связанного с ним пользователя.
- У frozen snapshot проверяются schema version, hash, companyId, userId,
  projectId и contractId. Подписанный договор без snapshot и повреждённые
  сохранённые стороны требуют разбора. Бизнес-строки не исправляются.
- Даже однозначный кандидат имеет `status=review_required`, `canApply=false`,
  `accessGranted=false`, `changesMade=false`. Это диагностика для разработчика
  или оператора, не разрешение на миграцию или доступ.

## Повторение

Нужно явно настроить `CONTRACTOR_IDENTITY_AUDIT_DSN` для разрешённой проверки,
предпочтительно с отдельной DB-ролью, имеющей только SELECT. Не передавать DSN
в аргументе команды и не публиковать его. Рабочая `.env` не загружается.

```bash
python -m backend.features.contractor_identity.report \
  --company-id 2 --read-only --limit 100 --offset 0
```

`--dsn-env` позволяет выбрать другое явно заданное имя переменной. Транзакция
всегда REPEATABLE READ READ ONLY, с statement/lock timeout и rollback в finally.
Проверка требует `transaction_read_only=on`. Ошибки подключения/несовместимой
схемы возвращают фиксированный `AUDIT_UNAVAILABLE`, без текста DB-драйвера.
Runtime DDL и загрузки backend.main для запуска команды нет.

Код возврата: 0 — страница требует проверки без найденных блокеров; 1 — блокеры
страницы; 2 — проверка недоступна или параметры CLI неверны. Код 0 не означает
готовность кабинета или возможность применения.

Страница по умолчанию 100, максимум 1000 записей. При продолжении есть hasMore
и `PAGE_INCOMPLETE`. `scope=company_page_only` сохраняется и на последних страницах.
SHA-256 относится только к прочитанным данным идентичности страницы, включая
текущие ссылки и saved parties. Это не полный отпечаток финансов/файлов/договоров,
не подписанный migration plan и не общий snapshot нескольких отдельных запусков.

## Проверки и границы

Добавлены unit-тесты классификации и PG-проверки: numeric collision, запрет
подбора по имени/почте, сохранность всех строк, 50 компаний двух accounts,
pagination, изменение evidence после отзыва, SELECT-only DB-роль и реальный
отказ PostgreSQL при случайной попытке UPDATE внутри read-only транзакции.
Отдельная проверка использует существующий runtime fixture: сотрудник и договор
создаются обычными HTTP API, затем проверяются точная ссылка и отзыв членства.

Фактический итог: 57/57 профильных unit/route-тестов (12 новых и 45 существующих),
9/9 изолированных PG-проверок и 1/1 проверка runtime API. Python compile,
разбор CI YAML и diff check прошли. Логи сохранены вне Git:
`/workspace/stroyka-verification/contractor-identity/`.

Оба PG fixture подключены к обязательному CI. Прогоны используют пустые
`supply_chain_test_*` БД, пользователя chain_test и Unix socket в отдельном
локальном PostgreSQL 16; реальные данные и серверы не используются.

Пользовательский интерфейс и существующий legacy resolver не менялись. Поэтому
найденные неоднозначности ещё не устранены в старых формах. Следующий срез —
явный тип исполнителя в существующем назначении работ с сохранением точной связи.
Собственная организация/команда подрядчика, юридическая идентичность по ИНН,
миграционный apply с drift guards и выдача новых прав остаются дальнейшей работой.
Миграций, enablement, публикации и установки не выполнялось. Frontend/browser,
общий backend discovery и удалённый CI в этом срезе не запускались.
