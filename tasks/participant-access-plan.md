## Threat model и границы

Активы: архивы покупателей, адресные документы поставщика, полномочия команды,
исторические snapshots/оплаты, служебная история. Недоверенные источники:
браузерные IDs/заголовки, aliases/имена/контакты, старые ссылки, задержанные ответы,
модель/worker и записи с неопределённым владельцем. Сервер заново проверяет
membership/account/роль; диагностика принадлежит точному reporter; UUID не даёт
доступа. Служебные API не читают банковские поля, файлы и чужие отношения.
Ни диагноз, ни исправление статуса не создаёт invite/stock/payment или кабинет.
Сохранение истории не оставляет доступ бывшему сотруднику. Internal notes должны
быть отдельны от публичного результата; до этапа переписки их нет.

## Этапы и критерии окончания

### 0. Аудит и архитектура
Карта выше, ADR0008, матрица прав. Остаток: полный route-by-route inventory
экспортов/WS/jobs и субподрядчика перед расширением их полномочий; read-only
диагноз реального «Сатурна» при наличии разрешённого источника. Не блокирует этап 1.

### 1. Служебный вертикальный этап
Организация → реальные supplier links → отказ с кодом → отдельное обращение →
администратор выбранной организации → история статусов → результат автору.
Не меняет user_id, memberships, aliases, snapshots или документы.
Критерии: практические PG rollback/forgery/revocation/concurrency/dedup/schema tests;
50 организаций из нескольких аккаунтов; поиск/пагинация >100 строк; мобильный и
десктопный браузер; поздний ответ после смены организации; build и регрессии.
Статус: вертикальный код реализован; профильные PG/RTL, build и браузер проверены
локально. Полный backend имеет воспроизведённые на baseline ограничения PDF
этого Mac; mandatory Linux CI и production не проверены.
Отчёт: [participant-access-stage1-review.md](participant-access-stage1-review.md).

### 2. Сотрудники и безопасные административные операции
Добавить реальные employees/invites views по verified memberships, без объединения
users/staff ID. Supplier connection — отдельная команда: server-built preview,
выбранная company/account, owner proof, expected versions, effects, confirmation,
atomic audit и повторная авторизация. Не очищать чужие suppliers.user_id.
Company merge переиспользуется с его предохранителями; исправление ошибочной
связи — отдельная операция, учитывает документы после ошибки, не универсальный undo.
Support capability ограничивает обращение/company/action/expiry/revocation;
проверить прямые URL/файлы/экспорт/старые формы. Выдача спорных прав отдельно.

### 3. Многоклиентский подрядчик
Собственная организация и команда; заказчики/договоры/объекты/бригады/назначения/
выполнение/акты/разрешённые расчёты/обращения. Explicit manager/brigadier scope.
Общая проверенная юридическая идентичность с отдельными supplier/contractor
отношениями; одинаковые бренды с разными ИНН остаются разными сторонами.
Legacy migration только dry-run доказуемых typed links; ambiguity stops apply;
plan drift guards/idempotency/восстановление. Не добавлять членство покупателя.

### 4. Масштабирование и операционная работа
Полная синтетическая матрица: ≥50 организаций нескольких аккаунтов, общий supplier
и contractor, owners/managers/brigadiers/internal staff; больший paged dataset.
Отзыв, смена роли, замещение, закрытие обязательств после suspension, исторический
адресный доступ, открытые формы/cookies/cache, jobs/WS/exports, ретраи timeout и
lock-order гонки; двухсторонние обращения, internal notes, attachments, очередь
уведомлений со статусом фактической доставки и без реальных отправок в тестах.
Retention диагностик/спам (базовый user advisory limit уже в этапе 1) и связь обращений
одного дефекта без раскрытия другого tenant. SLA/приоритеты только настраиваемые.
Измерять baseline на известном оборудовании/объёме, затем назначать бюджет задержки.

### 5. Приёмка и отдельный выпуск
Все 13 сценариев исходного задания, полный mandatory CI и реальный browser E2E
в изолированной среде. Затем review diff/пакет миграции/canary/backup/rollback;
public push и production apply/enable/deploy требуют явного разрешения.
Отдельно backend/database/frontend/browser checks по deployment-retention.md;
до них не ставить verified.json и не удалять резерв. Не объявлять весь контур
готовым после первого этапа.

## Какие проблемы решает раздел организации

Путь: кабинет владельца платформы → Аккаунты/компании → нужная организация →
«Участники и доступ». Сначала только реальные поставщики этой компании.
Другие типы появятся после подключения их настоящих источников.

| Задача | Что нужно видеть | Действие / этап |
|---|---|---|
| Не удаётся пригласить поставщика | Организация, карточка, точная причина, из накладной/по ссылке/вручную/неизвестно, роль, версия, время, история | Уже: разобрать обращение и ответить; исправление прав отдельно |
| Сотрудник не видит объект | Активные memberships, effective role и назначения этой компании | Реальные списки и диагностика — этап 2 |
| Карточка из накладной и кабинет по ссылке | Доказанная юридическая идентичность, source/target, версии, конфликты, влияния на документы | Existing company merge / отдельное подключение — этап 2 |
| Два зарегистрированных кабинета одной стороны | Подтверждения владения и конфликт | Спор ownership, не автоматический merge |
| Подрядчик работает у многих покупателей | Собственные договоры, команда, назначенные объекты | Многоклиентский кабинет — этап 3 |
| Отключили участника или сменили менеджера | Что прекращается, кто принимает обязанности, какие архивы разрешены | Явное замещение/отзыв — этап 4 |
| Ошибочно подключили/объединили | Исходная операция и документы/действия после неё | Корректирующая операция с preview, не универсальный undo |
| Технический сбой / недействующая ссылка | Безопасный код, correlation, экран, собственные IDs, версия | Расширение диагностики, без повтора business command |
| Претензия по поставке / экономический спор | Отдельный тип обращения, ответственный покупатель/контрагент | Маршрутизация, не автоматическая отправка владельцу платформы — этап 4 |

Форма ручного обращения из «Помощи», переписка, вложения, внутренние заметки,
уведомления и маршрутизация к директору/менеджеру пока не реализованы. Первый
этап даёт один вход рядом с подтверждённым отказом; это явное ограничение.

## Правила для следующих этапов

Четыре разных понятия: человек users, клиентский аккаунт platform_accounts,
юридическая сторона suppliers/contractor identity, отношение с покупателем.
Одна сторона может иметь несколько ролей, но разные ИНН нельзя объединять по
бренду. Команда принадлежит стороне, назначения менеджера — отношениям.
Договоры/объекты/бригады не создают общий доступ к покупателю.

Первая регистрация, подключение существующего кабинета, член внешней команды,
внутренний сотрудник и исполнитель договора имеют разные серверные типы
приглашений. Перед принятием повторно проверяются инициатор, адресат,
expiry/revocation, версия и полномочия; одновременное принятие атомарно.
Повторное включение не восстанавливает старые назначения автоматически.

Приостановка новых закупок у A не блокирует B и разрешённое закрытие обязательств
A. Архив завершённого договора сохраняется, но читается только текущими
уполномоченными представителями и точным адресатом. Уволенный сотрудник не
сохраняет архив через старую сессию. Авторство/суммы/банк/подписи выпущенных
документов неизменны; действующий адресный договор не требует нового
обязательного подтверждения для каждого счёта.

Очередь поддержки не даёт бизнес-полномочия: отдельные capability имеют
company/account, ticket, action, назначенного администратора, expiry/revocation
и аудит использования. Чтение, скачивание, поиск, экспорт, счётчики,
notifications/jobs/WS проверяют текущую область на сервере. Уже произошедшее
раскрытие файла нельзя отменить, но дальнейшее чтение прекращается.
