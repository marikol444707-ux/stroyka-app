# План реализации: договоры клиентов платформы

## Обзор

Добавить договор на использование «СтройКа» в существующую карточку компании-клиента. Правообладатель хранится отдельно, договор фиксирует снимок тарифа и связывает существующие счета, акты и оплаты. Реализация идёт вертикальными срезами и не изменяет тестовую компанию ИП Буцькина.

## Архитектурные решения

- Отдельный `platform_licensor_profiles`: правообладатель не является компанией-клиентом.
- Отдельный `platform_client_contracts`: один клиент может иметь историю договоров.
- Тариф, цена и лимиты сохраняются в договоре снимком, чтобы последующее изменение тарифа не переписало подписанный документ.
- Межфирменные связи защищаются составными внешними ключами `(client_contract_id, company_id)`.
- Старые счета и оплаты остаются валидными: ссылка на договор необязательна.
- UI встраивается в `SystemOwnerCabinet`, отдельный кабинет не создаётся.
- Все операции записи сначала проходят preview/валидацию и записываются в `platform_audit_log`.

## Зависимости

```text
Alembic-схема
  -> доменные проверки и API preview
    -> создание/статусы договора
      -> PDF и подписанный файл
        -> привязка счетов и оплат
          -> единая секция в карточке клиента
            -> production smoke и поэтапный деплой
```

## Этап 1. Схема и доменная модель

### Задача 1. Миграция договорного контура

Добавить профиль правообладателя, договоры клиентов и необязательные безопасные ссылки из счетов и оплат.

**Критерии приёмки:**

- миграция идемпотентно поднимается с текущей Alembic head;
- старые строки счетов и оплат не меняются;
- база запрещает ссылку документа или оплаты на договор другой компании.

**Проверка:** unit-тест миграции, `python3 -m alembic upgrade head` на временной БД, downgrade/upgrade round-trip.

**Файлы:** новая миграция, тест миграции, `migrations/README.md`.

### Задача 2. Чистые функции договора

Добавить нормализацию реквизитов, preview, генерацию номера, проверку сроков, переходов статуса и полноты сторон.

**Критерии приёмки:**

- неполные реквизиты дают понятные blockers без записи;
- повторный запрос с тем же idempotency key не создаёт второй договор;
- запрещены пересекающиеся действующие договоры одного типа.

**Проверка:** отдельные unit-тесты доменного модуля.

**Файлы:** доменный модуль и его тест.

## Контрольная точка 1

- схема и unit-тесты проходят;
- никаких production-записей и изменений существующих клиентов;
- обзор структуры до подключения API.

## Этап 2. Сквозное создание договора

### Задача 3. API профиля правообладателя

Добавить чтение и изменение реквизитов правообладателя для системных ролей.

**Критерии приёмки:**

- чтение доступно разрешённым системным ролям;
- изменение доступно только управляющим ролям;
- изменение журналируется и не затрагивает компании-клиенты.

**Проверка:** API contract-тесты ролей и аудита.

**Файлы:** routes/helper и тесты platform admin.

### Задача 4. Preview и создание договора

Добавить список, preview и создание договора с серверной нумерацией и защитой от дубля.

**Критерии приёмки:**

- данные компании и тарифа подставляются автоматически;
- preview не пишет в БД;
- двойное нажатие возвращает тот же результат либо конфликт, но не создаёт дубль.

**Проверка:** API contract-тесты, тест транзакции и принадлежности компании.

**Файлы:** routes/helper и тесты.

### Задача 5. Минимальная секция договора в карточке клиента

Показать действующий договор и форму создания внутри существующей карточки компании.

**Критерии приёмки:**

- нет нового дублирующего раздела;
- известные поля уже заполнены;
- blockers показаны человеческим языком;
- кнопка блокируется на время запроса.

**Проверка:** React-тест и production build.

**Файлы:** `SystemOwnerCabinet.jsx`, helper при необходимости, frontend-тест.

## Контрольная точка 2

- администратор может создать безопасный черновик из карточки клиента;
- клиентские данные и оплаты не меняются;
- backend tests и frontend build зелёные;
- ручной обзор UX до PDF и статусов.

## Этап 3. Документ и жизненный цикл

### Задача 6. PDF и подписанный файл

Сформировать PDF договора и зарегистрировать защищённый подписанный файл через существующее файловое хранилище.

**Критерии приёмки:**

- PDF содержит снимок реквизитов обеих сторон и условий;
- файл хранится в защищённом контуре компании;
- генерация PDF не активирует договор;
- замена подписанного файла журналируется.

**Проверка:** unit-тест PDF-данных, файловый contract-тест, визуальная проверка PDF.

**Файлы:** PDF/helper, routes и тесты.

### Задача 7. Статусы и клиентское чтение

Добавить разрешённые переходы статуса и безопасное чтение/скачивание для директора клиента.

**Критерии приёмки:**

- активировать можно только полный договор;
- клиентский директор не может менять договор;
- прекращение не удаляет историю;
- каждый переход попадает в аудит.

**Проверка:** матрица ролей и переходов в API-тестах.

**Файлы:** routes/helper, тесты, существующий клиентский экран документов.

## Этап 4. Счета, акты и оплаты

### Задача 8. Привязка биллинговых документов

Добавить выбор договора при создании счета/акта и показывать связанные документы в карточке.

**Критерии приёмки:**

- нельзя выбрать договор другой компании;
- документы без договора продолжают работать;
- номер договора отображается в PDF счета/акта.

**Проверка:** backend contract-тесты и frontend-тест формы.

**Файлы:** routes/PDF, `SystemOwnerCabinet.jsx`, тесты.

### Задача 9. Привязка оплаты и итоговая сводка

Связать ручное зачисление оплаты с договором и вывести оплачено/долг/период в карточке клиента.

**Критерии приёмки:**

- оплата другой компании отвергается;
- автоматического зачисления нет;
- суммы считаются из существующего журнала оплат;
- старые оплаты без договора учитываются в общей истории, но помечены как несвязанные.

**Проверка:** backend/API тесты, frontend-тест сводки.

**Файлы:** routes/helper, `SystemOwnerCabinet.jsx`, тесты.

## Контрольная точка 3

- полный поток «клиент -> договор -> счёт/акт -> оплата» работает;
- все роли и межфирменные границы проверены;
- smoke-check расширен новыми маршрутами;
- перед production-миграцией требуется отдельное подтверждение пользователя.

## Риски и защита

| Риск | Влияние | Защита |
|---|---|---|
| Правообладатель ошибочно считается клиентом | Высокое | Отдельная таблица профиля правообладателя |
| Смешение данных компаний | Высокое | Составные FK, серверная проверка и role tests |
| Изменение тарифа переписывает договор | Высокое | Снимок условий внутри договора |
| Двойное нажатие создаёт дубликаты | Среднее | idempotency key и уникальные индексы |
| Неполные реквизиты попадают в PDF | Среднее | Preview blockers и запрет активации |
| Новая функция усложняет кабинет | Среднее | Встроенная секция в существующей карточке |

## Не входит в этот блок

- ЭДО и электронная подпись;
- автоматическое подтверждение банковских платежей;
- архивирование тестовой компании;
- договоры стройкомпании с заказчиками строительства;
- договоры с бригадами и поставщиками.
