# Пилот: запись правил упаковки и объединение истории поставщика

Цель: дать другой организации сохранять независимое правило упаковки во время
объединения карточки поставщика. Общую защиту остальных таблиц сохранять.

Предикат упаковок в манифесте — `supplier_id=source_id`, поэтому общий ключ
должен защищать именно исходного поставщика во всех организациях, включая
добавление чужой истории без каталожной связи. Для этого выделяется namespace
advisory-замков `94101`; обычная запись берёт shared transaction lock.
Авторизованная подготовка схемы выполняется отдельно в autocommit и не держит
DDL-замки через бизнес-запись. Затем runtime-писатель начинает транзакцию,
берёт ключ поставщика, повторно проверяет компанию и роль, блокирует строку
правила и выполняет запись с commit/rollback.

Первый срез: подготовить единственный runtime-писатель, сделать сохранение одной
транзакцией и проверить реальные HTTP-команды в disposable PostgreSQL. Shared
ключи между обычными писателями совместимы. Этот срез сам по себе не меняет
блокировки объединения и не обещает устранения задержек других компаний.

Следующий срез: обеспечить тот же протокол на уровне базы для прямого SQL,
UPDATE со сменой старого/нового поставщика и DELETE; проверить DDL/TRUNCATE и
только затем добавить выключенный по умолчанию режим подтверждения с более
слабой табличной блокировкой. Нельзя ослабить `SHARE` только потому, что один
API-писатель уже подготовлен. Ветка остаётся локальной, production-миграции и
включение режима выполняются отдельно после проверки.

Критерии первого среза: конкурентная запись ждёт эксклюзивный ключ того же
поставщика до SQL-изменений; другой поставщик сохраняется; shared ключ держится
до commit; ошибка/таймаут откатывает запись и освобождает ключ; существующие
проверки прав компании сохраняются. Никаких новых действий в интерфейсе.

Семантика замков: [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html).

## Первый срез реализован локально

После авторизованной подготовки схемы `create_material_packaging_rule` явно
отключает autocommit, берёт shared ключ поставщика и повторно разрешает компанию
перед бизнес-записью. Ключ не освобождается между SQL-запросами этой транзакции.
DDL подготовки таблиц не удерживается до её commit. Для ожидания установлен таймаут
3 секунды; конфликт возвращает HTTP 409 с предложением повторить сохранение.
Запросы правил без `supplier_id` не берут чужой ключ. Новых UI-действий нет.

Регрессия на исходном обработчике воспроизведена: HTTP-запись не ожидала
удерживаемого ключа поставщика. После изменения проверены ожидание и освобождение
ключа, независимый ключ/организация, совместимость shared писателей, сохранение
и изменение одной записи, отказ чужому company context, откат при ошибке кода
и ошибке PostgreSQL, безопасный повтор после таймаута. Отдельно проверен отзыв
членства сотрудника во время ожидания ключа: повторная авторизация отклоняет
сохранение. Два независимых HTTP-писателя проходят подготовку параллельно, не
удерживая DDL-замки через бизнес-транзакцию.

Итог проверок первого среза: 9 PostgreSQL/HTTP тестов писателя, 14 существующих
unit-тестов упаковок и 8 PostgreSQL тестов манифеста/объединения прошли (31/31).

Кроме runtime создания/изменения найдены прямые удаления в
`scripts/smoke-material-packaging-review.py`. Без миграции защиты эти удаления
по-прежнему прикрывает общий `SHARE`. Само объединение пока не берёт namespace
`94101`, и ускорение независимых компаний в полном процессе ещё не реализовано.

## Второй срез: защита прямых SQL-писателей

Миграция `0100_packaging_history_guard` устанавливает `BEFORE ROW` триггер на
`INSERT`, `UPDATE`, `DELETE`. Он берёт shared transaction lock для каждого
непустого старого и нового `supplier_id` в сортированном порядке. Это закрывает
и прямые удаления cleanup-скрипта, и SQL/COPY, обходящие HTTP-обработчик.
Используется `ENABLE ALWAYS`, фиксированный `pg_catalog` search path и invoker
права; дополнительных полномочий функция не выдаёт. Настройка упаковок выделена
в канонический `schema.py`, используемый runtime и миграцией без дублирования DDL.

Установка, повторная установка и downgrade не изменяют бизнес-строки. Миграция
создаёт ленивые таблицы упаковок, если ими ещё не пользовались. Удаление защиты
при downgrade не удаляет эти таблицы или их содержимое. Production миграция
не выполнялась; новая общая схема остаётся выключенной/неподключённой к merge.

Проверены прямые вставки/изменения/удаления, переходы между поставщиками и NULL,
удержание обоих ключей до rollback, запись другой компании с тем же поставщиком,
COPY и работа триггера при replica mode в disposable БД. Контрольная пустая
функция дала ожидаемые три отказа тестов DML. Runtime функция восстановлена.
В тестовой модели `ROW EXCLUSIVE` совместим с независимой DML и удерживает
`TRUNCATE`/отключение триггера до конца транзакции; DDL-проверки откатываются.

Ограничения перед третьим срезом: триггер получает ключ после внутреннего
захвата строки при UPDATE, а сортировка двух ключей внутри одной строки не
задаёт порядок для произвольных многострочных скриптов. Нужны проверка отказа
при обратном порядке, повтор после deadlock, проверка точного guard-контракта
и устранение bootstrap DDL из пути записи в новом режиме. На момент второго среза API всё ещё
запрашивает bootstrap DDL перед каждой записью; при более слабом табличном замке
это тоже могло бы задержать другую компанию. Поэтому `SHARE` пока не ослаблен.

Проверки второго среза: 6 PostgreSQL тестов DB-защиты, 9 HTTP/транзакционных
тестов с установленным триггером, 14 unit-тестов упаковок и 8 тестов объединения
прошли (37/37). Bootstrap миграции проверен также после удаления пустых ленивых
таблиц в disposable fixture. Граф Alembic имеет один head
`0100_packaging_history_guard`; ни миграция, ни downgrade на production не запускались.

## Третий срез: готовая схема без повторного DDL

Реальный HTTP-регрессионный тест выявил лишний конфликт: при удержании
`ROW EXCLUSIVE` на таблице упаковок сохранение другого поставщика возвращало
409 ещё на bootstrap DDL. Прямой SQL в той же ситуации уже проходил.

POST сохранения правила после авторизации теперь читает каталоги PostgreSQL:
проверяет наличие используемых колонок обеих таблиц и готовность двух индексов
(включая уникальность индекса идентичности). При готовой схеме DDL не выполняется.
При отсутствующей таблице, колонке или индексе остаётся прежняя подготовка схемы.
Проверка выполняется заново для каждого запроса без process-cache. Это только
проверка готовности bootstrap, **не** проверка корректности guard-триггера и
не основание ослаблять блокировки объединения.

Регрессия до исправления: HTTP 409 вместо 200 под слабым табличным замком.
После исправления HTTP сохраняет правила другого поставщика и без поставщика
в той же ситуации. Проверены восстановление отсутствующей таблицы reviews,
колонки review_decision и каждого индекса с сохранением исходных строк.
Все изменения схемы в этих проверках откатываются в disposable PostgreSQL.
Итог: 14 unit + 7 DB guard/bootstrap + 9 HTTP/транзакционных + 8 merge =
38 проверок прошли; `git diff --check` без ошибок.

Далее остаются проверка точного guard-контракта и выключенный по умолчанию
режим merge. Обратный порядок и безопасный повтор проверены в четвёртом срезе.
Общий `SHARE` объединения пока сохранён; сервер не менялся.

## Четвёртый срез: реальные deadlock и безопасный повтор

Два дополнительных теста создают настоящий цикл ожиданий в disposable PostgreSQL:

- HTTP сохранения уже держит shared ключ поставщика и ждёт строку упаковки;
  прямой SQL-писатель держит эту строку и запрашивает exclusive ключ поставщика.
- Объединение держит SHARE на упаковках и ждёт таблицу счетов; прямой писатель
  изменяет счёт и затем пытается вставить правило упаковки в обратном порядке.

В обоих случаях существующая обработка DeadlockDetected возвращает HTTP 409
с просьбой повторить операцию. Проверены неизменность исходных строк после
отката конфликтующих транзакций, отсутствие присвоения владельца/применения
плана/аудита до повтора, освобождение ключа и успешный повтор. Повтор объединения
создаёт ровно одно событие аудита. Таймауты обнаружения deadlock изменяются только
для блокирующей тестовой транзакции, не для рабочего сервера.

Контрольное удаление обработки DeadlockDetected из каждого обработчика по
отдельности сломало соответствующий тест с реальным PostgreSQL DeadlockDetected.
После каждого контрольного прогона runtime файлы восстановлены. Обработчики не требуют
изменений: этот срез добавляет практическое доказательство уже существующего
отката, не включает новый режим объединения и не ослабляет SHARE.

Ограничение: будущий режим с ключами поставщика ещё должен пройти собственные
конкурентные тесты. Проверка текущего merge не доказывает корректность ещё не
реализованного порядка захвата ключей.

Итог четвёртого среза: 14 unit + 8 DB guard/bootstrap/deadlock + 9 HTTP +
9 merge = 40 проверок прошли. Контрольные отказы без обработки deadlock
получены отдельно для обоих обработчиков. `git diff --check` без ошибок.

## Пятый срез: точная диагностика guard-контракта

`packaging_guard_ready(cur)` читает каталоги PostgreSQL без исправлений и без
изменения бизнес-строк. Принимается только обычная таблица без наследования с
целочисленным supplier_id, единственным пользовательским триггером BEFORE ROW
на INSERT/UPDATE/DELETE, включённым ALWAYS без WHEN, аргументов и ограничений
по колонкам. Проверяется точная функция public/plpgsql, invoker-права, volatile,
parallel unsafe, отсутствие STRICT/leakproof, фиксированный search_path и точное
тело функции с namespace 94101. Каноническое тело выделено из GUARD_SQL без
изменения SQL установки миграции — строки до/после побайтно совпадают.

Интеграционная матрица отклоняет выключенный/обычный/replica триггер,
отсутствующий триггер или таблицу, другой namespace, WHEN(false), другие события,
AFTER/statement trigger, аргументы, SECURITY DEFINER, изменённый search_path,
IMMUTABLE/parallel safe/STRICT, переименованный supplier_id, дополнительный
пользовательский триггер и наследование. Каждый эксперимент откатывается;
готовность проверена с tuple и RealDictCursor. Дополнительные триггеры
консервативно требуют проверки: более поздний BEFORE-триггер мог бы изменить
supplier_id после получения ключа.

**Обнаруженное ограничение:** ROW EXCLUSIVE удерживает изменения триггера,
но не CREATE OR REPLACE самой функции. Отдельный конкурентный тест заменяет
её тело при удерживаемом слабом табличном замке, после чего диагностика даёт
false. В finally каноническая функция восстанавливается. Положительный результат
диагностики — снимок состояния, не гарантия его неизменности до commit.

Перед подключением сокращённого режима нужно закрыть конкурентную замену
функции: проверить права/владельцев DDL и закрепить протокол её обновления либо
выбрать другую проверенную защиту. Простое условие `if packaging_guard_ready`
в merge небезопасно. Новый диагностический helper пока не вызывается из merge;
старый SHARE сохранён, feature flag сокращённого режима не добавлен.
Сервер, права production-ролей и рабочие данные не изменялись.

Итог пятого среза: 14 unit + 10 DB guard/readiness/bootstrap/deadlock +
9 HTTP + 9 merge = 42 проверки прошли; SQL установки миграции побайтно
совпадает с предыдущим; `git diff --check` без ошибок.
