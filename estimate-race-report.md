## Обязательный переход старых вкладок

Новый frontend не меняет уже исполняющийся JavaScript. Старый клиент игнорирует
428; сервер не может заставить его показать сообщение или выгрузить черновик.
Поэтому выбран согласованный переход с участием пользователей, а не попытка
совместимого сохранения без ревизии. Ни proxy, ни backend не должны добавлять
expectedRevision из последнего GET к старому снимку: это снова разрешило бы
перезапись чужих изменений.

### До переключения backend/frontend

1. Ответственный за выпуск связывается с пользователями **вне приложения** и составляет список открытых редакторов: пользователь/устройство/вкладка, companyId, estimateId. Учитываются мобильные, спящие и временно offline устройства. По сетевым логам нельзя доказать отсутствие таких вкладок. Здесь уведомления никому не отправлялись.
2. Пользователи прекращают ввод, не закрывают вкладку, не выходят из аккаунта и не обновляют страницу. Отдельно копируют текст в незавершённых формах: новая ещё не добавленная строка, открытая модальная форма и черновики ЖПР могут не входить в selectedEstimate. Для новых данных не ждать, что старый клиент подтвердит сохранение: он подавляет ошибки.
3. До действий, способных вызвать старый autosave, включить окно обслуживания: на внешнем API закрыть mutations до backend, дождаться завершения уже принятых операций, остановить фоновые writers. Не перенаправлять запросы на вход и не использовать 401/принудительный logout как сигнал обновления. Пока черновики не скопированы, ключи/сессии не менять. На время capture обеспечить отсутствие 401/redirect также для фоновых API и CSRF-запросов: обслуживать их ответом 503 до auth/backend, пока копии не подтверждены; старую статику продолжать отдавать без изменения. Применение и проверка этого ограничения в реальной среде — обязательный шаг владельца выпуска, здесь оно не устанавливалось.
4. До подтверждения копий не переключать index/manifest/sw.js, не удалять старые static chunks и не инвалидировать кеши. В текущем исходном клиенте `src/api.js` вызывает reload при 401, а `src/registerServiceWorker.js` — при ChunkLoadError. Разрушение старых assets способно перезагрузить вкладку ещё до ручного обновления. Не использовать такой механизм для миграции черновиков.
5. С помощью ответственного специалиста сохранить **полный JSON локального снимка**, как описано ниже, и отдельно незавершённые поля/формы. Проверить копию с пользователем. Если копии неполны или владелец недоступен, не считать этот редактор готовым к переходу; не выполнять его принудительную перезагрузку. Если невозможно подтвердить охват всех редакторов, согласованный переход откладывается.

### Как сохранить локальный снимок без записи на сервер

Этот путь проверен на настоящем старом persistEstimateAction и EstimateSectionsEditor
в отдельном браузерном fixture с отклонением запросов до backend. Он требует
помощи специалиста, но не изменения кода уже открытой вкладки.

1. **Сначала убедиться, что запись заблокирована до backend.** Нельзя проверять это отправкой старого черновика в рабочий backend, который ещё принимает PUT без ревизии. В тесте gate вернул 503, счётчик forwarded остался нулевым.
2. Открыть DevTools → Network в существующей вкладке, включить запись запросов/Preserve log. Не обновлять страницу. Для уже загруженной строки сметы поставить фокус в поле наименования и убрать фокус, не меняя значение: существующий onBlur формирует PUT всего текущего selectedEstimate. Дождаться именно отклонённого PUT `/estimates/<нужный ID>`; не нажимать Replay/Resend.
3. Скопировать **только Request Payload в исходном JSON-виде** последнего запроса в локальный файл `company-<ID>-estimate-<ID>-draft.json`. Не копировать response: он содержит ошибку, а не черновик. Не использовать HAR/cURL/заголовки авторизации для резервирования черновика. Файл хранить отдельно для каждой компании и вкладки.
4. Открыть сохранённый JSON, проверить синтаксис, ID/компанию, число разделов/строк и последние изменения вместе с пользователем. Убедиться, что sections полностью загружены. Если данных нет, тело урезано, строка не соответствует вкладке или capture недоступен — вкладку не обновлять; требуется ручная копия всех изменений с проверкой полноты. После capture можно записать SHA256 файла для контроля неизменности.
5. Добавить отдельно содержимое ещё не добавленной строки/открытых форм, намерение удалить строки и спорные изменения, которые пользователь помнит. Excel из меню «Ещё» можно приложить как читаемую копию, **но не как единственную резервную копию**: он выгружает лишь часть полей, без полного JSON/метаданных. JSON тоже не включает формы, ещё не внесённые в selectedEstimate.
6. Зафиксировать подтверждение пользователя: «копия открывается, последние правки присутствуют, незавершённые формы сохранены отдельно». Только после этого разрешается закрыть старую вкладку. Копии не удалять до сверки и подтверждённого сохранения новым клиентом.

В новой проверке `recovered-draft.json` совпал с исходящим телом; сохранились
отредактированное имя и поля hiddenWork/importCode/comment, которые не покрывает
обычный Excel. Это проверяет механизм capture. Полноту реального пользовательского
черновика подтверждают пользователь и ответственный, а не тест с синтетическими данными.

### Переключение и восстановление работы

1. После подтверждения всех копий зафиксировать каноническое серверное состояние и резерв БД. Оставить запись закрытой, остановить все старые backend writers; выполнить 0103 и запустить новый backend. Строгий отказ без expectedRevision действует сразу, без grace period и fallback.
2. Установить согласованный frontend, проверить backend/схему/assets. Пользователи с подтверждёнными копиями закрывают старые вкладки и открывают новую сборку; это явное действие после сохранения данных, не массовый forced reload. Проверить фактически загруженную сборку и наличие revision в GET.
3. На время сверки назначить одного редактора на смету. Открыть актуальную смету нужной компании и сравнить её с сохранёнными черновиками. Внести вручную только согласованные изменения в новый редактор. Не импортировать старый JSON как слепую замену всего объекта и не отправлять его с подставленной текущей expectedRevision. Если исходной базы сравнения нет, намерение пользователя требует ручной сверки; по одному отличию снимков его определить нельзя.
4. После технических проверок открыть доступ к записи согласованно, сначала для завершения сверки; новый PUT формирует штатный клиент из актуальной модели. Дождаться 200 с новой revision и проверить чтением результата, затем получить подтверждение пользователя. При 409 сохранить новый локальный черновик, остановить сверку и заново сравнить; не менять revision для автоматического повтора.
5. Для журналов/расхода отдельно сверить уже проведённые операции и незавершённый outbox. Нельзя менять тело старого requestId, автоматически дополнять старую команду ревизией или повторять списание как новую операцию без проверки результата предыдущей. Уже завершённые операции сохраняют штатную идемпотентность.
6. Завершать окно только после подтверждения всех пользователей/вкладок из списка. Неизвестная старая вкладка всё равно получит 428 без перезаписи, но сообщения в её UI не будет: при таком обращении повторяется процедура сохранения копии до refresh. ## Причина и исправление

Раньше блокировка строки сериализовала PUT, но не проверяла, на каком снимке
основан запрос. Поэтому поздний старый PUT мог перезаписать уже сохранённые
правки. Обычное сохранение также подавляло ошибки и запускало фоновые проверки
старого снимка. Защиты только при загрузке/восстановлении было недостаточно.

Теперь `estimates.revision` — серверный BIGINT, начальное значение 1. Клиент
передаёт `expectedRevision`. В транзакции сервер проверяет владельца/компанию,
блокирует строку, сравнивает ревизию до изменений и сохраняет данные вместе
с увеличением ревизии. Триггер увеличивает её при любом UPDATE, включая
внутренние изменения статуса и количества выполненных работ. PUT дополнительно
содержит revision в условии UPDATE. После всех внутренних изменений возвращается
итоговая ревизия транзакции. Отклонённая запись не создаёт историю/побочные записи.

- 409 `estimate_revision_conflict`: ревизия устарела; ответ содержит ожидаемую и текущую ревизии.
- 428 `estimate_revision_required`: ожидаемая ревизия отсутствует.
- 422 `estimate_revision_invalid`: неверный тип/диапазон; отсутствующее обязательное тело также может дать стандартный 422 FastAPI.
- Чужая компания не получает ревизию: отказ существующей авторизации или 404.

Ревизия не определяет, какие пользовательские правки «новее». Из двух запросов
с одной базовой ревизией проходит первый зафиксированный; второй получает 409.
Старый PUT уже не заменит более новую зафиксированную ревизию. Отмена ожидания
ответа в браузере сама по себе такой гарантии не даёт.

Редактор различает ID, сессию открытия, локальную ревизию правок и номер запроса.
Локальная ревизия отличается от серверной. Поздние ответы не меняют редактор,
dirty-флаг, статус, ошибки или список и не запускают quality/norm-проверки.
Закрытие, повторное открытие того же ID и смена компании инвалидируют запросы.
Успешная запись метаданных не объявляет несохранённое содержимое сохранённым.
При 409 показано сообщение: скопировать правки отдельно, обновить данные и сравнить.
`currentRevision` из ошибки не принимается как новая база; автоматического повтора нет.

## Несовместимости и оставшиеся ограничения

- Новый backend требует миграцию 0103. Старые клиенты/интеграции без expectedRevision получают 428/422. Новому frontend нужен backend с revision в GET/ответах записи. Нет обхода проверки для старых клиентов.
- PUT/status/include-changes требуют expectedRevision в JSON; toggle-template и ai-detect-hidden теперь тоже требуют JSON-тело; DELETE — query-параметр. Старые незавершённые outbox-операции без ревизии отклоняются, не перебазируются автоматически. Ранее завершённые операции повторяются с исторически сохранённым форматом ответа.
- Быстрые пересекающиеся сохранения одной вкладки могут конфликтовать между собой. Если после начала PUT были правки, его ответ полностью игнорируется, включая server revision; следующий PUT может получить 409. Очередь отправки, merge и автоматическое повторное сохранение не добавлены.
- Локальные правки сохраняются в памяти открытого редактора, не гарантируется восстановление после перезагрузки/закрытия страницы. Перед обновлением их нужно скопировать отдельно.
- Уже начавшуюся актуальную фоновую проверку нельзя отозвать этим исправлением. Проверяется актуальность до запуска и между последовательными проверками; внешний AI/исполнители очередей не интеграционно проверялись.
- Узкий PG-harness подменяет внешние эффекты, часть нормализации и входной контекст авторизации. Финальная проверка дополнительно прошла настоящую HTTP-аутентификацию складского пути; полный production schema остаётся непроверенным; запуск в поддерживаемом Python теперь прошёл, см. текущие результаты выше.
- Успешный v2-процесс складского списания/ЖПР теперь проверен через HTTP: 10/10 тестов, плюс 5/5 legacy. Это два затронутых набора общего supply-chain fixture, а не весь закупочно-складской продукт. Браузерный ввод складских документов и внешние интеграции не проверялись.
- Существующий create_estimate архивирует соседние активные сметы и вставляет новую без общей транзакции. Старый снимок существующей сметы он не записывает, триггер повышает ревизии, но атомарность выбора единственной активной сметы при конкурирующем создании — отдельная нерешённая задача.
- Миграция проверена upgrade/downgrade на тестовой схеме. Время блокировки/перенос на большой существующей базе и полный путь Alembic не измерялись.

3. Открыть окно обслуживания и остановить записи смет, работы через смету и фоновые writers. Дождаться завершения текущих запросов. Убрать из обслуживания все старые backend-процессы: старый PUT не проверяет expectedRevision даже при наличии триггера. Смешанный rolling rollout старых/новых writers небезопасен.
4. При подтверждённом head `0102_platform_company_features` применить `0103_estimate_revisions` штатным Alembic в разрешённой среде. Команда-цель: `alembic upgrade 0103_estimate_revisions`. При другом head/ветках остановиться и сверить цепочку. Проверить BIGINT NOT NULL/default 1, CHECK, BEFORE UPDATE trigger и head; сравнить количество смет и контрольные бизнес-данные. Учесть блокировку таблицы во время ALTER.
5. Запустить новый backend на мигрированной схеме, оставив внешние записи закрытыми. Проверить import/startup/health и GET сметы с revision; проверить обработку отсутствующей и неверной ревизии. Новый frontend нельзя направлять на старый backend: тот может записать данные, а клиент лишь затем заметит отсутствие revision в ответе.
6. Переключить frontend на сборку той же версии. Проверить manifest/хеши и фактические загруженные скрипты. Старые вкладки обновлять только после копирования их локальных правок; не считать 428 видимым уведомлением. Закрыть/обновить все активные старые клиенты до возобновления записи. Если гарантировать это нельзя, оставить обслуживание или отдельно решить совместимость; обход expectedRevision не разрешать.
7. Выполнить проверки ниже на выделенных проверочных данных, затем возобновить записи и наблюдать 409/428/5xx. Рост 428 означает оставшиеся старые клиенты, а не повод отключить проверку ревизии.
8. Завершать выпуск только после отдельных проверок backend, database, frontend, browser. Лишь тогда оформлять deployed.json и verified.json с одним SHA и четырьмя checks=true согласно docs/deployment-retention.md. До этого сохранять резерв. После успешной проверки выполнить установленную политику удаления резервов/staging; не рассчитывать, что прежний staging останется для следующего выпуска.

### План отката с учётом 0103

- При провале миграции/проверок оставить записи закрытыми и резерв на месте. Проверить фактический Alembic head, column/trigger и транзакционный rollback; не продолжать установку по одному успешному health.
- При сбое приложения остановить новые writers и дождаться запросов. Сначала сохранить/экспортировать локальные черновики и зафиксированные после установки операции. Не восстанавливать старый полный backup БД поверх новых записей: это потеряет принятые данные.
- Предпочтительный аварийный вариант — вернуть согласованную старую пару backend/frontend, **сохранив добавочную column/trigger**, но держать запись смет закрытой до исправления. Само наличие revision не защищает старый backend: сравнения expectedRevision у него нет. Возможность чтения старой парой с добавочной схемой нужно проверить на staging; здесь это не проверялось.
- Если действительно нужен откат схемы, полностью остановить использующие revision процессы, сохранить актуальный backup и выполнить штатный downgrade до `0102_platform_company_features` в согласованном окне. Он удаляет trigger/function/column, не возвращает бизнес-данные к прежнему состоянию. После удаления column новый backend запускать нельзя. Сверить head, схему, сохранность данных и старую пару на staging перед открытием сервиса.
- Откат на старый код возвращает исходный риск потерянных обновлений. Возобновлять конкурентные записи в таком состоянии нельзя объявлять безопасным откатом; требуется отдельное решение владельца выпуска или исправленная версия. Полный runtime-откат в этой локальной проверке не пройден; проверен только SQL upgrade/downgrade узким PG-набором предыдущего прохода.
- Не создавать deployed/verified для неуспешного выпуска и не удалять его резерв/staging. После окончательно проверенного восстановления/исправления применять правила retention, не накапливать release-копии.

### Изменения за пределами узкого исправления обычного PUT

- **Сопутствующее усиление изоляции** в backend/main.py: пересчёт ЖПР требует company_id, ограничивает им смету и агрегат; hidden endpoint использует выбранную компанию. Это не нужно только для порядка ответов одного редактора, но закрывает небезопасные альтернативные writers и входит в ранее запрошенную проверку изоляции. Может оформляться отдельным логическим коммитом, не является новым изменением этого прохода.
- **Расширение контракта других мутаций:** status/template/delete/hidden/include и revision при создании/импорте/AI/нормах шире обычного сохранения. Оставлено для запрошенного охвата всех путей: без адаптации они либо обходили бы контроль, либо ломались бы на новом обязательном expectedRevision.
- **Изменение UX:** общие dirty/saving/saved/conflict/error и отказ hidden detection при несохранённых правках; success-alert переключения шаблона заменён общим статусом. Последняя замена alert не необходима для атомарности записи и является сопутствующим изменением интерфейса; при требовании строго минимального UI-diff её можно рассмотреть отдельно. В этом проходе поведение не менялось.
- **Служебные/test-only изменения:** Python __init__, безопасные runners, адаптации общих fixtures и часть revision-полей в старых тестах сами гонку не исправляют. Они обеспечивают воспроизводимость и совместимость тестов; косметические поля в загрузочных fixtures не обязательны.
- Startup CAS и перевод include-changes с autocommit на транзакцию относятся непосредственно к защите: без них старый снимок или отпущенная блокировка обходят проверку. Это не отдельная функциональность.

Независимых бизнес-функций, деплоя, обновления зависимостей проекта и изменений
рабочих данных в патче нет. Нет и исправления старого кешированного клиента:
его ограничение явно зафиксировано вместо объявления проверки успешной.

`estimate-race.patch` включает исправления пяти блокеров и этот отчёт. Проверены
`git apply --check`, применение к временной копии исходного индекса и побайтовое
совпадение всех 40 файлов. Итоговая контрольная сумма находится в
`tmp/estimate-blockers/patch-check.log`.
Патч, build, логи и временные проверочные scripts/fixtures внутрь патча не включены.
