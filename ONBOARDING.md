```bash

```

```bash

```

Перед любой правкой сначала прочитать существующий код и ближайшие тесты.
Не удалять рабочие данные, старые документы, сметы, накладные или историю
без отдельного согласованного плана и проверяемого cleanup.

## Назначение системы

`stroyka-app` - ERP для строительных компаний.

Главная операционная цепочка:

`объект -> смета -> пакет работ -> исполнители -> ЖПР/акты -> материалы -> склад -> финансы -> бухгалтерия`

Смета заказчика является основанием для работ, материалов и экономики. Для
объектов без ГРАНД-сметы допустим внутренний прайс, но он не должен
переписывать исходные сметные данные.

### Редакции смет

- Новая активная редакция меняет будущий план работ и снабжения. Она не
  переписывает подтверждённые ЖПР, подписанные акты, ручные цены бригад,
  складскую историю и платежи.
- Перед активацией или сравнением загружаются полные строки старой и новой
  редакции. Свод по объекту показывает только изменённые, добавленные и
  исключённые позиции: пакет, раздел, наименование, объём и сумму
  `было -> стало`.
- Выданные работы и открытые заявки переносятся между редакциями только
  отдельной проверяемой операцией и только в незакрытом остатке. Исторический
  факт не переносится и не пересчитывается.
- Связь редакций, назначений и снабжения строится по сохранённым
  `company_id`, `project_id`, `estimate_id` и ключу строки. Совпадение только
  по названию объекта или работы не является достаточной связью.

## Обязательные правила данных

### Сохранность и аудит

- Рабочие объекты, активные сметы, материалы, складская история, ЖПР,
  накладные, оплаты и audit log не удаляются обычными UI-действиями.
  Неиспользуемый черновик сметы без рабочих связей может безвозвратно удалить
  только директор выбранной компании. Вместе с ним удаляются только его
  техническая история версий и автоматически созданные черновые сверки.
  Сверка на проверке/утверждении, ЖПР, АОСР, договорная позиция, настройка норм,
  переписка или заявка снабжения по-прежнему запрещают удаление.
- Исправление материала проводится корректировкой, списанием, возвратом,
  перемещением или инвентаризацией с записью в истории.
- Закрытие объекта является отдельной процедурой директора. Перед мягким
  архивированием система показывает незакрытые остатки, заявки, ЖПР и задачи,
  но не блокирует решение директора. Архивирование меняет только статус
  объекта и дату архива: документы, сметы, склад и история не переносятся и
  не удаляются.
- Все новые бизнес-операции получают владельца только на сервере. Клиентские
  `companyId` и HTTP-заголовки не доказывают право доступа.
- Изменения цепочек объекта, склада, смет, финансов или доступа требуют
  backup БД, профильные тесты, `npm run build` и production smoke.

### Граница SaaS и компании

Иерархия:

`system_owner -> platform_account -> company -> project`

- `platform_account` - жёсткая граница независимого клиента.
- `company_id` - обязательный рабочий контекст внутри аккаунта.
- Режим `Все компании` работает только внутри одного `platform_account` и
  предназначен для чтения сводок. Любая запись требует выбранной компании.
- Роль для рабочего действия определяется активным `user_company_roles` в
  выбранной компании; глобальная `users.role` не повышает права.
- Одна компания не может быть выбрана, даже при ошибочной membership-записи,
  если она принадлежит другому `platform_account`.
- Проект всегда имеет одну компанию. Название проекта не является границей
  доступа; новые цепочки используют `project_id` и подтверждённый `company_id`.
- Файлы, уведомления, AI/OCR, экспорт и фоновые задачи наследуют владельца
  основного документа.

Production-проверки на 2026-08-03 подтвердили: изоляцию выбранной компании
внутри одного аккаунта, отказ записи в `Все компании`, а также отказ доступа
к компании другого аккаунта (`403`).

### Склад, поставки и первичные документы

- Основной склад поддерживает два разных сценария:
  - приход с поставщиком и первичным документом - создаёт обязательство для
    бухгалтерии;
  - внутренний приход без поставщика - доступен директору и заместителю,
    создаёт остаток и историю, но не создаёт supplier invoice или оплату.
- Прораб принимает только на закреплённый объектный склад. Основной склад для
  него недоступен.
- В цепочке снабжения одна компания сохраняется от заявки и КП до поставки,
  supplier invoice, складской накладной и истории склада.
- Новые приходы и выдачи могут хранить точную связь со строкой накладной.
  Автоматически угадывать источник по названию материала запрещено.
- В исторических движениях отсутствие прямой связи остаётся `legacy`; их не
  перепривязывать и не корректировать автоматически.
- Приход по упаковке не пересчитывается сам: правило `тара x содержимое =
  базовая единица` подтверждает директор или заместитель. Неизвестная тара
  остаётся в исходной единице до проверки.
- Ручная проверка старой упаковки сохраняет решение `confirmed`,
  `discrepancy` или `document_required`, комментарий, автора и снимок
  доказательств. Она не меняет остатки, накладную и историю движений.
- Автоматическую корректировку остатков по упаковкам не внедрять, пока не
  согласованы сверка, отмена операции и полная прямая трассировка движений.
- Контракт будущей корректировки описан в
  `docs/material-packaging-stock-correction.md`: сначала партии прихода и
  проводки лотов для новых данных, затем одна обратимая операция с preview и
  подтверждением директора/заместителя. Исторический агрегированный остаток
  остаётся только в ручной сверке.

### Материалы и снабжение

- Закупочный расчёт объединяет строки только по точной канонической позиции
  или подтверждённому алиасу. Семейство (`кабель`, `крепёж`, `профиль`) не
  является основанием для объединения.
- Сомнительные единицы, упаковки, алиасы и нормы получают статус `Проверить`
  и не попадают в `Докупить` или массовые заявки.
- Заявка из сметного контроля хранит проект, пакет, смету и точные
  координаты исходной строки. Устаревший или повторный запрос отклоняется.
- Перемещение на объект не отменяется только из-за расхождения со сметой:
  оно сохраняет снимок проверки и создаёт задачу сметчику/руководителю.
  Физический остаток, доступность партии накладной, права и компания по-прежнему
  проверяются строго.
- Поставщик может быть общим справочником, но условия, видимость КП,
  рейтинги и документы принадлежат связи конкретной компании с поставщиком.
- Объединение поставщиков делается только после ручного подтверждения
  юридического лица по ИНН/ОГРН или иной сильной идентичности. Совпадение
  названия или email является кандидатом на проверку, а не основанием для
  автоматического слияния.

### AI, MAX и сообщения

- AI готовит черновики и контрольные задачи, но не проводит склад, не меняет
  смету, не создаёт оплату и не закрывает объект без человека.
- AI-задачи, findings, отчёты и вложения принадлежат компании/проекту либо
  явно помечены системными; дедупликация не должна пересекать компании.
- Каждый инструмент агента получает список компаний только из проверенного
  сервером company context. Пустой контекст всегда даёт пустой результат без
  запросов к бизнес-таблицам; прямые глобальные чтения для агента запрещены.
- Один тип агента может обслуживать несколько компаний, но каждый запуск
  изолирован по `company_id`, роли и правам. Внешней модели передаётся только
  минимальный результат разрешённых инструментов, а не прямой доступ к БД.
- MAX-каналы, outbox, аккаунты и вложения используют сохранённого владельца.
- Внутренние MAX-каналы не создают CRM-лид; маркетинговые каналы создают лид
  только для своей компании.

## Проверки

Пароль не пишется в shell history:

```bash
read -rsp "Пароль: " PASS; echo
read -rp "Код 2FA: " CODE
```

Базовые проверки перед push:

```bash
PYTHONPYCACHEPREFIX=/tmp/stroyka-pycache python3 -m py_compile backend/main.py
npm run build
git diff --check
```

После backend/API изменения локально или на VPS:

```bash
npm run smoke:prod
npm run smoke:public-api
```

Защищённая проверка production:

```bash
SMOKE_EMAIL='nikolbas007@gmail.com' \
SMOKE_PASSWORD="$PASS" \
SMOKE_2FA_CODE="$CODE" \
npm run smoke:prod
unset PASS CODE
```

Профильные проверки запускаются только для затронутого контура:

```bash
# снабжение, поставка, накладная, складская история
npm run smoke:supply-chain

# инструменты и инвентарь
npm run smoke:inventory-ownership

# компания/аккаунт/CRM и отрицательные tenant-проверки
npm run smoke:platform-crm

# внутренний приход без поставщика
npm run smoke:main-warehouse-receipt

# ручная проверка упаковки без изменения остатка
npm run smoke:material-packaging-review

# material-control -> заявка с исходной сметной строкой
npm run smoke:material-control-lineage

# только чтение: подозрительные объёмы и ошибочно помеченные материалы в активных сметах
npm run audit:estimate-material-volumes

# готовность к будущей корректировке упаковок, без изменений данных
npm run audit:material-stock-correction-readiness

# audit supplier candidates, без изменений
npm run audit:supplier-duplicates
```

При расчёте потребности снабжения ресурсные корректировки сметы учитываются со
знаком минус. Например, строки материала `+41,4 м3` и корректировки `-41,4 м3`
дают план `0 м3`, а не `41,4 м3`. Отрицательные строки работ при этом не
считаются материалами. Старые заявки хранят снимок расчёта на дату создания;
тестовые записи сначала проверять через `npm run smoke:test-artifacts`, не
удалять вручную из базы. Карточка старой заявки без `calculatedAt` должна явно
показывать, что это снимок на дату создания; новые расчёты сохраняют и выводят
время пересчёта. Создание, содержательное изменение или активация сметы со
статусом `Активная` автоматически обновляет `estimateControl` связанных
открытых заявок той же компании и объекта. Автопересчёт не меняет количество,
статус, поставщиков или другие бизнес-поля заявки.

Browser smoke для большого проекта материалов:

```bash
SMOKE_EMAIL='nikolbas007@gmail.com' \
SMOKE_PASSWORD="$PASS" \
SMOKE_2FA_CODE="$CODE" \
BROWSER_SMOKE_PROJECT_NAME='Кисловодск Лицей 4' \
npm run smoke:browser-materials-prod
unset PASS CODE
```

Для browser smoke на VPS нужен Chromium (`/usr/bin/chromium-browser`). При
`429` или неверном 2FA не менять код: подождать лимит, запросить новый код и
повторить проверку.

## Production deploy

На VPS:

```bash
cd /var/www/stroyka-app
git pull --ff-only
bash deploy.sh
```

`deploy.sh` берёт lock `/var/lock/stroyka-deploy.lock`, проверяет Python,
собирает frontend во временную папку, перезапускает backend, атомарно
публикует frontend и запускает public smoke. Не запускать второй deploy, пока
первый не завершился.

После deploy выполнить как минимум:

```bash
npm run smoke:prod
```

После изменения API добавить:

```bash
npm run smoke:public-api
```

После изменения защищённого сценария выполнить соответствующий protected
smoke с паролем и свежим 2FA-кодом. Если полный smoke уже подтвердил публичные
маршруты, повторную авторизованную проверку запускать с
`SMOKE_PROTECTED_ONLY=1 npm run smoke:prod`: так предварительные анонимные
запросы не расходуют общий Nginx rate limit перед `/login`. Если smoke сообщает
nginx HTML вместо backend JSON, сначала добавить точный
`location ^~ /<api-prefix>` в активный server block nginx, затем
`nginx -t && systemctl reload nginx` и повторить оба smoke.

Для API статусов фоновых заданий готова безопасная повторяемая команда:

```bash
python3 scripts/ensure_agent_jobs_nginx_route.py /etc/nginx/sites-enabled/stroyka
nginx -t && systemctl reload nginx
```

Скрипт добавляет отдельно `/agent-jobs` и `/agent-jobs/{id}`, перед изменением
создаёт резервную копию в `/etc/nginx/backups` и ничего не дублирует при
повторном запуске.

После деплоя отмены фоновых заданий выполнить:

```bash
SMOKE_PROTECTED_ONLY=1 npm run smoke:prod
npm run smoke:agent-job-cancellation
```

Вторая команда создаёт queued/running задания и запись аудита только внутри
одной транзакции. Успех обязан содержать `steps=[cancel_queued, audit,
protect_running]`, `rolledBack=true`, `persistedAgentJobs=0` и
`persistedAuditRows=0`.
